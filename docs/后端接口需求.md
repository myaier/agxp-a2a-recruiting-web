# 后端接口需求 — AGXP · 求职端

> 面向后端同事。前端已按下述契约留好接入位（`src/数据/接口层.ts`），字段确认后前端改一处即可接上，屏幕代码不动。
> 本文档从已实现的 20 个屏反推，每个接口都标注了「对应前端」，可对照线上原型看：
> https://myaier.github.io/agxp-a2a-recruiting-web/

## 0. 全局约定（先读这节）

### 0.1 业务硬约束（产品定义，接口设计不可违反）

1. **双盲池 + 数值不披露**：求职者的期望薪资、底线，企业的薪资带，**任何接口都不得把对方的数值返回给本方**。匿名初筛阶段只返回布尔结论（「薪资带有交集」/「无交集」）或差额描述（「差 2K」），绝不返回对方原始数字。
2. **底线仅代理可见**：求职意向里的「本意向底线」只进代理决策引擎，不出现在任何面向对方的响应里。
3. **不做谈薪、不做谈到岗**：全系统没有报价、出价、还价字段。薪资与到岗时间由候选人与 HR 在意向确认后的真人聊天里自行商定，代理不介入 —— 「需要协调」阶段只处理软性要求（作息、办公方式、加班强度、团队规模、汇报线等）。
4. **四阶段状态机**：`匿名初筛 → 递交简历 → 需要协调 → 意向确认`。阶段推进由代理服务驱动，前端只读。不可跳阶段、不可回退（终止 = 归档，不是回退）。
5. **匿名是单向的 + 联系方式互换不可逆**：招聘方（公司名、对接人姓名与职务）从第一轮起对候选人实名可见；候选人在意向确认前只有代号与画像，任何接口都不得把候选人的真名 / 联系方式返回给企业方。双方都确认意向后才交换候选人真名与双方联系方式，接口要做双方确认的原子判定。
   对称的只有薪资数值（见第 1 条），身份不对称。
6. **屏蔽不可泄漏**：屏蔽现雇主及关联公司是双向的（互不推荐、互不出现在对方池子里）。

### 0.2 技术约定

- 字段命名建议 `camelCase` 英文。前端域模型是中文字段（见 `src/数据/类型.ts`），映射在前端 `接口层.ts` 一处完成，后端不用迁就。
- 鉴权：`Authorization: Bearer <token>`。登录接口见 §1。
- 时间戳统一 ISO 8601（UTC），前端负责本地化展示（原型里的「D1 09:15」「已停 6 小时」都是展示层格式）。
- 错误格式建议：`{ "code": "NEGOTIATION_NOT_FOUND", "message": "..." }`，HTTP 语义化状态码。
- 列表接口预留分页参数 `?cursor=&limit=`（原型数据量小，未用，但契约先定）。
- 实时性要求见 §9（推送）。

## 1. 认证（屏：R1 登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/sms-code` | 发送验证码。入参 `{ phone }`。需限流 |
| POST | `/auth/login` | 验证码登录。入参 `{ phone, code }`，未注册自动创建账号 |
| POST | `/auth/wechat` | 微信登录（v2，前端按钮已留） |

`/auth/login` 返回：

```json
{
  "token": "…",
  "isNewUser": true,
  "role": "seeker"
}
```

- `isNewUser=true` → 前端进注册引导（R2 → A1 → A2 → A3 → A4）；否则直接进主壳。
- 身份分流（R2）：本期只有 `seeker`（求职者）。猎头 / 企业端未做，接口预留 `role` 字段即可。

## 2. 用户档案与简历（屏：A2 工作经历、A3g 个人优势、A15 我的、A17 我的简历）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/profile` | 基本信息：姓名、年限、学历、当前状态、对外画像 |
| PUT | `/profile` | 更新基本信息 |
| GET | `/profile/experiences` | 工作经历列表 |
| POST / PUT / DELETE | `/profile/experiences/:id` | 经历增删改 |
| POST | `/profile/resume` | 上传简历文件（multipart）。**异步解析**，返回 `{ taskId }` |
| GET | `/profile/resume/parse-result?taskId=` | 轮询解析结果：预填的经历段 + 个人优势草稿 |
| PUT | `/profile/strengths` | 个人优势（≤500 字）+ GitHub 链接 |
| GET | `/profile/diagnosis` | 代理诊断（A17 顶部绿条：「2 项待优化」及明细） |
| GET / POST / DELETE | `/profile/blocked-companies` | 屏蔽公司。注意：选「在职·保密」时后端要**自动**屏蔽现雇主及关联公司并打标 `auto: true` |

工作经历对象示例（对应 A2 屏每个字段）：

```json
{
  "id": "exp_1",
  "company": "字节跳动",
  "industry": "互联网 · 本地生活",
  "startDate": "2019-06",
  "endDate": null,
  "title": "研发专家 2-2 · 交易中台",
  "description": "主导交易网关重建与峰值稳定性治理…",
  "hideFromCompany": true
}
```

`hideFromCompany` 即 A2 屏「对这家公司隐藏我的信息」开关，触发 §0.1 第 6 条的双向屏蔽。

## 3. 求职意向（屏：A20 意向管理、A21 添加意向、顶栏意向切换）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/intentions` | 意向列表（上限 5 个），含每个意向的在谈数 |
| POST | `/intentions` | 新建意向。**保存即触发代理入池初筛** |
| PUT / DELETE | `/intentions/:id` | 修改 / 删除 |

意向对象（对应 A21 表单逐项）：

```json
{
  "id": "int_1",
  "type": "fulltime",
  "city": "杭州",
  "extraCities": ["上海"],
  "position": "平台架构 · 基础平台",
  "industries": ["金融科技", "基础软件"],
  "expectedSalary": { "monthly": 55, "months": 15 },
  "bottomLine": { "monthly": 52, "months": 15 },
  "activeNegotiations": 1
}
```

> ⚠️ `bottomLine` 是 §0.1 第 2 条说的底线：**只写不回显给对方**，代理触线即拒。返回给本人时可以带（自己能看自己的底线）。

注册引导 A3a–A3f 收集的：求职状态（在职保密 / 已离职）、到岗节奏、硬性排除项（大小周 / 纯外包 / 全现场 / 频繁出差 + 自定义文本）——挂在用户级或意向级均可，建议：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / PUT | `/profile/preferences` | 求职状态、到岗节奏、硬性排除、披露偏好 |

硬性排除是**初筛红线**：命中即代理直接终止（见 §5 未通过说明里的呈现）。

## 4. 在谈列表（屏：A6·L 首页）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/negotiations?intentionId=` | 某意向下的在谈列表 |

单条结构（前端 `类型.ts` 的 `在谈单`，对照 A6·L 卡片自上而下）：

```json
{
  "id": "neg_01",
  "company": { "name": "云衢科技", "brief": "金融基建 · C 轮 · 500-1000 人" },
  "salaryBand": "50-65K",
  "jobTitle": "资深后端工程师 · 交易网关",
  "tags": ["上海 · 浦东", "15 薪", "混合 3+2", "45 天到岗"],
  "stage": "intent_confirm",
  "round": 3,
  "needsUser": true,
  "nextStep": "见面条件已一致，是否确认意向",
  "subText": "确认后转真人沟通 · 对方已确认",
  "gap": null,
  "matchScore": 94,
  "urgentBanner": { "text": "基本条件全部一致，对方已确认 — 只差你点头", "stalledFor": "PT6H" }
}
```

- `stage` ∈ `anon_screening | resume_exchange | coordination | intent_confirm`（四阶段，见 §0.1）
- `needsUser=true` 的排在前面（前端也会再排一次，但服务端排好利于分页）
- `gap`（分歧轴）在协调阶段出现：`{ "mine": "你的期望下限 52K", "delta": "差 2K", "theirs": "岗位带上限 50K" }` —— 注意这是**代理生成的展示文案**，不是原始数值接口（§0.1 第 1 条：本方看得到自己的数字和差额，看不到对方原始带宽，「岗位带上限 50K」是对方主动亮出后才可出现，由代理服务控制）

## 5. 谈判详情与决策（屏：A6·C / A6a 详情、A6b 未通过、A24 拿不准弹层）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/negotiations/:id` | 详情：列表字段 + 各阶段代理小结 + 职位详情 Tab 数据 |
| POST | `/negotiations/:id/decision` | 用户决策：`{ "action": "accept" \| "quit", "comment": "…" }` |
| POST | `/negotiations/:id/confirm-intent` | 确认意向。双方都确认后触发联系方式互换（原子，见 §0.1 第 5 条） |
| GET | `/negotiations/:id/rejection` | 未通过说明（A6b）：逐条核对项 ✓/✕ + 代理小结 + 松一档建议 |

详情里每个阶段的代理小结（对应详情页时间线节点）：

```json
{
  "stage": "resume_exchange",
  "status": "passed",
  "at": "2026-08-11T03:02:00Z",
  "summary": "软性核对通过：方向高度对口、平均任期 4.5 年。唯一保留项 — 直管从 8 人降到 5 人，按你「可接受」的偏好放行。",
  "attachment": { "name": "沈亦舟_简历_2026.pdf", "note": "已发给对方（隐去联系方式）" },
  "threadLink": true
}
```

**决策接口的返回要带「规则沉淀建议」**（驱动 A24 弹层）：

```json
{
  "negotiation": { "…": "决策后的最新状态（阶段推进 / 已归档）" },
  "ruleSuggestion": {
    "decisionSummary": "硅基流动「卡在现金」这一项你同意放宽 —— AI代理会立刻回报对方。",
    "draftRule": "现金差 2K 以内的，可以直接替我放宽",
    "impact": "近 7 天有 4 次这样的询问会消失，AI代理直接替你过滤掉。"
  }
}
```

用户点「记成规则」→ 前端调 §7 的建规则接口并带 `sourceNegotiationId`。

「松一档」建议（A6b）：`{ "blockedCount": 4, "expectedGain": 3, "rule": "不接受大小周" }`，用户选「改成可谈」→ 同样走 §7 规则接口（改规则）。

## 6. 往来记录与叮嘱（屏：A8·B）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/negotiations/:id/thread` | 代理间对话流 + 系统事件 + 历史叮嘱，支持 `?before=` 翻旧消息（原型里「早前 4 条」折叠） |
| POST | `/negotiations/:id/instructions` | 用户发叮嘱（介入）。入参 `{ "text": "超过 45 天就不等，直接终止" }` |

thread 条目类型（前端 `往来条目`）：

| type | 说明 | 额外字段 |
|---|---|---|
| `their_agent` | 对方代理发言 | `text, at` |
| `our_agent` | 我方代理发言 | `text, at` |
| `system` | 系统事件（分歧出现 / 企业确认 / 核对清零） | `text` |
| `instruction` | 用户叮嘱回显 | `text, at` |
| `intent` | 意向节点（3/3 条件一致 → 等你确认） | `text` |
| `day_divider` | 日期分隔 | `day` |

**发叮嘱的返回也要带 `ruleSuggestion`**（同 §5 结构）——原型里发完叮嘱 500ms 后弹 A24，就吃这个字段。同时返回我方代理的回执消息（「收到，我按这个口径继续谈」）。

### 推送（决定产品「代理替你干活」的体感，需要实时通道）

建议 WebSocket `/ws`（或 SSE），事件至少覆盖：

| 事件 | 触发 | 前端反应 |
|---|---|---|
| `negotiation.updated` | 阶段推进 / 对方回复 / 分歧出现 | 刷新在谈卡、详情时间线 |
| `negotiation.needs_user` | 出现需要你的决策 | 红描边置顶 + 横幅计数 +（App 内推送） |
| `message.new` | 任何会话新消息 | 未读数、消息流追加 |
| `briefing.updated` | 简报生成 | A27 简报卡刷新 |

原生推送（APNs）在 Capacitor 壳接入后走原生层，后端只需在上述事件上并行发推送。

## 10. 前端接入方式（给后端的对接说明）

前端所有数据进出都收口在 `src/数据/接口层.ts` 的 `数据源` 接口。联调时前端会：

1. 照本文档实现一个 `HTTP数据源`（fetch + 字段映射：英文 camelCase → 中文域模型）；
2. `export const 数据 = HTTP数据源;` 一行切换，20 个屏零改动。

因此：**字段名以本文档为草案，后端可以改，改完知会前端同步映射即可**；但 §0.1 的六条业务硬约束不可协商。
