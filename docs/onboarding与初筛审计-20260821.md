# Onboarding 与初筛配置审计（2026-08-21）

## 结论

初筛不应该依赖 Agent 临场追问。每一条可自动淘汰的条件，都必须满足：

1. 招聘端有结构化要求；
2. 候选端有同口径的结构化回答；
3. 用户知道它是“必须满足”还是“加分偏好”；
4. 系统能解释命中、未命中或信息不足；
5. 薪资只计算区间交集，Agent 不询价、不报价、不谈薪。

## 产品对照

- [LinkedIn Open to Work](https://www.linkedin.com/help/linkedin/answer/a512315)把职位、地点、办公方式、开始时间、雇佣类型作为独立偏好，而不是塞进一段自由文本。
- [LinkedIn Screening Questions](https://www.linkedin.com/help/recruiter/answer/a519651)把学历、地点、语言、证书、经验、工作许可、技能、混合办公等做成结构化问题，并允许标记 must-have。
- [Indeed Job Search Preferences](https://support.indeed.com/hc/en-us/articles/32603395892109-Adding-or-Editing-Job-Search-Preferences)进一步拆出工作时间、薪资、通勤、异地与远程；资格信息则包含语言、经历、学历、技能、执照和证书。
- [Indeed Screener Questions](https://www.indeed.com/hire/resources/howtohub/how-to-use-screener-questions-on-indeed)明确区分 Required 与 Preferred：前者可以自动筛掉，后者只做排序和提示。

可借鉴的不是页面数量，而是“偏好 / 资格 / 必须项”三类数据不混用。

## 三条本地流程

### 学生求职

角色与机会类型 → 基本信息 → 学历 / 学校 / 专业 / 时间段 → 实习经历、技能、证书 → 求职状态 → 薪资与排除项 → 披露 → 头像 → 飞书。

结构化初筛字段：校招/实习类型、城市、办公方式、实习月数、每周到岗天数、毕业届别、学历、专业、技能、证书与语言、薪资带交集。

### 社招求职

角色与机会类型 → 薪资 → 基本信息 → 求职状态 → 学历 → 工作经历、技能、证书 → 排除项 → 披露 → 头像 → 飞书。

结构化初筛字段：社招全职/兼职、城市、办公方式、工作年限、到岗状态、学历、经历、技能、证书与语言、薪资带交集。

### 招聘方

实名认证 → 招聘名片 → 发布岗位（三步）→ 飞书 → 企业主壳。

结构化初筛字段：招聘类型、职位类别、城市、办公方式、薪资带、学历、经验；校招补届别，实习补月数和每周到岗天数。职位关键词作为技能依据；自由文本只做加分偏好。

## 本轮发现并修复

- 招聘方首次注册绕过实名认证：已恢复认证入口。
- 招聘名片可直接改认证姓名和公司：已锁定，仅职务可编辑。
- 学生路径跳过已有的实习经历 / 技能 / 证书页：已接回流程。
- 学生端没有实习时长和每周到岗数据，无法对应招聘端条件：已补。
- 求职端没有结构化机会类型与办公方式：学生 / 社招分别补齐并持久化。
- 新岗位暗带三条用户没确认过的隐藏硬条件：已删除。
- 新岗位先创建半成品再补字段，存在编号与计薪单位错位：改为一次派发完整岗位。
- 招聘要求自由文本曾同时承担筛选与谈判：现在明确为“加分偏好”，不能自动淘汰。
- 发布前缺少合同复核：新增“匿名初筛合同”摘要，明确薪资只做交集核对。

## 后端接入约束

- 必须项使用枚举、数值区间或布尔值，不使用自由文本自动拒绝。
- 未采集到候选答案时返回“待核对”，不能当作“不符合”。
- 每次筛选结果应保存字段、双方版本、结论与原因，支持撤销和审计。
- 招聘方修改必须项后，只对新筛选或待核对候选按新版本执行；不得静默改写历史结论。
