# STG Onboarding Suite（stg-onboarding）

Suite `stg-onboarding` 在真实 STG 后端上固化两个角色从**空账号**出发的首次
onboarding 旅程：两个 Case（`stg-onboarding-candidate` / `stg-onboarding-recruiter`），
每 Case 两个变体（`manual` / `parsed`），共四个互相独立的选择项。

- 状态：本文只固化旅程与判定口径。四个选择项现阶段均为 `NOT_RUN` / 待 final gate，
  不预填任何通过数；正式运行属 final gate 的逐项决策。
- 权威设计：`docs/superpowers/specs/2026-09-14-stg-onboarding-contract-alignment-design.md`
  第 4–6 节（接口合同、状态分流、四条旅程）。
- 入口注册：[真实后端行为验收](真实后端行为验收.md)第 1 节范围选择与第 10 节。
- 报告：[真实后端报告模板](真实后端报告模板.md)第 5 节；证据落既有
  `dogfood-output/<run-id>/`，不新建报告平台。
- 独立性：与 `STG 基础试点` 互不替代、互不计入；旧 local B01–B05 / H01–H04 与
  [backend-local onboarding](backend-local-onboarding.md)（均已历史归档）互不替代、
  互不计入；原 `全部` 范围已随 local 归档退出活动入口。

## 1. 目的与范围

验收的是 Spec §4/§5 已实现的前端行为在真实 STG 上的表现：`GET /api/v1/me/onboarding`
的角色状态分流（选择身份 / 未完成引导 / 已完成主页 / 停用与读取失败恢复）、
`POST /api/v1/me/onboarding/{role}/complete`、完成后的草稿清理与回访落点。

- 每个选择项都是一条完整、可独立执行的用户旅程；不强迫先跑其他项。
- 非目标：企业日常编辑与设置 CRUD、长双角色复合旅程、PDF 解析质量评分
  （不是 parser benchmark，只判「真实成功 + 关键合成事实合理预填 + 用户确认后一致」）、
  local acceptance 栈行为。
- 本地 route-fixture Playwright/Vitest 只证明拦截边界，不是 STG 证据。

## 2. 选择与运行模型

| 选择项 | 类型 | 能力前提（部署依赖） | 现阶段状态 |
| --- | --- | --- | --- |
| candidate/manual | 核心 | STG 部署含 onboarding 查询与完成接口 | `NOT_RUN` |
| candidate/parsed | 条件 | 上项 + 后端 B02 附件验收开放 + 真实解析任务可用 | `NOT_RUN` |
| recruiter/manual | 核心 | STG 部署含 onboarding 查询与完成接口 | `NOT_RUN` |
| recruiter/parsed | 条件 | 上项 + 真实 JD 导入任务可用 + 终态有限保留支持 | `NOT_RUN` |

- 每项 = 新 `STG_RUN_ID` + 新浏览器会话；不复用上一项的账号、资料、预填、草稿或公司名。
- 保持 CLI 两个账号槽位约定：单 Case 只消费所需角色的 alias，另一个槽位保持未消费；
  finally 收尾按轮履行。
- 选择身份是 Case 的一个步骤；两个 Case 互不等待。支持只选单个三元组
  （Case + variant），不强迫跑长复合链。
- 条件项能力未开放时记 `NOT_RUN`（原因=能力未开放，写明缺哪项），不运行、
  不转手填凑数；解析未开放时经用户批准可只跑两个 manual，但报告必须写明
  四变体尚未全验收。

## 4. 生命周期与 operator 命令（部署依赖）

每个选择项的生命周期概念顺序（Spec §6）：

```text
（从调用者提供的后端 checkout 根执行）
1. ephemeral-empty 场景 prepare（本轮唯一 STG_RUN_ID）
2. verify --stage initial        # 确认空起点
3. 浏览器旅程（第 6 / 7 节）
4. verify --stage journey        # 后端侧旅程终态核对；不代表 UI PASS
5. finally cleanup               # 无论旅程成败都履行
```

**部署依赖警示（先核对、后执行）**：上面的场景名与阶段旗标是后端批准 Spec 的表达，
不是已核实的命令。执行前必须从该后端 checkout 读取
`.claude/skills/agxp-recruitment-stg-env/SKILL.md` 等现场文档与 CLI 帮助，核对子命令、
参数与输出；现场 CLI 输出是真相，本文件不是版本真相源。

- 命令未实现或语义不同：按实际能力记录；**未实现的命令不得当作真实命令执行**；
  受影响项记 `NOT_RUN`（命令缺失）或 `BLOCKED`（命令存在但前置失败），并写明版本差异。
- prepare 未明确 READY 或 initial verify 失败时不得打开浏览器消费数据。
- STG 前端服务、代理上游证据（`https://recruitment-stg.agxp.ai`）、退出码语义
  （`2` 参数错误 / `75` BLOCKED / `1` FAIL）、占用与恢复、foreign run 处置沿用
  [真实后端行为验收](真实后端行为验收.md)第 4 与 6.1 节，本文件不复制其全文。
- 记录每轮 receipt / login 文件路径与实际 deployment tag / source revision。

## 5. 安全登录与凭据

- 登录材料位于后端 checkout 的
  `.agxp-recruitment-stg-env/sessions/<STG_RUN_ID>/login.json`；号码只读入受限进程；
  OTP 只经后端 skill 声明的受限通道取得。
- 输入方式：UI 内编辑区号 + 输入号码 + OTP（沿用 `STG 基础试点` 口径）。执行前确认
  浏览器工具支持不落入 shell argv、终端输出、聊天、报告、截图/录像的安全输入；
  做不到记 `BLOCKED`，不能用明文参数绕行。
- **登录凭据输入期间停止截图与录像**；报告不写手机号、OTP、Cookie、Authorization、
  proof 或完整认证状态；只引用 receipt / login 路径与允许公开的安全实体 ID。
- 公开证据只记「受限内核对通过/失败」的结论。

## 6. Case stg-onboarding-candidate

### 6.1 共同断言（两个变体）

- 完成落点：保存确认全部通过后由前端触发完成调用；进入已完成候选主页。
- 持久化：简历（姓名/教育/意向）硬刷新后仍一致；手机号显示服务端掩码。
- 回访：退出并重新登录后**直接进入已完成候选主页**，不回身份选择或引导；
  资料减少或公司不存在不退回引导（Spec §5：已完成 → 正常主页）。
- 旧草稿收口：完成后本轮 onboarding 草稿与预填恢复信息被清理，不再触发自动业务重放；
  后端已完成事实优先于旧草稿的回访拦截。本 Suite 只验证「不再拦截回访」，
  不验证普通编辑。
- 只读补证（可选，同角色）：`GET /api/v1/me/onboarding` 的 `completed_at` 非空；
  API 只补充证据，不替代页面结果。
- 可观察失败（出现即相应节点 `FAIL`；取证后停止依赖该 run 的后续动作并进入 cleanup）：
  - 完成调用返回 404 → 部署/接口不匹配，不得当「未完成」或回退资料推导；
  - onboarding 读取失败被合成为「未完成」直接进引导（应显示错误与重试）；
  - 完成后重登录仍被拉回身份选择或引导；
  - `422 validation_failed` 无法定位到具体字段（如教育不完整、意向缺失、姓名/状态缺失）；
  - `403 role_suspended` 显示停用但被悄悄激活或闪入业务主页。
- 等待预算（启动前记录，执行限制而非产品 SLA）：页面加载/水合、每屏保存、
  完成请求回执；parsed 变体另加解析任务终态。到期记录时间、最后状态与
  「原因待定位」，不无限延长至通过。

### 6.2 variant manual（核心）

旅程按 Spec §3 的目标主序走（两身份同一顺序）：**求职意向（首屏，含期望薪资）
→ 基本信息 → 求职状态 → 最高学历 → 毕业院校 → 专业 → 就读时间段 → 简历资料
（工作/教育/技能/证书/作品集/个人优势）→ 补充偏好 → 披露说明 → 添加头像 → 已完成主页**。

| # | 节点 | 断言 |
| --- | --- | --- |
| 1 | 新浏览器会话 UI 登录 → 选「我要找工作」 | 进入候选引导（求职意向首屏），不停在身份页；后端 active 未完成可只读补证 |
| 2 | 首屏求职意向：办公方式 + 期望职位（目录真实点选）+ **期望薪资行**（开共用薪资区间层确认 25-35K 或明确面议） | 未确认薪资时「下一步」被拦并提示；确定后行内回显所确认的区间；取消/遮罩不改原值 |
| 3 | 手填基本资料（姓名 沈知行、社招、工作起始年 2022）→ 求职状态（在职/在校/离职三态之一） | 字段校验可定位到具体字段；前后导航不静默覆盖已填值；状态在基本信息之后收口，不被跳过 |
| 4 | 至少一条完整教育（江城理工大学 / 计算机科学与技术 / 本科 / 2018.09–2022.06；学校与专业走目录真实点选） | 保存成功；完成门槛满足 |
| 5 | 简历资料页：个人优势（三年前端开发经验…）随本页保存链写入 | 保存成功才前进；优势保存失败留页并保留输入 |
| 6 | 补充偏好页只有一题（硬性排除 + 屏蔽公司）→ 明确继续动作 | **首次求职意向在此创建且只创建一条**（前端开发工程师 / 杭州 / 25-35K / 全职；引用与薪资取首屏最新确认值）；意向创建失败留页可重试 |
| 7 | 披露说明 → 添加头像 → 保存确认全部通过 → 完成落点 | 进入已完成候选主页；完成时间唯一 |
| 8 | 刷新持久化 | 简历（含个人优势）与意向硬刷新后一致；手机号显示服务端掩码 |
| 9 | 退出 → 重新登录 | 直接进候选主页，不回引导；只读 `GET /api/v1/me/onboarding` 补证 `completed_at` 非空 |

- 首屏薪资与向导：本 Suite 无独立薪资页；旧 `/wizard?stage=salary` 深链只作兼容替换回首屏，
  不得据它判定流程未更新。
- 个人优势不在向导：若在补充偏好页看到优势题，说明部署或前端版本不是本轮目标流程，
  记录版本差异并停止该节点的 PASS 判定。
- 简历资料页的「企业屏蔽」开关属日常/隐私写入，本 Suite 不做屏蔽与披露写操作
  （该部分由 fixture 回归承担：`e2e/suites/隐私与实名.spec.ts` 的经历屏蔽 Case）。
- 公司资料维护入口不在本 Suite：注册流名片不渲染「公司主页资料」行，也不得在本旅程里
  打开公司档案分区（日常名片仍有该入口，由 招聘组织/账号与支持 方向的用例覆盖）。

## 7. Case stg-onboarding-recruiter

### 7.1 共同断言（两个变体）

- 公司 run 唯一：本轮组织名形如 `云杉智能装备-<run 短码>`（或等价的 run 唯一后缀），
  先目录搜索、无结果才创建；不与历史轮同名，不要求同企业名重建。
- 完成行为：名片保存成功后由前端触发 `POST …/recruiter/complete`；完成失败留在
  可重试状态，不重建已有 profile；完成调用不修改角色偏好。后端首次完成只要求
  有效非空 public_name 档案，不要求企业/认证/岗位，不得人为补企业。
- 注册流名片不渲染「公司主页资料」维护行（Spec §4.1）：所属公司选择/创建是名片自身
  内容，不属公司主页维护；日常名片的公司入口不在本 Suite 判定范围内。
- 首岗是旅程终点：进入首岗页面完成填写并发布；不新增首岗服务端状态；
  零岗位不得重开 onboarding。分类层打开一级即自动出现该一级的二级分组标题与三级可选
  岗位（二级是标题不是按钮），不需要再点二级下钻。
- 回访：退出并重新登录后直接进入招聘主页；岗位列表含刚发布岗位；名片刷新一致。
- 只读补证（可选，同角色）：`GET /api/v1/me/onboarding` 的 `completed_at` 非空；
  不替代页面结果。
- 可观察失败：完成调用 404；完成后重登录被拉回名片或引导；零岗位被当未完成；
  `422`（recruiter profile / public_name 缺失）无法定位字段。

| 4 | 建议稿核对 | 与第 3 节基线比较：岗位标题/描述/要求/地点关键词；未解析字段人工补充——公司按 run 唯一规则确认、薪资人工填写；无证据字段不判对 |
| 5 | UI 确认补充后发布 | 发布成功且在招；最终岗位与确认值一致 |
| 6 | 刷新持久化与回访 | 同 manual 节点 5–6 |

## 8. 业务、收尾与隔离结论

- **业务写入全部走 UI**（上传、授权确认、保存、发布、完成）；prepare / verify /
  cleanup 是 operator 例外；同角色只读 API 只补证，不能用 API 成功掩盖页面未显示。
- 每个选择项分别给出三个独立结论：**业务 / 收尾 / 隔离**，互不覆盖。
- journey verify（`--stage journey`）成功只说明后端观察到旅程终态，**不等于 UI
  PASS**；两者分别记录，页面节点未过时不得写业务 `PASS`。
- retained（允许保留的资源）：
  - 按后端批准能力保留唯一终态资源（当前预期如 recruiter/parsed 发布的终态 JD；
    后端合同保留其他终态时按实际记录）。
  - 每条 retained 记录**类别 / 原因 / 隔离依据**；隔离依据必须是后端证明的隔离
    （独立 run 账号、独立命名空间或唯一命名，不会与下一轮冲突）。
  - 不要求 `residuals=[]`、不要求全物理删除；**无法删除本身不构成 `BLOCKED`**——
    实际干扰下一轮或归属未知才须处理并记 `BLOCKED`。
  - pending / unknown 等清理状态按后端实际支持报告；不在前端私自删数据库/对象、
    reset 或接管外部 run。
- 隔离与两轮证据：
  - Suite / Case 级隔离结论需要**至少两个独立 run 的衔接证据**：第二个 run 开始前
    核对（1）未混入第一轮资料、引用或预填；（2）第一轮占用已释放；（3）第一轮旧凭据
    反证（第 9 节）。只记允许公开的安全 identity / resource ID 与结论。
  - 只运行单个三元组时，报告只写该单项的业务/收尾/隔离观察，并明确
    「两轮隔离未验证」，**不冒称两轮验证已覆盖**；不为此强迫再跑长复合旅程。
  - 不将第一轮旧资料（预填、公司名、草稿）误用为第二轮前置。

## 9. 受限凭据反证（部署依赖）

- 每项 finally cleanup 完成后，对该轮退休的登录材料做**一次有界正常认证 API 反证**，
  确认旧凭据不能再建立会话（沿用 `STG 基础试点` 第二轮口径）。
- 号码与 OTP 不出受限进程；公开只记结论与允许的安全 ID。
- 该反证是辅助核验，不冒称 UI 登录覆盖；可行性与时机取决于后端退休合同的实际实现，
  未实现时按实际记录，不虚构执行。

## 11. 能力缺口与依赖（诚实清单）

- onboarding 查询与完成接口在 STG 的可用性属部署依赖：后端未部署新接口时相关项
  `BLOCKED`/`NOT_RUN`；STG 上 404 表示部署/接口不匹配，不得当「未完成」处理。

  不得执行，更不得把执行结果写成已验证。
