# 真实后端行为验收（Agent Dogfood）

由 Agent 使用 `agent-browser` 在真实后端上执行的业务行为验收，替代已退役的
`test:agent-browser:backend-local` / `hosted-agent` 两个 npm 入口（同批退役的还有
`unit` / `shell`）。没有运行器替你点击和判分：环境启动、数据准备、页面操作、观察与
结论全部由执行 Agent 按本指南完成，证据落 `dogfood-output/<run-id>/`，结论写入
[报告模板](真实后端报告模板.md)。

本指南覆盖九类 local 行为：基础 B01–B05（候选/招聘加载与 CRUD、双会话隔离）、
Hosted H01–H04（happy 闭环与三个公开失败场景）；另提供独立的 `STG 基础试点`，
验证一次性双角色账号的登录、最小 CRUD、隔离与清理。新人注册流程走
[backend-local onboarding](backend-local-onboarding.md)，与上述范围互相独立。

## 1. 入口与范围选择

调用者提供以下必需输入，缺哪项就只询问缺项，可先做无依赖的只读准备：

| 输入 | 说明 |
| --- | --- |
| 目标 URL | 通常为 `http://localhost:5173`；先核对后端 Cookie/CORS 的 Origin 配置，不得擅自改成 `127.0.0.1` 或其他端口 |
| 后端工作区 | `AGXP_MONOREPO_DIR` 指向调用者提供的后端检出。local 范围要求 `dev-local.sh` 与 `browser-fixture.sh`；`STG 基础试点` 要求 `stg-env.sh`、tracked 默认配置及该 checkout 的两个环境 skill |
| 账号与登录材料来源 | local 范围使用专用测试账号的安全来源；STG 由 CLI 生成受限材料，调用者必须提供不经日志/聊天传递材料的安全输入能力 |

先判定范围是否为 `STG 基础试点`，再进入对应环境分支。范围可选：`STG 基础试点`、
`全部`、`基础行为`（B01–B05）、`Hosted`（H01–H04）、单个 Case ID。原 `全部`
仍只表示 B01–B05 + H01–H04，不含 STG。选中 STG 时跳过 local dev-local、
browser-fixture 与 B/H baseline 前置，B/H 表保持 `NOT_RUN`；反之不执行 STG。
只选一项时允许执行其必要前置，但不把前置或子集冒称其他组合 Case 已通过。

## 3. 准备与工具

所有范围都先核对当前安装版本的现场 CLI 输出；现场输出是真相，本指南不是版本真相源：

```bash
agent-browser --version
agent-browser doctor
agent-browser skills get core --full
agent-browser skills get dogfood
```

- `doctor` 需通过；Docker daemon 仅 local 范围必需。
- 两个角色各用一个独立具名浏览器会话，全程不混用（如
  `agent-browser session id --scope worktree --prefix "dogfood-backend-candidate"` 与
  `...-recruiter`）；记录会话名。
- 记录实际视口（参考 390×844）与 locale/时区（zh-CN / Asia/Shanghai），与截图一起留证。
- 前端依赖已安装（必要时 `npm ci`，不为本次迁移升级依赖）。
- `STG 基础试点` 还要从调用者后端 checkout 根完整读取
  `.claude/skills/agxp-recruitment-e2e-env/SKILL.md` 与
  `.claude/skills/agxp-recruitment-stg-env/SKILL.md`。前者决定前端工作位置与默认
  ephemeral 流程，后者决定 CLI、占用/proof、退出码与恢复；文档冲突时以后端
  checkout 的实际 skill 与 `stg-env.sh` 输出为准，不复制或改造 operator。

## 4. 环境

### 4.1 local 后端栈

先读目标后端仓库的规则与 `dev-local.sh` / `browser-fixture.sh` 的文档与帮助，再操作：

```bash
export AGXP_MONOREPO_DIR=/absolute/path/to/agxp-monorepo
"$AGXP_MONOREPO_DIR/apps/recruitment/scripts/dev-local.sh" health --acceptance
```

- 已健康 → 复用，记录栈归属，本轮结束不由你关闭。
- 不健康但 default 栈在跑 → 该栈属于他人，不 down、不切换，记 BLOCKED 联系其 owner。
- 都不健康 → `prepare --acceptance` 然后 `up --acceptance`，必要时再 `health --acceptance`；
  你自起的栈由你收尾 `down`（永不带 `--volumes`，不删持久卷）。

记录前后端 commit、acceptance profile 与栈归属（自起 / 复用）。

### 4.2 local 前端服务

```bash
VITE_DATA_SOURCE=backend VITE_BACKEND_ENV=local \
  npm run dev -- --host localhost --port 5173 --strictPort
```

- 固定 Origin `http://localhost:5173`，与后端 Cookie/CORS 配置一致；复用已跑服务前先核对
  它带的是这套 env，不确定就问 owner 或自起独占实例。5173 已被占用时与占用者协调，
  不自动换端口。
- 记录自起的 PID；只结束自己创建的资源，不按端口批量杀进程。

常见阻塞的处置线索（细节以后端文档为准）：下游 `down_status` 类错误先查 BFF 与平台
server/worker 及其数据库，不用前端延时掩盖瞬断；浏览器 locale/时区不符时换正确的
浏览器环境重跑，不要在错误环境里继续取证。

### 4.3 STG 前端与 operator

仅 `STG 基础试点` 使用本节，并跳过 4.1、4.2 与第 5 节的 local 数据准备。先在
调用者后端 checkout 根核对以下路径存在：

- `apps/recruitment/scripts/stg-env.sh`
- `apps/recruitment/testdata/stg-ephemeral/default.yaml`
- `.claude/skills/agxp-recruitment-e2e-env/SKILL.md`
- `.claude/skills/agxp-recruitment-stg-env/SKILL.md`

依赖缺失时按后端指引从同一 checkout 使用 `tools/dev-env.sh exec -- <同一 CLI 命令>`；
不在现场安装临时框架，不复制脚本到前端仓库。前端使用独占的 STG 代理构建：

```bash
VITE_DATA_SOURCE=backend VITE_BACKEND_ENV=stg \
  npm run dev -- --host localhost --port 5173 --strictPort
```

浏览器默认且固定访问 `http://localhost:5173`，不得换成 `127.0.0.1`。复用已有服务前
必须核对实际 `VITE_DATA_SOURCE=backend`、`VITE_BACKEND_ENV=stg`、代理目标及 owner；
无法核实时自起独占实例，5173 被占且不能安全协调时记 `BLOCKED`，不关他人服务、不按
端口批量杀进程。保存启动输出与浏览器实际 `/api/v1` 请求证据，确认代理上游为
`https://recruitment-stg.agxp.ai`；local 栈、route fixture 或仅见页面都不能算
STG PASS。发现
Cookie、Origin、Secure cookie 或代理缺口时保留证据，不放宽后端安全属性。

## 5. 数据与 receipt 生命周期

本节只服务 local B/H 范围；`STG 基础试点` 直接进入第 7 节，不能用本节的账号、
browser-fixture receipt 或 local acceptance 栈替代 STG operator。

### 5.1 基础行为基准

B01–B05 需要账号已收敛到基准态：候选侧有简历（姓名/摘要）、求职意向、披露偏好与至少
2 个空附件槽位；招聘侧有名片（姓名/职务/公司/介绍）、在招与归档两个基准岗位。

- 用 `browser-fixture.sh` 的现有 candidate/recruiter 基准收敛能力准备，或使用已按等价
  要求准备的专用账号。变更前记录初始值与对象归属。
- 规划基线观察到的基准字面量（现场以后端 fixture 工具当前输出为准，不把这里当合同）：
  候选真名「浏览器验收候选人」及其基准摘要、一条意向「前端开发工程师 · 上海市 ·
  30-45K」（列表显示为 `[上海市] 前端开发工程师`）、披露「当前公司：不披露」；
  招聘名片「浏览器验收招聘官 / 招聘负责人 / 浏览器验收科技」及基准企业介绍；
  岗位「…在招基线」（在招）与「…归档基线」（已归档）。
- 附件槽位收敛只保证「上限 − 已有 ≥ 2」，账号可能合法持有既有附件；不要用「附件库为空」
  当断言，用目标附件行的出现/消失。
- 当前部分后端版本没有 `baseline` scene（`converge --scene` 只有 happy/p4/p5/p6）。
  此时不得借用要求 Hosted 图的 happy 做普通 CRUD 基准；没有等价安全基准与恢复能力就把
  受影响基础 Case 记 BLOCKED，不把范围扩展为实现后端 fixture。

### 5.2 Hosted 场景准备

H01–H04 分别由真实后端 acceptance scene `happy` / `p4` / `p5` / `p6` 准备，通过现有
fixture 工具收敛；不得用网络 route mock、前端状态注入或改业务代码制造结果。缺某个
scene 或能力不匹配时记 BLOCKED 并写明版本差异，不臆造协议。

### 5.3 receipt v2 生命周期（一轮一个 run ID）

- 一轮场景使用一个唯一 `BROWSER_FIXTURE_RUN_ID`（如
  `$(date -u +%Y%m%dT%H%M%SZ)-<随机串>`）；该轮 `converge --scene <scene>`、
  `verify --ledger <receipt>`、`cleanup --ledger <receipt>` 三次调用共用它，下一轮换新 ID。
- receipt 是后端写下的文件（位于后端 `apps/recruitment/.local-dev/browser-fixtures/`
  下、以 run ID 命名）。把后端输出的准确 receipt 绝对路径用于该轮后续算子；
  自己记录的 journal/报告不是算子输入。
- `verify` 成功才开始消费该场景；一次只消费一个 fixture 生命周期，收尾完成前不并发改写
  同一组测试资源。
- `cleanup` 成功后 receipt 退休（后端输出 `receipt=retired`）：不再对它 verify、重新
  converge 或手工删除。需要复测就开新一轮（新 run ID、新 receipt）。
- converge 半路失败也要检查是否已产生 receipt/对象，并尝试现有清理入口；receipt 为
  symlink 时不是后端写的收条，不传给 cleanup，原样保留待人工处置。
- 遵守实际登录限流：重复获取 OTP 或重复调用 fixture 不能成为无界重试手段；相邻算子
  调用之间错峰，遇 429 退避。旧文档的 `FIXTURE_LOGIN_PACE` 只在核实运行中后端确实
  加载了降档 cooldown 配置时才适用，否则保持后端默认节奏。

## 6. 操作方式（浏览器工作循环）

1. 用 snapshot 和截图理解当前页面、实体与状态；跳转、重渲染、弹层出现后重新观察，
   旧 refs 失效就重新定位。
2. 依据当前 refs 或可访问语义选择用户会做的操作；不固定控件 refs、完整提示语、
   CSS module 名、像素坐标或整段点击序列。
3. 根据实际结果决定下一步：允许重新定位、滚动、关闭遮挡弹层或正常导航恢复。
   工具 ref 失效且重新观察后正常完成 → 记录工具恢复，不判产品失败；
   绕过的是产品缺陷 → 保留 FAIL。
4. 到关键节点验证结果、刷新/重开后的持久化和角色可见性，并立即记录证据。

- 被测业务写入全部走 UI（含规则确认、附件上传、委托、Case 推进）。环境准备与收尾
  清理是明确例外，只用现有工具允许的范围。不能在测到失败后补写业务结果让 Case 通过。
- 异步响应未知时先回读是否已生效，不盲目重试制造重复资源。
- 同角色只读 API 核验可补充页面证据：记录 method/path、必要脱敏字段与结论；
  不用管理员全量数据冒充用户权限，不用 API 成功掩盖页面未显示，不记录 Authorization。
- 准备阶段允许阅读工具与环境文档；页面 dogfood 按用户视角进行，不用源码里的状态
  推测代替浏览器观察。问题取证后的代码归因另行进行。
- 删除断言先确认对应列表已加载，再看目标不存在；硬刷新后先用基准数据等水合完成，
  再断言目标缺席。

## 7. STG 基础试点（仅选中该范围时）

本范围是两轮 `ephemeral-baseline` 浏览器试点，不是原 B02/B04 的缩写，也不执行
Hosted、local acceptance 或 browser fixture。所有 operator 命令都从调用者提供的
后端 checkout 根执行；前端目录只负责启动第 4.3 节服务、浏览器操作与证据记录。

### 7.1 CLI 顺序、材料与恢复

每轮创建全新且唯一的 `STG_RUN_ID`；推荐可辨识前缀、UTC 时间戳与随机后缀，且必须
符合后端 skill 声明的格式。以下顺序固定，`cleanup` 具有 finally 语义：

```bash
apps/recruitment/scripts/stg-env.sh validate --config apps/recruitment/testdata/stg-ephemeral/default.yaml
apps/recruitment/scripts/stg-env.sh prepare --run-id "$STG_RUN_ID" --scene ephemeral-baseline
apps/recruitment/scripts/stg-env.sh verify --run-id "$STG_RUN_ID"
# Agent 通过两套独立浏览器会话完成 UI 步骤后，无论成败都履行 cleanup：
apps/recruitment/scripts/stg-env.sh cleanup --run-id "$STG_RUN_ID"
```

- `validate` 是在线只读配置校验。`prepare` 未明确返回 `READY` 或 `verify` 失败时，
  不得打开浏览器消费数据；ephemeral 前置失败不得降级成固定 `baseline` 账号。
- `preflight` 与 `status` 只用于开始前核对或故障诊断：`status` 不带 run ID；
  `preflight` 是固定账号与 ephemeral 前置的并集，必须把无关的固定账号输入缺失与
  本轮真正需要的 fixture 管理面、对象存储、组织自动审批、部署/SSH 前置分开判读，
  既不能因前者误判本轮不可用，也不能忽略后者。
- 现场 CLI 的退出码为事实：`2` 是参数错误且零 mutation，`75` 是外部前置/占用/
  部署漂移导致 `BLOCKED`，`1` 是已开始操作、产品断言或 cleanup 的 `FAIL`。缺运行
  依赖时按后端 skill 从同一 checkout 用
  `tools/dev-env.sh exec -- apps/recruitment/scripts/stg-env.sh ...` 重试同一命令，
  不现场安装临时框架。
- prepare 部分失败只用同一 `STG_RUN_ID` 幂等重试或 cleanup；未完成 cleanup 不得换
  ID 绕过。遇 `occupied_by` 或其他 foreign 占用只记录并协调 owner，不抢锁、不清理
  他人 run。`CLEANUP_BLOCKED` 或 `CLEANED_WITH_RESIDUAL` 保留同 run 回执、残留和
  恢复责任，用同 ID 收敛，不能算完整通过。
- 操作者中断先用无参数 `status` 核对 run、ledger digest 与占用，再按后端 skill 决定
  继续或 `recover`。proof 丢失且任一 ephemeral fixture 登记已 pending/committed 时，
  `fixture_proof_stranded` 是 fail-closed 边界：找回原受限 proof 或升级人工处置，不
  force-unlock、不删远端状态、不新开 run 掩盖残留持锁。

登录材料位于后端 checkout 根的
`.agxp-recruitment-stg-env/sessions/<STG_RUN_ID>/login.json`，安全回执位于
`.agxp-recruitment-stg-env/receipts/`。号码只从前者读入受限进程；OTP 只经后端
skill 声明的受限通道取得。执行者必须先确认浏览器工具支持不会进入 shell 明文 argv、
终端输出、聊天、报告、截图/录像的安全输入；做不到就记 `BLOCKED`，不能用明文参数
绕行。登录期间停止录像，不记录完整认证状态、Cookie 或 proof。报告只引用 receipt、
login 文件路径和允许的安全实体 ID，不复制文件内容。

### 7.2 两轮节点

第一轮按以下顺序逐节点记录操作后与刷新证据：

1. `validate`、prepare/verify；记录 run、scene、receipt/login 路径、初始资源安全 ID、
   资源归属，以及回执中的实际 deployment tag/source revision。
2. 候选、招聘各用独立具名浏览器会话；在受限进程内把 login.json 的完整 `+999…`
   合成号码拆成区号与本地数字，通过 UI 编辑区号、输入号码和 OTP 登录。受限内核对
   登录输入与材料一致，公开证据只记核对通过。验证角色、基础资料及资源与 prepare
   结果一致。
3. 候选修改一个普通简历字段并刷新回读；新建、编辑、删除一条意向，每次写入后刷新
   回读，最终保留 prepare 创建的基准意向。
4. 招聘修改名片职务并刷新回读；新建岗位后依次编辑、归档、重开、删除，每次写入后
   刷新回读，最终保留 prepare 创建的基准岗位。公司资料编辑和首次 onboarding 不做。
5. 候选退出并确认本端退出生效；招聘会话刷新后仍有效，且资料与资源归属正确。
6. 关闭本轮两个浏览器会话并 cleanup；只在回执为 `CLEANED`、residuals 为空且占用
   已释放时把清理节点记 PASS。

第二轮必须使用全新的 `STG_RUN_ID`，重复 `validate`、prepare/verify 与双角色 UI
登录，然后执行一条意向的新建、刷新回读、删除和再刷新。受限进程内比较两轮号码与
身份，公开报告只记：两轮 candidate/recruiter identity 均不同、第二轮未继承首轮新建
资源，并记录允许的安全 identity/resource ID。首轮 cleanup 后，用现有正常认证 API
做一次有界反证，确认首轮登录材料不能再建立会话；该辅助核验不冒称 UI 登录覆盖，
号码和 OTP 仍不出受限进程。最后关闭第二轮会话并 cleanup，同样要求 `CLEANED`、
零残留、占用释放。

被测业务写入全部经 UI；prepare/verify/cleanup 只由 operator 完成。除首轮登录失效所需
的那一次有界正常认证 API 反证外，API 辅助核验只读，且只补充当前角色或实体证据。
页面自动请求若产生额外资源，记录 method/path、安全 ID 与归属；不能因没有手点对应
动作就假定零副作用，也不能屏蔽请求让试点通过。

### 7.3 排除范围与结论

不执行附件/PDF、披露设置、首次 onboarding、发现刷新/委托、规则创建、Hosted、
MatchCase、IM、实名、导出、反馈或公司资料编辑。若基础导航自动触发这些域的写入，
记录真实问题，停止依赖该 run 的后续动作，并进入同 run cleanup；不手写业务 SQL、
不改数据库、不补写结果、不部署或修后端。

每个节点使用 `PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`，两轮 cleanup 单独判定。只有
两轮全部必需节点通过且各自 `CLEANED`、零残留、占用释放，才可写 `STG 基础试点
PASS`。新登录代码回归通过但 STG 不可用时，必须分别写“代码回归通过”和“STG 基础
试点 BLOCKED”；原 B01–B05/H01–H04 继续为 `NOT_RUN`，不得把本子集填成 B02/B04
或原 `全部` 通过。

## 8. 行为场景卡

顺序是节点依赖，不是固定跨 Case 脚本。每条组合 Case 逐节点记录，不能只完成其中一个
动作就判整条通过。合成附件使用 `docs/dogfood/resources/简历-v1.pdf`、`简历-v2.pdf`
（字节不变的两份材料）；使用 fixture 时临时对象名称遵守其当前清理合同。

### B01 候选基准加载（原 candidate-load）

- 目标：候选登录后，简历、求职意向、披露偏好三屏都来自真实后端。
- 前置：候选账号已收敛基准（5.1）。
- 关键节点：基准姓名/摘要正确；意向的职位/城市/薪资及数量（配额行）正确；披露选中
  档位正确。
- 刷新/重开：每一屏硬刷新后仍然成立。
- 证据：每屏操作后与刷新后各一份截图/快照摘要。
- 反例：空态、Mock 数据或招聘方私有资料被误当加载成功。

### B02 候选 CRUD（原 candidate-crud）

- 目标：候选资料可改可还原，附件可上传/替换/删除。
- 前置：候选账号已收敛基准；临时对象用本次专属名称，避开基准值。
- 关键节点（各节点独立记录）：
  1. 改名 → 刷新确认 → 还原 → 刷新确认。
  2. 新建意向（职位/城市走目录真实点选）→ 刷新确认 → 调薪编辑 → 刷新确认 →
     删除 → 目标消失、数量回落、基准意向仍在。
  3. 披露改档 → 刷新确认 → 还原 → 刷新确认。
  4. 上传 `简历-v1.pdf` → 完成 UI 授权确认 → 回读目标附件行 → 刷新仍在 →
     用 `简历-v2.pdf` 替换 → 槽位/行仍正确 → 删除 → 刷新后目标行消失。
- 解析终态独立记录；不以本 Case 宣称 PDF 解析质量已验证。
- 反例：列表未加载就断言删除；只见保存提示但刷新丢失；响应未知重复创建。

### B03 招聘基准加载（原 recruiter-load）

- 目标：招聘登录后，名片、公司介绍、岗位管理都来自真实后端。
- 关键节点：姓名/职务/公司/介绍与基准一致；在招与归档岗位位于正确分组；刷新后恢复。
- 反例：混入候选私有摘要、岗位分组或资料错位。

### B04 招聘 CRUD（原 recruiter-crud）

- 目标：名片职务/公司介绍可改可还原；岗位发布→编辑→停止→重开→删除全链路。
- 关键节点：
  1. 职务修改 → 刷新逐字确认 → 还原 → 刷新确认（公司介绍同理）。
  2. 发布岗位（类别/城市走目录真实点选；当前 UI 要求的确认项逐项完成）→ 创建出目标
     岗位且在招 → 编辑描述/要求 → 刷新重开后进入编辑页读到服务端返回的改后值 →
     停止招聘后归档 → 重新开放后在招 → 删除（含产品二次确认）→ 目标消失且两个
     基准岗位保留。
- 反例：只看创建提示未验证描述持久化；跳过归档/删除；误改不可变字段（类别/类型/城市）。

### B05 双会话隔离（原 session-isolation）

- 目标：两个独立会话各自只看到授权数据；退出只影响本端。
- 关键节点：双账号分别登录并读各自资料；候选端退出生效；招聘端刷新后仍登录且资料正确。
- 反例：复用同一会话伪造角色隔离；候选退出把招聘端也踢下线。

### H01 Hosted happy 闭环（scene `happy`）

- 目标：完整成功链路，双方到达确认完成。
- 前置：`happy` scene 收敛 → verify 成功。
- 关键节点（逐节点留证）：
  1. 规则解释并确认：提交一条可执行的候选规则 → 解释就绪 → 确认生效 → 刷新后有效
     规则数量 +1 且内容对应。
  2. 上传 `简历-v1.pdf` → 完成 UI 授权 → 解析成功。
  3. 候选发起委托 → 产生 Case → 进入 Case 深链。
  4. 候选补充事实（回答补问）→ 推进到提交初筛。
  5. 招聘端读取同一 Case → 执行初筛且成功。
  6. 双方用页面公开允许的动作（接受/确认意向）推进协调与确认 → 到达双方确认完成
     （或后端合法推进到的已创建会话状态，需有对应实体与双方确认证据）。
  7. 深链复读：两端重开 Case 详情终态仍成立，过期推进动作消失。
- 迁移终点保留为双方确认完成及创建会话阶段；不宣称已验证 P7 私聊发送/接收。
- 反例：只有提示语没有实体；忽略初筛；匹配旧提示语就当确认完成。

### H02 委托失败零 Case（scene `p4`）

- 目标：已准备的委托失败场景中，委托被准确解释且不产生假进展。
- 关键节点：委托后 AI 不可用被准确解释；本次没有创建 Case、无「查看进展」类假进展
  入口；刷新后事实一致；必要时同角色只读 API 补零 Case 证据。
- 反例：只核验错误文案，漏掉误创建的 Case。

### H03 初筛 attention（scene `p5`）

- 目标：成功开案并推进后，招聘 Agent 进入需注意，双端看到一致且安全的原因。
- 关键节点：Case 存在但未继续；招聘端显示需注意；双端原因一致且不泄漏内部细节；
  不把 readiness 校验伪装成 Agent retry；刷新后不变成假成功；候选深链复读同一说明。
- 反例：只测一个角色；刷新后出现假成功。

### H04 规则解释失败与草稿恢复（scene `p6`）

- 目标：规则解释失败被诚实呈现，草稿可恢复。
- 关键节点：提交规则后解释失败说明明确；无确认成功入口、无新增有效规则（刷新后
  计数不变）；关闭失败卡后原草稿恢复；再次刷新仍无新增规则。
- 反例：失败后规则实际生效；草稿丢失。

### 七个视觉观察位置

在对应 Case 的节点上额外做视觉观察（不要求固定 PNG 差异率）：

1. 候选简历加载后（B01）；2. 候选意向加载后（B01）；3. 候选披露加载后（B01）；
4. 候选改名并上传附件后（B02）；5. 招聘名片加载后（B03）；6. 公司介绍加载后（B03）；
7. 新岗位发布后的列表（B04）。

逐处检查：文字可读、无遮挡、无溢出、状态与数据一致；记录实际视口并截图留证。

## 9. 证据与结论判定

| 状态 | 含义 |
| --- | --- |
| PASS | 该 Case 所有必需节点均有证据，结果与刷新/重开核验成立 |
| FAIL | 已观察到业务、数据、交互或隔离违反目标；关联问题证据 |
| BLOCKED | 环境、账号、故障场景或工具使关键目标无法验证；写具体边界与已完成节点 |
| NOT_RUN | 未选择或尚未执行；不能用缺少问题记录代替 PASS |

- 节点状态先于组合 Case：逐节点判，再汇总 Case。
- 同一 Case 已有 FAIL，后续被环境阻塞也不抹掉失败，额外记录未完成节点。
- 异步等待有界：优先用当前测试环境公开约定；没有约定就在启动前记录本轮各节点类型的
  观察预算（如单节点最长等待）。预算是执行限制，不是产品 SLA。到期记录时间、最后状态、
  诊断与原因；无法区分产品或环境时写「原因待定位」，不得无限延长至通过。
- 证据落 `dogfood-output/<run-id>/`（`report.md` + `screenshots/` + 按需 `videos/`），
  从执行开始持续写入，保证中断后可恢复。关键节点保留截图或快照摘要；每次业务写入有
  操作后与刷新两份证据。
- 不把 OTP、Cookie、Authorization 或完整认证状态写进报告；不在登录材料输入期间录像。
  含私密业务数据的原始证据只留在忽略目录；长期摘要按 `docs/runs/` 脱敏约定。

## 10. 清理与恢复

- 正常、失败和中断路径都有清理义务：按本轮 receipt 用现有工具回收其拥有的资源；
  自行准备的账号数据按事前记录的对象与原值通过 UI 还原。不能确认归属时不按名称猜测删除。
- 后端工具的 acceptance cleanup 属于收尾，不算产品业务成功证据。
- 中断或换会话恢复：先核对真实服务/回执状态（栈健康、receipt 是否存在/已退休），
  再决定继续或清理，不默认重开同一场景。
- 持续记录本轮服务归属、场景、receipt 准确路径与已创建对象。
- 只结束自己启动的服务与会话：不 `close --all`、不按端口批量 kill、不删卷。
- 清理失败保留准确 receipt 位置、对象归属和恢复步骤；依赖相同资源的后续测试停止，
  不把失败 receipt 当成下一轮准备成功。
- 没有进程级自动清理：Agent 中止即止，靠持续记录供下一次恢复。

## 11. 完整通过与局部范围

- 完整业务通过 = 九类 Case 全部 PASS + H01 清理后第二次独立运行成功 + 全部清理完成。
  完整范围下 H01 至少两次独立运行：前轮 cleanup 成功后，用新 run ID/receipt 再准备后轮。
- `STG 基础试点` 是独立范围：只有第 7 节两轮全部必需节点 PASS、两轮各自 `CLEANED`、
  residuals 为空且占用释放，才报试点 PASS；它不计入原 `全部`，也不能替代上述九类 Case。
- 部分范围必须写明所选范围；有 FAIL 不报全通过，有 BLOCKED/NOT_RUN 不报全覆盖。
- 清理结论单列（完成/未完成/不涉及）；清理未完成时，即使业务节点通过也不能宣称整轮通过。
