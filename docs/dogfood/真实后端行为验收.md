# 真实后端行为验收（Agent Dogfood）

由 Agent 使用 `agent-browser` 在真实后端上执行的业务行为验收，替代已退役的
`test:agent-browser:backend-local` / `hosted-agent` 两个 npm 入口（同批退役的还有
`unit` / `shell`）。没有运行器替你点击和判分：环境启动、数据准备、页面操作、观察与
结论全部由执行 Agent 按本指南完成，证据落 `dogfood-output/<run-id>/`，结论写入
[报告模板](真实后端报告模板.md)。

活动范围只覆盖真实 STG：`STG 基础试点`（第 6 节，两轮 `ephemeral-baseline`）、
`STG Onboarding` Suite（`stg-onboarding`，两角色空账号首次 onboarding 旅程，第 10 节，
见 [stg-onboarding](stg-onboarding.md)）与 `STG 匹配` Suite（`stg-matching`，双向匹配
S0–S3，第 11 节，见 [stg-matching](stg-matching.md)）。旧 local 行为（B01–B05 / H01–H04）与
local 环境/数据准备已整体移入历史归档
[archive/local-behavior.md](archive/local-behavior.md)；backend-local onboarding 六个
Case 见历史归档 [backend-local-onboarding](backend-local-onboarding.md)。两者退出活动
执行入口，原断言保留为归档材料，迁移对账（原风险 / 现有覆盖 / 未承接 / 后续归属）
见 `docs/testing/README.md`。

## 1. 入口与范围选择

调用者提供以下必需输入，缺哪项就只询问缺项，可先做无依赖的只读准备：

| 输入 | 说明 |
| --- | --- |
| 目标 URL | 通常为 `http://localhost:5173`；先核对后端 Cookie/CORS 的 Origin 配置，不得擅自改成 `127.0.0.1` 或其他端口 |
| 后端工作区 | `AGXP_MONOREPO_DIR` 指向调用者提供的后端检出。`STG 基础试点` 要求 `stg-env.sh`、tracked 默认配置及该 checkout 的两个环境 skill |
| 账号与登录材料来源 | STG 由 CLI 生成受限材料，调用者必须提供不经日志/聊天传递材料的安全输入能力 |

范围可选：`STG 基础试点`、`STG Onboarding`（Suite `stg-onboarding`，可细化到 Case
`stg-onboarding-candidate` / `stg-onboarding-recruiter` 与变体 `manual` / `parsed`
的单个三元组）、`STG 匹配`（Suite `stg-matching`，可细化到 Case
`stg-matching-recruiter` / `stg-matching-candidate` 单个 Case）。三个范围互不替代、
互不计入。只选一项时允许执行其必要前置，但不把前置或子集冒称其他组合 Case 已通过。

## 3. 准备与工具

所有范围都先核对当前安装版本的现场 CLI 输出；现场输出是真相，本指南不是版本真相源：

```bash
agent-browser --version
agent-browser doctor
agent-browser skills get core --full
agent-browser skills get dogfood
```

- `doctor` 需通过。
- 两个角色各用一个独立具名浏览器会话，全程不混用（如
  `agent-browser session id --scope worktree --prefix "dogfood-backend-candidate"` 与
  `...-recruiter`）；记录会话名。
- 记录实际视口（参考 390×844）与 locale/时区（zh-CN / Asia/Shanghai），与截图一起留证。
- 前端依赖已安装（必要时 `npm ci`，不为本次迁移升级依赖）。
- `STG 基础试点` 还要从调用者后端 checkout 根完整读取
  `.claude/skills/agxp-recruitment-e2e-env/SKILL.md` 与
  `.claude/skills/agxp-recruitment-stg-env/SKILL.md`。前者决定前端工作位置与默认
  ephemeral 流程，后者决定 CLI、占用/proof、退出码与恢复；文档冲突时以后端
  checkout 的实际 skill 与 `stg-env.sh` 输出为准，不复制或改造 operator。

## 4. STG 前端与 operator

本节服务第 1 节的两个 STG 范围。先在调用者后端 checkout 根核对以下路径存在：

- `apps/recruitment/scripts/stg-env.sh`
- `apps/recruitment/testdata/stg-ephemeral/default.yaml`
- `.claude/skills/agxp-recruitment-e2e-env/SKILL.md`
- `.claude/skills/agxp-recruitment-stg-env/SKILL.md`

依赖缺失时按后端指引从同一 checkout 使用 `tools/dev-env.sh exec -- <同一 CLI 命令>`；
不在现场安装临时框架，不复制脚本到前端仓库。前端使用独占的 STG 代理构建：

```bash
VITE_DATA_SOURCE=backend VITE_BACKEND_ENV=stg \
  npm run dev -- --host localhost --port 5173 --strictPort
```

浏览器默认且固定访问 `http://localhost:5173`，不得换成 `127.0.0.1`。复用已有服务前
必须核对实际 `VITE_DATA_SOURCE=backend`、`VITE_BACKEND_ENV=stg`、代理目标及 owner；
无法核实时自起独占实例，5173 被占且不能安全协调时记 `BLOCKED`，不关他人服务、不按
端口批量杀进程。保存启动输出与浏览器实际 `/api/v1` 请求证据，确认代理上游为
`https://recruitment-stg.agxp.ai`；local 栈、route fixture 或仅见页面都不能算
STG PASS。发现
Cookie、Origin、Secure cookie 或代理缺口时保留证据，不放宽后端安全属性。

## 5. 操作方式（浏览器工作循环）

1. 用 snapshot 和截图理解当前页面、实体与状态；跳转、重渲染、弹层出现后重新观察，
   旧 refs 失效就重新定位。
2. 依据当前 refs 或可访问语义选择用户会做的操作；不固定控件 refs、完整提示语、
   CSS module 名、像素坐标或整段点击序列。
3. 根据实际结果决定下一步：允许重新定位、滚动、关闭遮挡弹层或正常导航恢复。
   工具 ref 失效且重新观察后正常完成 → 记录工具恢复，不判产品失败；
   绕过的是产品缺陷 → 保留 FAIL。
4. 到关键节点验证结果、刷新/重开后的持久化和角色可见性，并立即记录证据。

- 被测业务写入全部走 UI（含规则确认、附件上传、委托、Case 推进）。环境准备与收尾
  清理是明确例外，只用现有工具允许的范围。不能在测到失败后补写业务结果让 Case 通过。
- 异步响应未知时先回读是否已生效，不盲目重试制造重复资源。
- 同角色只读 API 核验可补充页面证据：记录 method/path、必要脱敏字段与结论；
  不用管理员全量数据冒充用户权限，不用 API 成功掩盖页面未显示，不记录 Authorization。
- 准备阶段允许阅读工具与环境文档；页面 dogfood 按用户视角进行，不用源码里的状态
  推测代替浏览器观察。问题取证后的代码归因另行进行。
- 删除断言先确认对应列表已加载，再看目标不存在；硬刷新后先用基准数据等水合完成，
  再断言目标缺席。

## 6. STG 基础试点（仅选中该范围时）

本范围是两轮 `ephemeral-baseline` 浏览器试点，不是原 B02/B04 的缩写，也不执行
Hosted、local acceptance 或 browser fixture（这三类旧 local 内容已归档，见
[archive/local-behavior.md](archive/local-behavior.md)）。所有 operator 命令都从调用者提供的
后端 checkout 根执行；前端目录只负责启动第 4 节服务、浏览器操作与证据记录。

### 6.1 CLI 顺序、材料与恢复

每轮创建全新且唯一的 `STG_RUN_ID`；推荐可辨识前缀、UTC 时间戳与随机后缀，且必须
符合后端 skill 声明的格式。以下顺序固定，`cleanup` 具有 finally 语义：

```bash
apps/recruitment/scripts/stg-env.sh validate --config apps/recruitment/testdata/stg-ephemeral/default.yaml
apps/recruitment/scripts/stg-env.sh prepare --run-id "$STG_RUN_ID" --scene ephemeral-baseline
apps/recruitment/scripts/stg-env.sh verify --run-id "$STG_RUN_ID"
# Agent 通过两套独立浏览器会话完成 UI 步骤后，无论成败都履行 cleanup：
apps/recruitment/scripts/stg-env.sh cleanup --run-id "$STG_RUN_ID"
```

- `validate` 是在线只读配置校验。`prepare` 未明确返回 `READY` 或 `verify` 失败时，
  不得打开浏览器消费数据；ephemeral 前置失败不得降级成固定 `baseline` 账号。
- `preflight` 与 `status` 只用于开始前核对或故障诊断：`status` 不带 run ID；
  `preflight` 是固定账号与 ephemeral 前置的并集，必须把无关的固定账号输入缺失与
  本轮真正需要的 fixture 管理面、对象存储、组织自动审批、部署/SSH 前置分开判读，
  既不能因前者误判本轮不可用，也不能忽略后者。
- 现场 CLI 的退出码为事实：`2` 是参数错误且零 mutation，`75` 是外部前置/占用/
  部署漂移导致 `BLOCKED`，`1` 是已开始操作、产品断言或 cleanup 的 `FAIL`。缺运行
  依赖时按后端 skill 从同一 checkout 用
  `tools/dev-env.sh exec -- apps/recruitment/scripts/stg-env.sh ...` 重试同一命令，
  不现场安装临时框架。
- prepare 部分失败只用同一 `STG_RUN_ID` 幂等重试或 cleanup；未完成 cleanup 不得换
  ID 绕过。遇 `occupied_by` 或其他 foreign 占用只记录并协调 owner，不抢锁、不清理
  他人 run。`CLEANUP_BLOCKED` 或 `CLEANED_WITH_RESIDUAL` 保留同 run 回执、残留和
  恢复责任，用同 ID 收敛，不能算完整通过。
- 操作者中断先用无参数 `status` 核对 run、ledger digest 与占用，再按后端 skill 决定
  继续或 `recover`。proof 丢失且任一 ephemeral fixture 登记已 pending/committed 时，
  `fixture_proof_stranded` 是 fail-closed 边界：找回原受限 proof 或升级人工处置，不
  force-unlock、不删远端状态、不新开 run 掩盖残留持锁。

登录材料位于后端 checkout 根的
`.agxp-recruitment-stg-env/sessions/<STG_RUN_ID>/login.json`，安全回执位于
`.agxp-recruitment-stg-env/receipts/`。号码只从前者读入受限进程；OTP 只经后端
skill 声明的受限通道取得。执行者必须先确认浏览器工具支持不会进入 shell 明文 argv、
终端输出、聊天、报告、截图/录像的安全输入；做不到就记 `BLOCKED`，不能用明文参数
绕行。登录期间停止录像，不记录完整认证状态、Cookie 或 proof。报告只引用 receipt、
login 文件路径和允许的安全实体 ID，不复制文件内容。

### 6.2 两轮节点

第一轮按以下顺序逐节点记录操作后与刷新证据：

1. `validate`、prepare/verify；记录 run、scene、receipt/login 路径、初始资源安全 ID、
   资源归属，以及回执中的实际 deployment tag/source revision。
2. 候选、招聘各用独立具名浏览器会话；在受限进程内把 login.json 的完整 `+999…`
   合成号码拆成区号与本地数字，通过 UI 编辑区号、输入号码和 OTP 登录。受限内核对
   登录输入与材料一致，公开证据只记核对通过。验证角色、基础资料及资源与 prepare
   结果一致。
3. 候选修改一个普通简历字段并刷新回读；新建、编辑、删除一条意向，每次写入后刷新
   回读，最终保留 prepare 创建的基准意向。
4. 招聘修改名片职务并刷新回读；新建岗位后依次编辑、归档、重开、删除，每次写入后
   刷新回读，最终保留 prepare 创建的基准岗位。公司资料编辑和首次 onboarding 不做。
5. 候选退出并确认本端退出生效；招聘会话刷新后仍有效，且资料与资源归属正确。
6. 关闭本轮两个浏览器会话并 cleanup；只在回执为 `CLEANED`、residuals 为空且占用
   已释放时把清理节点记 PASS。

第二轮必须使用全新的 `STG_RUN_ID`，重复 `validate`、prepare/verify 与双角色 UI
登录，然后执行一条意向的新建、刷新回读、删除和再刷新。受限进程内比较两轮号码与
身份，公开报告只记：两轮 candidate/recruiter identity 均不同、第二轮未继承首轮新建
资源，并记录允许的安全 identity/resource ID。首轮 cleanup 后，用现有正常认证 API
做一次有界反证，确认首轮登录材料不能再建立会话；该辅助核验不冒称 UI 登录覆盖，
号码和 OTP 仍不出受限进程。最后关闭第二轮会话并 cleanup，同样要求 `CLEANED`、
零残留、占用释放。

被测业务写入全部经 UI；prepare/verify/cleanup 只由 operator 完成。除首轮登录失效所需
的那一次有界正常认证 API 反证外，API 辅助核验只读，且只补充当前角色或实体证据。
页面自动请求若产生额外资源，记录 method/path、安全 ID 与归属；不能因没有手点对应
动作就假定零副作用，也不能屏蔽请求让试点通过。

### 6.3 排除范围与结论

不执行附件/PDF、披露设置、首次 onboarding（现由 `STG Onboarding` Suite 单独覆盖）、
发现刷新/委托、规则创建、Hosted、
MatchCase（委托与 S0–S3 主路径现由 `STG 匹配` Suite 单独覆盖）、IM、实名、导出、
反馈或公司资料编辑。若基础导航自动触发这些域的写入，
记录真实问题，停止依赖该 run 的后续动作，并进入同 run cleanup；不手写业务 SQL、
不改数据库、不补写结果、不部署或修后端。

每个节点使用 `PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`，两轮 cleanup 单独判定。只有
两轮全部必需节点通过且各自 `CLEANED`、零残留、占用释放，才可写 `STG 基础试点
PASS`。新登录代码回归通过但 STG 不可用时，必须分别写“代码回归通过”和“STG 基础
试点 BLOCKED”；原 B01–B05/H01–H04 继续为 `NOT_RUN`（已归档、未承接），不得把本子
集填成 B02/B04 或原 `全部` 通过。

本节的 `CLEANED`、零残留、占用释放等收尾要求只约束 `STG 基础试点` 自身的
ephemeral-baseline 范围（历史范围不变）；`STG Onboarding` Suite 的收尾与资源保留按
[stg-onboarding](stg-onboarding.md) 第 8 节的 retained/隔离原则单独判定，
不适用零残留或同名复建要求。

## 7. 证据与结论判定

| 状态 | 含义 |
| --- | --- |
| PASS | 该 Case 所有必需节点均有证据，结果与刷新/重开核验成立 |
| FAIL | 已观察到业务、数据、交互或隔离违反目标；关联问题证据 |
| BLOCKED | 环境、账号、故障场景或工具使关键目标无法验证；写具体边界与已完成节点 |
| NOT_RUN | 未选择或尚未执行；不能用缺少问题记录代替 PASS |

- 节点状态先于组合 Case：逐节点判，再汇总 Case。
- 同一 Case 已有 FAIL，后续被环境阻塞也不抹掉失败，额外记录未完成节点。
- 异步等待有界：优先用当前测试环境公开约定；没有约定就在启动前记录本轮各节点类型的
  观察预算（如单节点最长等待）。预算是执行限制，不是产品 SLA。到期记录时间、最后状态、
  诊断与原因；无法区分产品或环境时写「原因待定位」，不得无限延长至通过。
- 证据落 `dogfood-output/<run-id>/`（`report.md` + `screenshots/` + 按需 `videos/`），
  从执行开始持续写入，保证中断后可恢复。关键节点保留截图或快照摘要；每次业务写入有
  操作后与刷新两份证据。
- 不把 OTP、Cookie、Authorization 或完整认证状态写进报告；不在登录材料输入期间录像。
  含私密业务数据的原始证据只留在忽略目录；长期摘要按 `docs/runs/` 脱敏约定。

## 8. 清理与恢复

- 正常、失败和中断路径都有清理义务：按本轮 receipt 用现有工具回收其拥有的资源；
  自行准备的账号数据按事前记录的对象与原值通过 UI 还原。不能确认归属时不按名称猜测删除。
- 后端工具的 acceptance cleanup 属于收尾，不算产品业务成功证据。
- 中断或换会话恢复：先核对真实服务/回执状态（栈健康、receipt 是否存在/已退休），
  再决定继续或清理，不默认重开同一场景。
- 持续记录本轮服务归属、场景、receipt 准确路径与已创建对象。
- 只结束自己启动的服务与会话：不 `close --all`、不按端口批量 kill、不删卷。
- 清理失败保留准确 receipt 位置、对象归属和恢复步骤；依赖相同资源的后续测试停止，
  不把失败 receipt 当成下一轮准备成功。
- 没有进程级自动清理：Agent 中止即止，靠持续记录供下一次恢复。

## 9. 完整通过与局部范围

- `STG 基础试点` 是独立范围：只有第 6 节两轮全部必需节点 PASS、两轮各自 `CLEANED`、
  residuals 为空且占用释放，才报试点 PASS；它不计入 `STG Onboarding`，反之亦然。
- `STG Onboarding`（`stg-onboarding`）是独立范围：四个 Case×variant 选择项按
  [stg-onboarding](stg-onboarding.md) 分别给出业务/收尾/隔离结论；它不计入
  `STG 基础试点`，反之亦然。两个手填变体通过不代表四项 Suite 全通过。
- `STG 匹配`（`stg-matching`）是独立范围：两个 Case 按 [stg-matching](stg-matching.md)
  分别给出业务/准入/cleanup/隔离结论；只跑一个 Case 不代表双向验收完成，S1 及以前
  的阶段性观测不代表 A 终点（S3 后完成与会话就绪）已通过。它不计入 `STG 基础试点`
  或 `STG Onboarding`，反之亦然。
- 部分范围必须写明所选范围；有 FAIL 不报全通过，有 BLOCKED/NOT_RUN 不报全覆盖。
- 清理结论单列（完成/未完成/不涉及）；清理未完成时，即使业务节点通过也不能宣称整轮通过。
