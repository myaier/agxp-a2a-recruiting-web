# AGXP 招聘 Web：代码与产品评审（2026-08-21）

## 结论

这是一个完成度较高、双端主链路可演示的高保真前端 mockup。当前阶段尚未接入后端，
页面直接使用模拟数据属于合理实现，不作为当前缺陷。现阶段应优先修复可复现 Bug、交互一致性
与产品口径问题；数据层迁移、认证和生产能力放在 mockup 定稿之后处理。

## 已验证

- `npm run typecheck`：通过
- `npm run lint`：通过（修复中文组件命名导致的规则误报后）
- `npm run build`：通过
- 本地开发服务：`http://127.0.0.1:5173/` 返回 HTTP 200
- 浏览器走查：登录、求职端首页、求职端谈判详情、企业端首页均可打开，无控制台错误

## 已修复

1. 企业推荐流 `useMemo` 缺少 `状态.推荐列表` 依赖；推荐池变化后现在会重新计算。
2. Oxlint 无法把中文函数名识别为 React 组件/自定义 Hook，原配置产生整库误报。关闭两条命名启发式规则，保留并提升 `react-hooks/exhaustive-deps` 为错误。
3. 所有屏幕原本同步进入登录主包，生产 JS 为 807.84 KB（gzip 238.47 KB）。改为路由级按需加载后，登录首屏预加载 JS 合计约 397 KB（gzip 131 KB），原始体积下降约 51%、gzip 体积下降约 45%，构建不再出现 500 KB 大包警告。

## 主要发现

### 后续接后端前：统一数据访问边界

当前是纯前端 mockup，31 个屏幕/组件直接引用 `模拟数据.ts` 或 `企业端模拟数据.ts`，便于快速调整演示内容，现阶段不构成 Bug。

需要注意的是，`src/数据/接口层.ts` 所写的“换一行即可接后端”与现状不一致。未来正式接后端时，仍需要逐步迁移这些直接依赖，企业端也要补对应的数据源契约。

建议：等 mockup 和交互逻辑稳定后，再按用例建立求职端与企业端 Repository/API 契约，把全局状态初始化、列表、详情、消息和写操作统一迁移到该层，然后接 HTTP；不必在当前 Bug 修复阶段提前重构。

### P0：薪资隐私口径冲突

`src/数据/类型.ts` 明确要求双方薪资数字不互通，只交换区间是否相交；企业候选卡却主动读取匿名简历中的期望薪资带并在意向确认前展示。README 也把“数值互不披露”列为产品定义。

需要产品拍板：

- 若坚持隐私承诺，候选卡只显示“薪资带有交集/无交集”，删除具体数字；
- 若允许候选自愿公开区间，需要同步更新 README、类型注释、披露策略、授权记录和撤回规则，避免宣传与行为相反。

### P1：登录与权限仍是演示逻辑

短信验证码不校验、微信登录直接进入、没有登录态写入或路由守卫，`/#/app` 与 `/#/hr` 可直接访问。原生桥虽定义了安全存储与握手，但目前没有业务调用。

建议：接后端前先定义认证状态机（未登录/注册中/已登录/令牌失效）、路由守卫、刷新令牌与退出清理。

### P1：没有自动化测试

仓库没有测试脚本或 `*.test.*` / `*.spec.*` 文件；现有 `docs/runs` 是人工截图回归记录。全局 reducer 承载大量跨屏状态变更，一旦继续迭代，人工走查很难覆盖状态组合。

建议优先补三层：reducer 单元测试、关键组件交互测试、Playwright 的求职/企业核心 smoke。

### P1：可访问性债务较集中

临时启用 Oxlint `jsx-a11y` 审计得到 127 条问题，主要是可点击 `div` 没有键盘操作、弹层遮罩/对话框语义不足、开关没有可访问名称，以及滚轮列表的非原生交互。

建议先治理复用组件（弹层、开关、滑动行、滚轮），一次修复覆盖多屏；再处理各业务页的局部遮罩。

### P1：reducer 含持久化副作用

`应用状态.tsx` 的 reducer 内直接写 `localStorage`。React reducer 应保持纯函数；开发 StrictMode 或未来并发渲染可能重复调用，后续如果持久化从本地写升级为网络写，风险会放大。

建议 reducer 只返回状态，把持久化移动到 Provider 的 effect 或独立持久化中间层。

### P2：企业端人为等待 2 秒

企业人才首页对同步模拟数据强制展示 2 秒骨架，明显慢于求职端 450ms。演示时能体现加载态，但会让核心工作台感觉迟钝。

建议原型统一到 300–500ms；接真实接口后按请求状态显示，避免人为延迟叠加真实网络延迟。

## 产品评审摘要

做得好的部分：

- “匿名初筛 → 递交简历 → 需要协调 → 意向确认”四阶段在卡片、详情时间线和文案中一致；
- 待用户决策的卡片置顶，卡面不直接放决策按钮，降低误触；
- 求职端和企业端信息架构同构，学习成本低；
- “代理不谈薪，确认意向后转真人”的边界在详情页解释清楚。

需要优先验证的产品问题：

- 用户是否相信“薪资只做布尔匹配”，以及看到具体薪资带时是否产生被泄露感；
- 四阶段标签是否足以让用户理解代理到底做了什么，还是需要更强的证据/审计入口；
- 需要用户拍板的事项是否能在 10 秒内理解“差异、建议、后果”；
- 企业端是否真的需要先按岗位切换，再看人才池；多岗位 HR 可能更需要一个跨岗位待办视图。

## 推荐实施顺序

1. 修复能够稳定复现的交互与状态 Bug。
2. 冻结薪资披露规则与双盲边界，完成 mockup 产品定稿。
3. 为 reducer 与两端核心链路补必要的自动化回归。
4. 以复用组件为起点清理影响实际操作的可访问性问题。
5. mockup 稳定后建立 API/Repository 层，并移除屏幕对 mock 的直接依赖。
6. 接入认证、路由守卫、Capacitor 真机能力、推送、Deep Link 与安全存储。
