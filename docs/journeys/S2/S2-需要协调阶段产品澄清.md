# S2“需要协调”阶段产品澄清

版本：v0.1 · 2026-09-10。状态：**阶段归属已由用户确认；完整旅程及合同尚未设计/批准**。

关联：第一阶段C07/E08的S2部分；[J-PILOT-01](../J-PILOT-01/J-PILOT-01-产品旅程与状态规则.md)仅验收到S0及S1交接，本文件记录跨阶段澄清，不扩张本轮试点。

## 已确认的产品方向

用户明确：“人工补充事实应该是在需要协调那个阶段（S2阶段），所以可以把它补到那个阶段的文档里。”

- 人工补充事实归S2“需要协调”阶段；S0由双方Agent按已有授权资料及有限问答处理，不额外请求用户输入。
- S0信息不足首版自动结束，保留信息不足原因、不递交简历；不把该Case直接送入S2来补事实。S2仍承接S1之后的剩余差异协调。
- 本轮只确认阶段归属，不代表S2补充入口、权限、触发条件或提交后推进规则已全部确定，也不代表现有接口已经支持。

## 当前依据与缺口

前端既有批准设计`docs/superpowers/specs/2026-08-25-recruitment-p0-contract-seams-design.md:48`把S2定义为双方Agent处理完整JD与简历筛选后的剩余差异。`docs/superpowers/specs/2026-08-29-recruitment-p5-frontend-wiring-design.md:37`记录当前S2为针对active issue的accept/reject决定。

后端基线：`1ae0b7a46f060e27c7f6db38e0469d15c626e2c5`，`apps/recruitment/internal/matchcase/lifecycle.go:533–549`按当前议题required_roles及是否已决定给出`decide_coordination`。这证明已有协调决定，不证明有人工补充事实的提交与Agent重新处理闭环。既有S0 `respond_fact`也不能直接宣称可用于S2。

因此标记为：**S2协调决定已存在；人工补充事实为已确认产品方向，具体合同与支持程度待专项核对**。保留旧批准文档的历史事实，由本澄清承接新的阶段归属要求。

## 留给后续S2旅程Agent的问题与交接

只在开展S2旅程时逐项讨论：

- 哪种信息缺口触发人工补充，由哪一方或双方回答；与接受/拒绝协调方案的关系。
- 输入围绕当前议题还是允许提出新议题，谁可看到原文；不能默认将私有诉求向对方公开。
- 提交后由哪一方Agent处理，怎样更新方案，原决定是否失效，以及异步失败、重试和刷新恢复。
- 没有补充、仍无法协调或用户退出时如何收敛。

验收应证明补充进入正确议题、仅向获授权角色展示、由权威状态反映处理结果，且没有把“提交成功”误当作协调达成。具体稳定旅程/步骤ID、OpenAPI及Arazzo映射在S2完整设计时确定，不在本轮预建接口或状态机制。

本文件仅新增产品文档，未实施、未运行S2测试。
