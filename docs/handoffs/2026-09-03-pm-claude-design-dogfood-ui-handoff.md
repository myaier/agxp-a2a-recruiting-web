## 1. 范围与原则

产品是双端招聘应用，包含候选人与招聘方视角。现有功能大多已经可导航，但以下界面把“固定机制”“尚无数据”“身份资料”和“可操作设置”表达得不够清楚。

设计目标：让用户一眼分辨三种状态：

1. 这是用户可修改的设置；
2. 这是平台固定的机制/规则；
3. 这是没有数据或服务暂不可用的状态。

本 Handoff 不要求改变后端合同、不设计新的 AI 能力、不增加 JD 上传入口、不变更双盲/隐私产品规则。请在现有移动端视觉系统内给出组件、文案、状态和验收稿；Coding Agent 再按设计落地。

## 2. 设计任务 A：候选人屏蔽组织的搜索无结果

### 现状

候选人输入公司名称后，系统只允许从组织目录的搜索结果中选择一项再屏蔽。没有稳定组织 ID 时，“屏蔽”按钮保持不可用。这一约束是正确的：不能把用户自由输入的公司名伪装成组织 ID。

但无匹配时页面没有任何解释，用户会误以为按钮或搜索坏了。

### 需要设计

- 搜索中、无结果、已选择组织、搜索出错四种状态的清晰区分；
- 无结果时说明“暂未找到可屏蔽的组织，请换关键词或从结果中选择”，但不要泄露组织是否存在、是否被停用等内部原因；
- 在无结果时解释为什么不能直接用输入文字提交；
- 保持用户对“屏蔽后该组织无法看到我”的理解；
- 给出键盘焦点、读屏文案和窄屏换行要求。

### 验收

用户输入一个未命中名称时，能理解下一步且不会把按钮不可用误判为故障；输入命中并选择结果后，能明确知道已选择的是哪一家组织。

## 3. 设计任务 B：招聘方“我的”身份卡的信息层级

### 现状

招聘方完成招聘名片后，姓名、职位、公司均已保存；“我的”页顶部卡目前主要显示公司名，以及“个人未认证 / 任职无”等身份状态。用户必须点击进入招聘名片才能看到自己的姓名和职位。

这不是数据丢失，而是顶部卡的信息层级选择不够贴合“我是谁”的预期。

### 需要设计

- 明确顶部卡主信息、次信息与认证/任职状态分别应该是什么；
- 在不把“手机号登录”误称为实名、也不把“公司名”误称为个人身份的前提下，提出招聘负责人姓名、职位、公司之间的紧凑移动端排版；
- 给出姓名/职位/公司缺失、未认证、无任职关系、企业已验证等组合的状态表；
- 保留点击进入招聘名片编辑的可发现性；
- 不新增复杂认证流程或后台术语。

### 验收

已填写招聘名片的用户无需进入二级页，就能辨认自己对外显示的姓名、职位与所属公司；认证和任职状态也不会被误读为同一件事。

## 4. 设计任务 C：企业披露策略是固定机制，不是可编辑设置

### 现状

页面把各披露档位渲染成分段按钮，但全部禁用；底部却写“改动即时生效”。代码定义这些是平台固定机制，而非企业可调参数。

### 需要设计

- 将页面从“不可用的设置表单”重构为易理解的机制说明；
- 明确哪些信息从第一轮可见，哪些薪资细节由机制限制，以及原因；
- 若保留档位对照，必须采用非交互组件，不让用户以为可以点击修改；
- 重新定义标题、副标题、底部说明和“机制锁定”标记；
- 给出候选侧披露偏好页面与企业侧固定披露机制在视觉和文案上的区分，避免用户误以为两端权限相同。

### 验收

用户不再看到“禁用按钮 + 改动即时生效”的自相矛盾组合，并理解这是平台机制而非保存失败的设置。

## 5. 设计任务 D：候选人设置中的候选实名状态

> **复核标记（2026-09-05 05:37 +08:00）：进行中。** 原“不能可靠显示已实名”的无合同判断已被后端 `aa150811d` 取代；前端 `68587f9f`–`7ecbd722` 已把真实查询、提交、取消、拒绝后重提纳入设计/计划，当前实现到 `d4f6e152` 的 data source。完整页面与主线合入仍见 `2026-09-03-frontend-verification-matchcase-summary-handoff.md`。

### 现状

候选人使用短信验证码登录后，页面仍显示“实名认证已认证”。当前产品仅能确认登录手机号验证；简历姓名不等于实名，且没有候选人实名流程。

### 需要设计

- 在尚未提供候选实名能力时，决定是否隐藏该入口、展示“暂未提供”，或采用其他不误导的静态呈现；
- 不把“手机号已验证”包装成实名；
- 区分“账号安全/登录凭据”和“个人身份认证”；
- 若保留行项，明确它是否可点击，以及点击后看到什么；不允许假成功 toast。

### 验收

用户不会将手机号验证码登录误解为平台已经核验真实身份，也不会遇到一个看似可操作但实际没有流程的入口。

## 6. 设计任务 E：可读性与对比度审计

### 现状

候选人简历页与招聘方“我的”页存在多处文本对比度不足：包括页脚小字和部分导航/辅助标签。自动化 axe 检查已报告违规。

### 需要设计

- 为正文、辅助文本、禁用机制说明、标签、页脚、浅色背景上的文字建立语义色 token；
- 满足 WCAG AA：普通文本至少 4.5:1；大文本至少 3:1；不要依赖颜色作为唯一状态传达；
- 给出 hover/pressed/focus/disabled 的一致状态，尤其是“机制锁定”与真正不可用操作的区分；
- 不以降低字号、降低透明度或增加阴影替代对比度修复。

### 验收

相关页面通过 axe 的色彩对比检查，且视觉层级仍能区分主信息、辅助信息和固定机制。
