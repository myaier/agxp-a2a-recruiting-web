### C3. 接触记录必须区分加载、失败与权威空数据

### C3b. 接触记录不得静默截断第 51 条及以后的权威事件

**现象：** 接触记录数据源首屏固定请求 50 条，并且已经解析/保存 `next_cursor`、实现了 `操作.追加接触记录()`；但页面从未读取快照的 `nextCursor`，也没有任何“加载更多”入口。因此当服务端返回第二页游标时，用户只能看到前 50 条，之后的真实接触记录被静默遗漏。

**根因：** `src/屏幕/接触记录.tsx` 只在挂载时调用 `加载接触记录()`，渲染只遍历当前 `items`，没有消费 `后端状态.接触记录.nextCursor` 或调用既有的 `追加接触记录()`。这不是后端缺少分页：`src/数据/招聘数据源/接触记录.ts` 已将 `next_cursor` 纳入严格 DTO，`src/状态/后端/接触记录操作.ts` 已实现 owner/session fence 下的追加读取与去重。

**修改：**

1. 仅在 Backend、当前 candidate owner 的成功快照、`nextCursor !== null` 时，在列表末尾显示一个“加载更多”按钮；`刷新中` 时禁用并显示读取中。不能显示“共 N 条”或“已全部加载”等没有总数合同支撑的数字/承诺。

### C3c. 接触记录的追加失败必须能重试同一个游标

**现象：** 在已成功加载第一页后，请求下一页若遇到网络/503/decoder 失败，前端保留第一页和 `nextCursor`，但再次调用 `追加接触记录()` 会立即报“分页游标已被消费，请刷新后重试”；普通 `加载接触记录()` 又因当前成功快照命中缓存而不发请求。用户不能重试下一页，只能丢掉已读窗口后强制重新加载。

**根因：** `src/状态/后端/接触记录操作.ts` 在发起追加请求前就把 cursor 加入 `接触记录已消费游标`，但 `catch` 路径没有将这个尚未成功提交的 cursor 移出集合。该集合本应用于阻止重复**成功**消费或不前进游标，却把临时失败变成终局消费。

**修改：** 在同一 front-end operation 内区分“请求在飞”“成功消费”“失败可重试”：追加失败、可恢复的 decoder error 和被用户重试前都必须释放本次 cursor；只在成功提交下一页（或已确认的契约循环/重复错误）后将 cursor 保留为已消费。保持现有 subject/session/generation fence、单飞和 401 清理规则；不要借由无条件 `force` 重载来伪造“重试”。

**测试：** 成功首屏 → 下一页 503 → 重试同一 cursor 会重新发请求且可成功追加；decoder 失败同理；成功追加后重复点击不会重消费；不前进/已见 cursor 仍 fail closed；切 subject 或登出时迟到失败不会污染新会话。

### C4. 账户时间按本地时区格式化

**现象：** 多个页面把 RFC3339 文本 `slice` 成 UTC 字面片段，在非 UTC 时区显示错误日期或时分：账号安全、Backend 真人会话收件箱与会话正文、MatchCase 时间线、职位发布时间、组织屏蔽创建日期、Agent 规则更新时间和公开企业认证日期均受影响。工作经历编辑页还以 `new Date().toISOString().slice(0, 7)` 计算“本月”作为可选工作起止月上界；在本地已跨月、UTC 尚未跨月的时段，该上界会错误停在上月，阻止用户选择本月。

**根因：** `src/屏幕/账号安全.tsx` 的 `取展示时间()` 直接拼 `iso.slice(0, 10)` / `slice(11, 16)`；`src/屏幕/P7/Backend会话列表.tsx` 与 `src/屏幕/P7/Backend真人会话.tsx` 分别截取活动日期/时分，`src/屏幕/P5/MatchCase详情.tsx` 截取时间线时分；此外 `src/数据/后端映射.ts`、`src/数据/发现推荐映射.ts`、`src/数据/隐私映射.ts`、`src/数据/Agent规则映射.ts` 将发布时间/创建时间/更新时间提前 slice 成页面文本，`src/屏幕/企业详情.tsx` 直接截取认证日期。RFC3339 的这些字面段是 UTC，不是用户本地日历/时间。`src/屏幕/工作经历.tsx` 的 `本月()` 也错误地把 UTC 的 ISO 字面月用作本地用户填写工作日期的业务上界。

**修改：** 建立一个可测试的本地绝对时间 formatter（可复用 `接触记录.tsx` 的 `Intl.DateTimeFormat` 思路，但不要把页面组件函数变成跨页隐式依赖）。无效时间必须输出中性值而非 `Invalid Date`。各页面可按产品需要选择日期、时分或日期时分 format，但必须从同一个本地时间点格式化，不能再 slice 原字符串。特别注意 data mapping 层不得在仍可需要本地化的时间戳到达页面前先切成 UTC 字面展示串；保留原始时间或通过共享 formatter 投影。

**测试：** 固定 `timeZone` 覆盖 UTC+8 跨日、夏令时地区、非法字符串；账号会话/导出、P7 收件箱与会话、P5 时间线、职位发布时间、屏蔽/规则时间和企业认证日期均验证本地日历/时分口径。工作经历的本月上界要覆盖“当地已是新月、UTC 仍是上月”和反向时区，确保按用户本地 `YYYY-MM` 给原生年月控件。出生年月、毕业年月等业务“日期字段”不能被错误当作 UTC 时间戳转换。

### C5. 通用反馈页在 Backend 模式只能提交真实“产品反馈”

### C7. 组织屏蔽搜索必须区分空结果、加载和失败，并可重试

**现象：** 候选人在屏蔽名单中选来源并搜索组织时，首页请求若发生网络、503 或 strict-decoder 错误，输入框保留但页面没有结果、错误文案或重试动作；视觉上和“没有匹配组织”完全相同。已有结果时“加载更多”失败也只是静默停留，用户不知道是否应重试以及如何重试。

**根因：** `src/屏幕/组织查询钩子.ts` 的首页与翻页 `catch` 都只保留/清空局部数据并退出 loading，未保留 error 状态或 retry action；`src/屏幕/屏蔽名单.tsx` 只根据 `结果.length` 和 `下一页游标` 渲染，既不显示 `搜索中`，也不渲染失败或已成功空结果的语义。现有 hook 测试还把“失败后仅退出 loading”固定为唯一结果。

4. Mock 的 free-text 原型不挂载 Backend 搜索、错误或分页状态；不修改后端 API、隐私写入、组织 ID 选择规则或现有 session/401 清理。

**测试：** hook 覆盖首页 503/network/decoder failure、成功空页、输入/来源切换时迟到失败；屏幕覆盖安全错误文案与重试参数、追加失败后已有命中仍可见且重试使用同一 cursor、成功终页隐藏 CTA、Mock 不请求搜索。更新当前“失败只退出 loading”的断言。

## 6. 工作包 D：岗位管理与通用错误不制造误导

### D1. “归档岗位”必须有可区分的目标

**现象：** 招聘“我的”的“岗位管理”和“归档岗位”都跳到 `/hr/jobs`。当没有归档岗位时，`岗位管理` 根本不渲染“已归档”分组，因此两个入口没有差异。

**根因：** `src/屏幕/企业我的.tsx` 两个入口同用 `路径.岗位管理`；`src/屏幕/岗位管理.tsx` 仅在 `归档组.length > 0` 时渲染分组。

**修改：** 保留入口时，为“归档岗位”增加明确的路由 state/query/fragment（选择一种现有导航体系可安全携带的方式），目标页读取它并聚焦归档分组；归档组为空时仍显示最小“暂无归档岗位”的功能性空态。或者删除重复入口。不得通过渲染虚假归档岗位解决。

**测试：** 两入口目标可区分；零归档时归档入口可见空态；有归档时定位正确；发布、归档、重开、删除的已有岗位 CRUD 行为不回归。

### D2. 不把 5xx 或未审核 4xx 的原始英文展示给终端用户

> **状态：已完成，原问题已失效。** 判定时间：`2026-09-05 05:37 +08:00`。依据：当前前端 `main@fc006281` 已包含该批安全错误映射与 P5 无效详情收口；`src/数据/HTTP客户端.ts` 不再把未审核原始服务端文案直接交给终端页面，P5 缺失/无权访问详情按终局不可用处理且不开放无意义重试。保留下文作为历史问题和回归验收依据。

**现象：** 某些页面将后端原始英文 message 直接展示。例如历史 MatchCase 页的 500；招聘端打开不存在的 MatchCase 深链时，页面虽有“这一单暂时打不开”，正文仍显示服务端英文 `The match case does not exist.`，且把终局 404 当作可无限“重试”的暂时失败。

**根因：** `src/数据/HTTP客户端.ts` 的 `取后端错误文案()` 已处理 502/503/504 与部分 closed code，但 500、`internal_error` 和未在闭合表中的 4xx 最终都落到 `error.message`。`src/状态/后端/MatchCase操作.ts` 的失败快照直接使用该函数，`src/屏幕/P5/MatchCase详情.tsx` 又把快照 error 原样渲染并无差别放出“重试”。

**修改：**

1. 5xx（包含 500）及 `internal_error` 一律映射为中文安全通用文案；
2. 只有已审核、闭合且可行动的 4xx/业务错误码才能在 UI 使用具体文案；
3. P5 detail 的“case 不存在或当前不可访问”闭合 404 应显示中文不可用页并移除 retry，避免将 foreign/missing case 的终局状态伪装为短暂网络失败；其它可恢复读取错误保留 retry；
4. 原始 message 若需诊断，仅留在开发诊断通道，绝不进入 toast、错误卡或页面文本；
5. 不把普通 `Error`、`invalid_response` 或网络错误误归类为 5xx，保持当前三者的安全文案。

### D5. Backend 岗位管理不得把已退役的 Mock 在谈数组显示为权威 `0 人`

**现象：** Backend 招聘账号的岗位管理页对每一条权威岗位均显示“在谈 0 人”，并因而开放“删除”操作；当前账号的两个岗位都复现。这个 `0` 不是服务端确认的空 Case，而是前端 Backend 种子特意清空了遗留 Mock 数组后的长度。

**本批纯前端修改要求：**

1. Backend 模式下，`岗位管理`、行内语义、停止确认和删除可见性不得读取 `状态.企业候选列表` 或任何其它 legacy MatchCase 演示数组；Mock 保持既有实时原型计数与删除保护。

3. 在没有按岗位权威总数/删除资格合同之前，Backend 岗位管理不显示“删除”操作；不要因前端数组为空放行不可逆删除。停止招聘在 Backend 必须始终进入确认，但确认文案只能说明“可能影响仍在进行的流程”，不得声称确切人数或“候选会收到终止通知”。实际命令继续由现有后端接口执行，前端正确展示其闭合错误；本批不新增 endpoint、不改服务端业务规则。
4. `组织岗位` 的 legacy reducer 保护只能服务 Mock；Backend 分支不得再依赖其空数组得出“可删除”。若现有 Backend operation 已通过服务端 mutation 后重读权威岗位列表，保持该 CAS/刷新路径，不能用局部乐观删除替代。
5. 后续若产品需要恢复精确“在谈 N 人”与按人数开放删除，另立先后端任务：后端为当前 recruiter + job scope 发布权威、可分页外精确的 count/eligibility 合同，前端 strict decoder 接入后再显示。这个后续合同不属于本 Handoff。

**测试：** Backend 种子中 legacy `企业候选列表=[]` 且 P5 未读/首屏/`nextCursor` 非空/读取失败的矩阵：页面从不显示“在谈 0 人”或确切人数，且不暴露删除；停止始终需中性确认，不含捏造人数/通知承诺。Mock 同样矩阵保持既有实时在谈数、仅零人在谈可删除的原型语义。补断言 Backend 渲染不读取 legacy candidate array；真实服务端拒绝停止/删除时现有错误提示仍正确显示。

## 10. 工作包 H：所有职位分类入口的中间层可访问性

### 问题与复现

招聘方在 Backend 模式发布岗位，以及候选人在 onboarding 选择期望职位时，都会经历根分类 → 中间分类 → 可选叶子的至少三级目录。选择一级“产品”后，右侧出现 `产品经理 / 游戏策划 / 高端产品职位` 等**仍需继续展开的中间层**。它们在 DOM 可访问树中却均为 `button[aria-disabled=true]`。因此键盘、读屏用户和遵守 disabled 语义的自动化都可能无法继续；实际点击后，确实能进入下一层并选择叶子（例如 `AI产品经理`），表单也能正常保存分类引用。

这不是 JD 解析或后端 taxonomy 合同问题：目录数据正确返回，叶子选择、预填和岗位发布均已正常完成。问题仅在前端把“可展开”节点错误标成了不可用。

### 根因

`src/屏幕/发布岗位.tsx` 的 `职业分类层后端` 和 `src/屏幕/选期望职位.tsx` 的 `小类卡后端` 中，非叶子节点的按钮都同时具有：

```tsx
onClick={() => 切子项(项)}
aria-disabled={!项.selectable ? true : undefined}
```

`切子项` 的设计正是“非 `selectable` 节点继续请求/展示子层，`selectable` 叶子才写入表单”。`aria-disabled` 与这个交互模型互相矛盾。

### 修改要求

1. 中间节点是可操作的“进入下一级”按钮：在发布岗位和候选 onboarding 两处都移除 `aria-disabled`，不能添加原生 `disabled`。
2. 若需要表达层级导航，使用与真实状态一致的 `aria-haspopup`、`aria-expanded` 或清晰的可访问名称/辅助文案；不要把可展开错误宣称为不可用。
3. 叶子仍只能走当前“选择分类引用”的路径；中间节点不得被误写入 `category_reference`。
4. 保持现有严格 taxonomy decoder、异步 loading/error 处理和 Mock 两层选择器行为；本工作包不改变 JD 上传、解析、建议字段或岗位后端合同。

### 必测

- 发布岗位和候选 onboarding 的至少三层目录：中间节点均可通过键盘 Enter 和 Space 进入下一层；可访问树不把它标为 disabled；
- 叶子仍可选择并保存正确的 ID/display name；中间节点不会被保存为分类；
- taxonomy 子层 loading/error 时不会保留旧层作为可操作的错误结果；
- Mock 选择器及已有岗位编辑中“发布后不可改”类别展示不回归。

建议更新：`src/屏幕/发布岗位.test.tsx`、`src/屏幕/选期望职位.test.tsx`，必要时补独立的键盘可访问性测试。

## 13. 工作包 K：匿名候选画像不得伪称 AI 生成和双向核验

### 问题与根因

```tsx
<代理横幅
  前文="初筛与前几轮我已谈完，"

  // ...
/>
```

- `src/屏幕/看市场.tsx`；
- `src/屏幕/在谈首页.tsx`；
- `src/屏幕/企业在谈候选.tsx`。

### 修改要求

1. Backend 横幅的完整文案必须由目前已知的 scope/snapshot 状态选择，不能永远以“已谈完”开头。
2. 至少满足下列事实边界：

   - 游标未尽：保留“已读入的里”一类非全量语义，且前缀同样不能作全量/完成承诺。

## 22. 工作包 T：双架 MatchCase 历史不能因单槽 scope 栅栏永久骨架屏

### 问题与复现

Backend 的候选端“历史代谈”和招聘端“历史代谈”均同时展示“已谈成”（`completed`）与“已结束”（`ended`）两架。任一架首次请求失败时，页面本应显示“历史暂时加载不了”与“重试”；实际 `completed` 请求返回 500 后仍无限显示两张骨架卡，既没有错误文案也没有重试入口。另一架可独立完成或为空态。

这不是要求前端吞掉后端 500：服务端故障仍应由服务端修复；本工作包只修复前端已收到读取失败后丢弃失败快照、把可恢复错误伪装成永久加载的问题。两端、两个 lifecycle 都必须互相隔离。

### 根因

`src/屏幕/P5/MatchCase历史.tsx` 在同一个 effect 内先调用 `设置P5范围(role, completed键)`，再调用 `设置P5范围(role, ended键)`，随后并发 `加载历史` 两架。`src/状态/后端/MatchCase操作.ts` 的 `P5可见范围` 是每个 role 仅能存一个字符串的槽位；第二次注册会使 completed scope 的生命周期代际失效，且把可见 scope 改成 ended。

于是 completed 的读取已经先落了 `阶段: '进行中'`，但 500 落入 catch 后，`栅栏仍当前(fence)` 因 visible scope/代际不匹配而返回 false；失败快照从未落位，组件只能持续把这条“进行中”快照渲染为骨架。现有 `MatchCase历史.test.tsx` 只用操作 mock 断言“先注册两键再并发加载”，没有执行真实栅栏和拒绝 Promise，反而把冲突时序当作正确行为。

### 修改要求

1. 重新设计 P5 的可见范围注册，使同一页面可同时拥有多个独立的 active scope。每个历史架子的读取、失败、重试、刷新和追加必须只受自身 `scopeKey` 的生命周期保护，不能因兄弟架子注册或重试而变 stale。
2. 不可用“最后注册者获胜”、串行请求、延迟/定时器或忽略失败来规避问题。推荐把单值 `P5可见范围[role]` 替换为可登记多个 scope 的集合/带挂载代际的 lease，或提供显式的多 scope 注册 API；无论实现方式，都必须防止卸载→同路径重挂的 ABA 迟到回写。
3. 保持现有安全栅栏：切换 subject、role、会话、离开历史页时，旧读取的成功或失败都不得回写当前页面；同 scope 的读代际、单飞读锁、分页窗口和 mutation 后刷新语义不回归。
4. 组件层应保留现有首载失败的中文错误态与“重试”。`completed` 失败、`ended` 成功/空态（以及反向组合）必须同时正确可见；已有成功列表刷新失败时仍保留旧卡并显示单独错误行，不能降级成骨架或空态。
