## 3. 页面布局和交互

### 3.1 代谈、市场、推荐列表

覆盖招聘推荐及收藏/淘汰筛选、求职看市场、双端现有代谈列表及非历史架子。保持当前浅底白卡、信息顺序、头像/画像、薪资位置、分数环尺寸和业务动作。卡片默认不铺开六行。

- 将现有分数圆环变为独立可操作的按钮，只有圆环可见，不增加环下文案或额外图标。
- 保留可访问名称“查看匹配分析”，支持键盘 Enter/Space；无需在视觉上重复这个名称。
- 圆环视觉尺寸不变，触摸目标至少 44×44px；不挤占薪资、画像等原有内容。
- 点击圆环只打开分析弹层，不触发卡片详情导航、收藏、淘汰、委托或滑动行操作。不得产生嵌套原生按钮。
- 打开时使用该行已返回的解释；弹层开关不发请求。
- `match_score=null` 保留中性“—”，不绘制假的 0 分环，不添加环下说明。真实 `0` 正常显示。
- 换账号、角色、意向、岗位或记录时关闭旧弹层；刷新替换同记录数据时使用新权威值，解释变 null 时清除旧六行。

### 3.2 列表分析弹层

复用现有底部弹层框架、遮罩、圆角和抓手，不增加弹层基础设施。

阅读顺序：标题“匹配度分析”与关闭按钮 → 当前记录的简短岗位上下文/总分 → “推荐生成时的匹配结果” → 六维行 → 技能口径说明。弹层中总分使用紧凑文本，不再增加分数环。

采用第 4 节的最终紧凑勾选行效果，覆盖初版“右侧大分项、原因固定另起一行”的布局。长原因自然换行，维度与小号分项保持可读；内容超出窄屏可视高度时在既有弹层内滚动，关闭控件保持可达。

关闭按钮、遮罩和 Escape 均关闭弹层并恢复到触发圆环的焦点；触发记录已卸载时不恢复到旧节点。弹层打开期间键盘焦点不能进入背景卡片。

### 3.3 招聘推荐详情和在谈在线简历 Tab

匿名在线简历/推荐详情、招聘在谈详情的在线简历 Tab、从历史进入的招聘详情均直接展示一个“匹配度分析”区。

- 保留现有匿名画像与职位行，不重新设计姓名或头像逻辑。
- 阅读顺序沿用现状：匿名画像/职位行 → 匹配度分析 → 个人优势 → 求职期望及经历等后续正文。
- 总分保留在现有顶栏；分析区不重复分数环。
- 新解释存在时替换原有限六行依据，不再显示独立“推荐依据”或“当前接口仅提供部分匹配依据”。
- 分析不是个人优势，不写入简历正文内容或个人亮点字段。

### 3.4 求职职位详情与职位资料 Tab

覆盖从推荐进入的职位详情、pre-Case 协商详情的职位资料 Tab、已有 Case 在谈详情的职位资料 Tab、从历史进入的详情以及求职聊天“看职位”层。

- 保留白底分节和现有岗位/薪资/JD/公司/发布人区，不重排这些内容。
- 推荐职位详情在分析区保留本页唯一总分环，六维行在其下直接展开。
- 在谈详情已有顶栏总分时，职位资料 Tab 不重复分数环。
- 聊天“看职位”沿用当前 Case 职位资料版式，仅保留一个总分位置。
- 删除旧的“当前简历学历/经验核对行作为本次匹配分析”的路径；学历不属于六维评分。岗位对学历的公开要求仍可在 JD 中展示。
- 新解释存在时不再另设“推荐依据”小区。

### 3.5 招聘聊天“看在线简历”层

保持已批准的灰底白纸版式。纸身内容顺序仍是：姓名 → 最近职位/年限 → 手机/邮箱 → 工作经历 → 教育经历 → 个人优势。

在完整纸身下方增加同 Case 的独立分析区，使用单独白色区块与纸身留出间距，区块内标题、唯一总分环及六维行沿用已确认 Mock Up。分析不进入个人优势、工作经历、PDF 正文，也不改变附件原件内容。

底部“继续沟通”保持现有关闭行为。手机、邮箱仍为“—”；身份姓名与头像逻辑不在本次重做。资料失权时遵守现有不可用分支，不因解释仍在缓存而展示旧简历或分析。

### 3.6 历史代谈列表

双端及 Mock 的历史/归档列表保持原样：公司/候选摘要、职位、结果、结束阶段、时间和“回看往来”等现有信息保留。不论该行是否有分数或详细解释，都不新增评分 UI 或分析入口。

历史卡打开现有详情路由后，详情使用自己的响应展示分析。列表不通过携带别条记录的解释补齐详情。最初指定的历史读取合同仍纳入严格解码和验证责任，不能因列表不显示而放宽响应校验。

## 4. 六维展示语义

固定顺序和名称：方向、技能、经验、地点、办公方式、薪资。

最终视觉采用用户提供的 Mock 勾选行风格：左侧状态图标，旁边为维度名称和次级小号 `points/max_points`，右侧用较弱但可读的文字展示原因与状态。matched 使用绿色实心勾选；其余状态保留各自图标及状态文字，不能全部退化成相同空心圆。长原因允许换行，窄屏可将右侧说明折到本行下方，不截断关键原因或挤掉分项。详情与弹层共用此行样式。截图中的“学历”仅作视觉参考，不新增为评分维度。

| 后端状态 | 可见标识 | 状态文字 |
|---|---|---|
| matched | 实心勾选 | 匹配 |
| partially_matched | 独立半圆/部分匹配标识 | 部分匹配 |
| not_matched | 空心叉标识 | 不匹配 |
| unknown | 中性空心横线标识 | 未核对 |

颜色沿用现有绿、协调橙和中性/提醒色体系；标识与文字同时存在，不只靠颜色区别。状态直接来自后端字段，不按分数大小或是否存在证据文字推断。

每行显示实际 `points/max_points`；技能可显示“命中X/Y个岗位关键词”。归一化关键词命中不是模型认证能力；部分命中不代表全部满足，即使取整后 0 分也必须显示“部分匹配”。

`reason_code` 使用固定中文闭表映射，不展示原始码、不生成模型文案。unknown 原因必须区分缺资料、要求未确认和口径不可比。新解释标题下显示“推荐生成时的匹配结果”，技能说明为“技能按关键词命中核对，不代表能力认证。”不暗示当前简历已经重新核验。

## 5. 来源、缺失和错误

### 5.1 解释合同

字段为 `match_explanation`，不是 `match_analysis`。未请求展开时键缺席；显式请求后键必须在场，可为合法对象或 null。

对象的版本、basis、六维顺序、reason/status 对应关系、技能计数和分项约束以冻结后端 OpenAPI/验证器为准。当前版本为 `match-explanation.v1`、`discovery-ranking.v2`、`batch_snapshot`，总满分 100，六维权重分别为 25/35/15/10/5/10。前端验证并展示后端实际分值，不实现另一套评分器。

各分项之和必须等于 `total_points`，且等于同响应的 `match_score`。请求展开后缺键、损坏对象或总分不一致进入既有契约错误与重试分支，不能静默转为 null。默认未展开响应、收藏/淘汰/重试/归档等写回执继续遵守各自闭合合同。

### 5.2 合法缺失

- `match_explanation=null`：保留合法总分，显示“暂无该次匹配的详细分析”。
- 同一来源有旧正向原因：在同一分析区标为“有限依据”，仅展示能解释的已知原因；不能补出负向状态或分项分数。
- 无旧依据：仅显示缺失说明，不造六条“不匹配”或“未核对”。
- `match_score=null`：显示“—”，不当作 0，不用当前岗位/简历计算。
- 无特定人岗评分上下文的通用职位详情：显示“当前职位没有特定推荐上下文”。

### 5.3 推荐详情上下文

从推荐进入职位详情时，路由携带 `recommendation_id / batch_id / intention_id / job_id` 精确坐标。坐标用于定位来源，不是权限证明。

刷新后只能恢复原推荐及其批次。已有接口无法恢复该记录时显示“该次推荐上下文已不可用”；仍可展示当前有权访问的通用职位资料，但不拼入最新批次或同岗位其他意向的匹配分数/解释。直接打开无推荐坐标的通用岗位详情，不扫描其他意向推荐来拼数据。

不为恢复旧批次新增后端接口，也不新增本地持久评分快照缓存。保留现有权限读取、账号/角色/意向/岗位/记录隔离及迟到响应栅栏。推荐上下文丢失不改变现有写动作的授权门槛。

### 5.4 Case、协商和聊天

Case 与协商各自使用自己的响应；聊天使用本会话的 Case。不同角色分数可以不同，不能跨角色复制。协商详情存在嵌套 `case_detail` 时，外层与嵌套解释完整解码，并校验同一候选视角的同源关系。pre-Case 转 Case、归档、刷新和写后重读都不得遗留旧记录解释。

## 6. 请求覆盖和实际链路

以下只增加指定读取展开，不把 include 加到所有接口。保留现有分页、过滤、生命周期、岗位与游标参数；多个展开合并为同一个 include。

| 求职推荐/看市场 | `GET /api/v1/me/job-recommendations`；`match_explanation` | 发现推荐数据源 → 当前意向快照 → 发现推荐映射 → 求职推荐卡 |

| 招聘历史列表 | `GET /api/v1/recruiter/match-cases/history`；仅 `match_explanation` | MatchCase 数据源 → 历史快照 → 历史代谈展示映射 → 原历史卡，不新增评分 UI |
| 双端 Case 详情 | `GET /api/v1/recruiter/match-cases/{case_id}`、`GET /api/v1/me/match-cases/{case_id}`；`screening_records,match_explanation`，已有 `progress_details` 时一并保留 | 解P5详情 → 详情控制 → MatchCase/详情展示映射 → 职位资料或在线简历正文 |

| 真人聊天资料层 | 同会话的 Case 详情读取及展开 | use真人会话资料 → 当前 Case 资料状态 → 资料映射 → 职位资料或真人在线简历及独立分析区 |

## 7. Mock

对应 Mock 页面使用同一六维展示组件、状态含义和布局。每条演示记录保存固定快照，列表分数、详情总分和分项合计一致；当前简历/JD 编辑不改变既有演示快照。

允许调整现有 Mock 分数，不要求保留旧本地评分算法产生的数值。不同记录保留不同快照，至少涵盖四态、技能部分命中但 0 分、真实总分 0、无快照与总分缺失，便于观察记录切换和缺失清理。

旧学历核对行不属于新评分维度。不得让列表继续用本地 JD/学历/经验评分，而详情展示另一份六维快照。历史列表同样不新增评分 UI。

## 8. hidden 和资料权限配套

保留后端 hidden 字段，不清旧值、不新增兼容层。现有经历开关仍接 organization-blocks，徽标按有效屏蔽状态展示，新经历 hidden=false，旧值在无关保存时保留。

后端已取消 hidden 的隐私作用：源公司存在、current_employer=anonymous 且无有效屏蔽时，即使 hidden=true，前端也展示服务端实际返回的公司。更新过期的说明和 fixture，不在前端按 hidden 再遮蔽。personal_highlights 继续消费原字段，合法空数组正常展示，不强行生成亮点。

有效投递后的具体 Case 不因后续企业屏蔽撤销已授予的在线资料、身份和 PDF 访问；推荐和未投递 Case 仍受屏蔽，其他披露/授权门不变。前端提示和测试不得声称“屏蔽后撤回所有历史访问”，也不得在前端自行给所有 Case 放行。

## 8A. 全页面薪资格式与来源

### 8A.1 统一显示合同

本节统一已有薪资数值字段，Backend 与 Mock 同一口径；不把薪资金额与六维中的“薪资匹配状态/得分”混为一项。

| 同源数据 | 显示 |
|---|---|
| 月薪 30–45，年薪月数未填或为 12 | `30–45K` |
| 月薪 30–45，明确 14 薪 | `30–45K x 14` |
| 日薪 300–500 | `300–500 元/天`，不追加年薪月数 |
| 时薪 40–60 | `40–60 元/时`，不追加年薪月数 |
| 合法单值（上下限相同） | `30K` / `300 元/天` / `40 元/时`；月薪可追加 ` x 14` |
| 来源明确为面议 | `面议`，不追加年薪月数 |
| 展示字段缺失、空白或无法安全判明单位 | `薪资未知`，不造 0、不推断面议 |

区间统一使用 en dash `–`，月薪数字与 `K` 无空格，日薪/时薪数字与单位之间一个空格，后缀使用小写 ASCII ` x N`（不再带“薪”字）。只有月薪且明确填写非 12 的合法年薪月数才追加；未填只是省略，不代表已确认 12 薪。不得按 12 补写接口或持久数据，不把年薪/月薪/日薪/时薪相互折算。只读展示统一移除对应独立的 `N 薪` 标签：非 12 月薪已由后缀表达，12 薪及日/时薪也不另留标签；填写控件的标签不受此规则影响。

填写控件仍保留明确的“月薪 · K / 日薪 · 元/天 / 时薪 · 元/时”和“年薪月数”标签；上下限数值框、滚轮以及独立年薪月数输入不改成拼接字符串。选定后的摘要、保存回显和再次读取遵守同一显示合同。表单未确认仍为“请选择”或既有必填占位，不混同只读的“薪资未知”；明确面议继续沿用已有提交语义，不重写 0/空值协议。

### 8A.2 页面覆盖矩阵

“全页面统一”包括所有已有结构化薪资展示；不是给每个页面新增薪资区。保留各页现有层级与位置，公共职位卡/详情的薪资沿用现有薪资字体和强调色，资料 Tab 仍使用资料行，不因示意图统一搬到标题旁。

| 页面/入口 | 现有链路与本次责任 |
|---|---|
| 建档首屏 | `学生分流` → 薪资区间层 → 引导预填；统一确认摘要，保留未确认/面议/区间三态和确认闸门 |
| 求职意向添加、编辑、管理与顶部选择栏 | `添加意向`、`求职意向管理`、`顶部意向栏` → 后端映射/意向模型；统一草稿回显、保存回读及用于消歧的薪资摘要 |
| 发布/编辑岗位、岗位管理及自己的岗位详情 | `发布岗位` → 后端映射 → `岗位管理`/`岗位详情`；保留输入布局，统一只读薪资带和年薪月数后缀 |
| 求职市场/推荐卡及推荐职位详情、直达通用职位 | 发现推荐映射 → 求职推荐卡、准备职位正文/职位正文展示；统一字符串并移除重复年薪月数标签；无推荐上下文仍可展示有权读取的公开岗位薪资 |
| 求职代谈各架子、pre-Case 与已有 Case 详情 | 连续代谈/详情展示映射 → 求职在谈卡、详情顶栏、职位资料；使用当前记录公开薪资，不跨记录补值；空白统一缺失占位 |
| 招聘 Case 的岗位上下文与职位资料 | MatchCase/详情展示映射 → 详情顶栏及已有职位信息；仅格式化公开岗位薪资，不新增候选人的期望薪资数字 |
| 真人聊天的“看职位”及既有结构化职位卡 | `use真人会话资料`/`Backend真人会话` 与 Mock `真人会话`/`企业真人会话`；同 Case 资料统一格式，纸身简历不新增薪资区 |
| 企业公开页的在招职位 | 企业公开页映射 → `企业公开页展示`；统一已有岗位薪资字段，不新增评分区 |
| 问 AI 代理的结构化岗位/在谈查询结果卡 | `问AI代理/查询结果展示` 复用发现推荐及连续代谈薪资口径，移除重复年薪月数标签；不改写助手自然语言内容 |
| 历史/归档 | 不新增薪资或评分区域；现有薪资字段若存在则统一格式，打开详情遵守详情规则 |
| 其他 Mock 消费者 | `模拟数据`、`企业端模拟数据` 中供上述页面消费的薪资带和年薪月数统一；同记录各入口金额/周期/后缀一致 |

招聘推荐/候选卡和匿名在线简历中仅有薪资关系的入口，继续展示既有关系文案，不补披露候选人薪资数字。个人简历编辑、统计、普通消息气泡、JD/PDF 正文中的自由文本不扫描替换；它们不是结构化薪资控件。既有结构化聊天职位卡的格式统一不意味着给消息新增评分区。

### 8A.3 数据来源和字符串边界

优先在现有映射处使用本条记录的结构化上下限、周期和年薪月数；保留 Case 冻结资料语义，不能为了格式化补读当前岗位覆盖历史金额。求职意向、岗位公开薪资和候选私有期望不是互相补值的数据源。

当前 negotiations 的 `job.public_salary_range` 与部分 Case 摘要是显示字符串；不能只在 JSX 全局替换连字符。允许在薪资映射边界对已核对的有限格式做明确识别：紧凑 `30-45K`、`30–45K`、`300-500 元/天`、`40-60 元/时`，以及月薪 `30-45K/month x 14薪`、Mock `30-45K · 14 薪`。明确的同源年薪月数可并入后缀，但冲突值不能自行择一或重复追加。格式化仅改变表示，不改变数值、周期、历史来源或严格 DTO 解码。

只读后端 `RenderPublicSalaryRange` 当前存在统一拼 `K/` 的实现，可能产生 `K/day` / `K/hour`；该风险尚无真实接口验证。不得把这类单位矛盾的字符串擅自解释成元。若同一记录具有可用且无冲突的冻结结构化薪资，使用其明确单位；否则显示“薪资未知”，记录为后端合同/数据问题，不能声称全量真实环境已对齐。其他不可识别或相互冲突的表示同样不得猜测。这里的显示降级不吞掉 DTO 层的契约错误；后端修复不在本任务范围。

最小实现为复用/收拢一个小型薪资格式化函数与上述有限输入适配，服务实际已有消费者；不建立通用金额引擎、不解析任意自然语言、不新增请求、配置或跨记录缓存。

## 8B. MatchCase / Negotiation 详情契约兼容

### 8B.1 范围与现状

当前闭合解码器拒绝新增的 `dialogue_progress.step` 和 answer 的 `exchange_ref`，可能使 HTTP 200 的完整详情进入“这一单暂时打不开 / 服务返回异常，请稍后重试”。兼容修复覆盖双端独立 Case、Negotiation 详情的嵌套 `case_detail`、详情阶段流及读取同 Case 的聊天资料层；复用现有解码、映射、重试和迟到响应隔离，不重构状态机。

本项后端升级不新增 endpoint、HTTP method、请求 body、action 或错误码。用户提供的独立修复说明中“不接入 match_explanation”只限制该兼容修复的依赖，不是本 Spec 的全局非目标。最终同一交付包含兼容修复、六维评分和薪资统一；测试先证明未请求评分的默认响应正常，再证明评分解释与新字段同时存在时正常。字段允许范围仍由默认/展开/写回执的各自合同决定，不全局放行未知键。

### 8B.2 dialogue_progress.step

wire 类型增加可选 `step?: 'assessing' | 'answering' | 'awaiting_human' | 'complete'`；归一化类型的 `step` 为同一闭词联合或 `null`。仅字段缺席归一化为 `null`，显式 null、空字符串、未知字符串或非字符串必须拒绝。已有整个 `dialogue_progress` 对象的可空合同保持不变。

| step | 当前步骤说明 |
|---|---|
| assessing，asking_role=recruiter | 招聘 Agent 判断中 |
| assessing，asking_role=candidate | 候选 Agent 判断中 |
| answering，asking_role=recruiter | 候选 Agent 回答中 |
| answering，asking_role=candidate | 招聘 Agent 回答中 |
| awaiting_human | 等待真人补充回答 |
| complete | 本轮问答已完成 |
| 字段缺席 | 不显示推测的当前动作，仅显示服务端轮次 |

步骤与轮次分开表达，例如“候选 Agent 回答中”及“招聘方已问 1/2 轮”。轮次直接读取 `recruiter_round` / `candidate_round` / `round_budget`，不计时推进、不本地加一。当前阶段有该对话进度时，使用上述步骤说明替代会误导执行方的旧“当前由招聘方发问”，不并列展示相互矛盾的旧步骤文案；没有 step 不从 asking_role 猜动作。

`awaiting_human` 不说明具体等谁；实际待办归属、按钮权限和用途继续唯一读取 `pending_actions[].role/purpose`。`complete` 只表示该问答块完成，不证明整个 S2 完成，更不触发前端进入 S3。阶段归属始终读取服务端状态；非当前阶段不能套用另一阶段的实时步骤。

### 8B.3 answer.exchange_ref 与严格配对

wire 与归一化 answer 联合的有正文、无正文分支均增加可选引用（归一化缺席为 `null`）。S1 `resume_submission`、S2 `needs_coordination` 的 question/answer 引用在场时统一满足 `^cex_[0-9a-f]{32}$`；显式 null、空串、坏格式和非字符串拒绝。同步收紧当前 question 仅校验非空字符串的路径。S0 `anonymous_screening` 的 question 和 answer 都禁止该键。

扩展 `解S0筛选记录` 已有的“stage + asking_role + round”账本，保存对应 question 的引用：

- answer 必须出现在同一块、同一发问侧、同轮已登记 question 之后；不能拿另一侧、另一轮或另一阶段的引用配对。
- answer 带引用时，question 必须带完全相同的引用；缺失或不等即拒绝。
- question 有引用、answer 缺引用合法；两者都缺引用同样兼容旧响应。
- 保留既有 ID 唯一、阶段/轮次顺序、角色对应、正文与回答状态约束；引用不替代这些校验。

`exchange_ref` 是不透明 ID，不解析业务含义、不从 record id 推导、不显示给用户，不建立新的通用配对框架。示例中的 `answer_source: candidate` 不是合同新增值：实际 answered 来源继续为 `agent | human`，无正文分支保留原合法来源和状态闭表，不为兼容引用新增非法来源。

### 8B.4 公开回答文案和状态语义

`confirmation_summary.confirmed_facts` 表示公开记录中已有回答依据的事项，回答可以来自 Agent 或真人。标题统一“已回答事项”，空态“暂无已回答事项”；不表示真人确认、双方接受或条件达成一致。保留真正的确认动作、其他摘要类别及授权语义，不全局替换一切“确认”字样。

`coordinating` 过程说明改为“双方 AI 正在确认是否还有待协调事项”；阶段标题“差异协同”保持现有设计。按服务端实际响应覆盖：

1. S1 Agent continue、招聘者完成 `s1_continue`、reconsider 恢复三条路径均可进入 S2；即使 open items 为空也展示 S2，不自行跳 S3。
2. S2 招聘 Agent assessing → 招聘侧 finish → 候选 Agent assessing → 候选侧 finish → 服务端进入 S3。前端不根据一侧 finish、step=complete、列表为空或回答条数提前推进。
3. S1/S2 累积历史中的 S0 `declined` 保持“已拒绝回答”，`not_available` 保持“暂无可用信息”；不折叠为 unknown，也不当作正文回答。

continue、confirmed_facts 和 S3 confirm 均不得描述成“接受全部条件”。前端回归证明其正确消费服务端响应，不声称单靠 fixture 证明后端状态机已按此执行。

### 8B.5 实现边界与自动化验证

主要接点为 `src/数据/BFF契约.ts`、`src/数据/招聘数据源/MatchCase.ts`、`src/数据/MatchCase展示映射.ts`、`src/数据/详情展示映射.ts` 及阶段流消费者；Negotiation 复用 Case 解码，并须在其嵌套入口验证，不复制一套解码器。同步 BFF 样本与相应浏览器 fixture，删除“任何 answer 携带 exchange_ref 都是漂移”的过期断言，替换为上述条件约束。

必要回归：

- step 缺席与四个合法值，null/空串/未知值/非字符串反例；两种 asking_role 的 assessing/answering，awaiting_human 不猜人，complete 不推进阶段；轮次严格使用服务端数值。
- S1/S2 answered、unknown、incomplete answer 携带匹配 ref；缺引用的旧响应兼容；S0 禁止引用；坏格式、无前置 question、跨侧/跨轮/跨阶段借 ref、引用不等或 question 缺 ref 均拒绝。
- step 与 answer ref 同时出现的完整 Case；独立 Case、Negotiation 嵌套 Case、聊天 Case 读取；默认评分未展开与显式评分展开（对象/null）两组组合，保持默认写回执合同。
- 三种 S1 continue/恢复来源后消费 S2 响应；招聘侧 finish 后仍展示 S2 候选 Agent 判断中，仅服务端推进后展示 S3；缺省 step 的旧响应不显示推测执行方。
- confirmed_facts 新标题/空态，S1/S2 累积历史中 declined/not_available 各自语义，既有待办角色/动作、阶段流、重试与隔离不回归。

Plan 按现有测试拆分选择 `src/数据/招聘数据源/MatchCase.test.ts`、连续代谈数据源对应测试、`src/数据/MatchCase展示映射.test.ts`、`src/数据/详情展示映射.test.ts`、`src/组件/阶段对话流.test.tsx` 及相关 fixture 浏览器用例；收尾执行必要的 `npm run typecheck`、`npm run lint`、`npm run build`，不因用户接手真实验收而省略自动化验证。测试清单按仓库入口生成更新，不手抄。

## 9. 最小方案和非目标

复用现有数据源、状态容器、错误/重试、卡片与弹层框架，只增加一个小型六维严格解码器、固定中文映射和共享分析展示组件。列表和详情存在多个真实消费者，这一共享范围用于防止四态、分值与缺失语义漂移。另按第 8A 节收拢现有薪资格式化，解决已核对的跨页单位、后缀和回显不一致；不借机重构表单或资料模型。第 8B 节仅扩展既有闭合字段与问答账本并修改固定文案，不新增状态机、协议适配层或通用框架。

不新建通用评分引擎、通用分析框架、身份服务、持久评分缓存或逐行详情补读机制。后续只有后端实际增加评分版本/维度，或出现现有请求能力无法满足的明确产品需求时，再考虑扩展。

聊天消息列表/气泡、个人简历编辑、通用公司页、统计页不增加评分区。历史列表不加评分。手机/邮箱和头像逻辑不重做。不借本次重构无关页面，不部署、不做后端数据迁移。

## 10. 验证义务

执行阶段按 `docs/testing/README.md` 选择最小充分的验证范围；当前为设计阶段，不把预览检查当作产品测试或真实联调。

- 请求矩阵、分页、筛选和 include 合并；详情禁止列表专用展开，协商禁止 screening_records。

- 四态同时有标识与文字，技能部分命中但 0 分仍正确；0 与 null 区分；旧推荐无快照、Case 无评分来源。
- 同记录列表/详情一致；不同批次/角色不串解释；pre-Case→Case、嵌套同源、归档和写后重读正确。
