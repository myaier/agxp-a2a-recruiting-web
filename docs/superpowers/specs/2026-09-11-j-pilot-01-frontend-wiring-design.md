# J-PILOT-01 连续委托与 S0 匹配前端接线设计

日期：2026-09-11。状态：设计草案，待用户批准全文；本轮不实施、不写 Plan。

## 1. 目标与批准边界

候选人对推荐岗位完成委托后，立即能在在谈找到同一次委托，查看公开信息初评、双端 S0 条件确认及结果；初评技术失败可按服务端权限在原记录重试或归档。关闭页面、刷新、开案和进入 S1 都不丢失记录身份。

本次是 J-PILOT-01 的完整前端接线，不只是增加 S0 气泡。招聘方参与已经创建的 Case，查看获授权的问答和 S1 附件；招聘侧发现候选人、主动发起委托的完整旅程不在本次范围。

本轮对话已确认：

1. 尽最大可能不改 PM 设计的布局和样式，复用现有列表卡、详情外壳、两个 Tab、四阶段流、总结区和动作卡，不另建委托工作台。需要增加展示内容时优先使用已有组件及其槽位，不自行发明新的 UI 组件、视觉样式或交互模式；具体约束见 §3。
2. 双端 S0 保留原聊天输入框及发送按钮，禁用输入与发送；placeholder 根据真实阶段及结果变化。不能替换成纯文字只读条，不能通过隐藏输入框改变布局。
3. 创建委托受理后留在岗位页，原主按钮变为可点击的“查看进展”；用户点击后进入同一记录。同时该记录已经能从在谈读取。不自动跳页。
4. 连续记录详情承接开案前进度、初评总结、开案后的 S0 问答及结果；允许的重试／归档使用现有动作区域。
5. 本次不安排 L3 测试。用户正在建设 STG Release 环境，完成后由用户另行设计初始化与测试框架。本 Spec、后续 Plan 和执行提示词均不安排这部分设计、建设或执行，详见 §11。

以上是已确认的方向与交互，本文件其余细化仍需用户整体审阅。批准 Spec 后才编写零上下文 Plan、进行异构文档 review 并交付新实施会话提示词。

选择“候选连续记录读取＋复用既有 Case 展示和动作”。在现有 HTTP 数据源、应用状态及详情控制模式内增加 negotiation 数据，不建立通用工作流或第二套消息系统。

| `src/屏幕/在谈首页.tsx`、`src/屏幕/归档谈判.tsx`、P5 列表／历史 | 候选 active/history 连续记录；招聘仍由 Case 列表承接 |

新增业务模块只服务 negotiation 的闭合 DTO、有限恢复记录和对应快照；精确文件边界在批准后的 Plan 冻结。Case mutation 使用真实 `case_id`，negotiation 读取及恢复使用真实 `record_id`，不能混用。

不采用只替换列表 URL：旧 Case DTO 无法表达尚未开案的委托与 retry_generation。也不把所有 pre-Case 数据伪装成 MatchCase，避免制造阶段、动作或披露事实。不新增独立聊天页面、消息 API、通用离线队列或后端聚合服务。

### 3.1 布局、样式与组件复用约束

- 本任务以数据接线、状态映射、文案和真实操作为主，尽最大可能保持原布局、信息位置、尺寸、间距、字体、颜色和响应式行为，不借接线美化页面、重新排版或改写 CSS。
- 需要增加消息、总结、失败原因或动作时，先查找并复用现有组件、展示槽位和样式能力；允许组合已有组件或补充最小的 props／状态支持，不复制一套近似组件，也不新造视觉组件或组件框架。
- §5 的连续历史分页、§6 的初评展示及 §7 的禁用输入均服从本约束；更换数据模型不自动授权新增卡片版式、Tab、面板或布局容器。
- 已有组件确实无法表达批准行为时，在设计／Plan 中指出具体能力缺口和满足需求的最小扩展。涉及新的布局或视觉取舍时先交用户确认，执行者不得以“接线需要”为由自行设计。
- Plan 对每个涉及 UI 的 Task 指明复用组件及保留的样式；有必要改动时逐项写明原因。验收检查实际 diff 和已有视觉基准，不能只写一句“保持布局”。

## 4. 委托入口、记录身份与路由

委托前复用现有附件库读取：0 份引导上传；1 份点名确认；2–3 份显式单选，不预选。请求为单岗位 `selection.items`、准确 `resume_file_id`／`resume_file_version_id` 和当次 `disclosure_acknowledged=true`。取消不发送。

发送前冻结原命令，提交中防重复操作。HTTP 200 必须检查单项回执：无 delegation_id 的拒绝不创建卡、不出现假的查看进展入口；有持久回执后保留 ID，读取 negotiation，并使 active 首屏失效重读。读取失败不撤销已受理事实，允许通过已知持久 ID 进入错误可恢复的详情。

岗位页不自动跳转。已有持久回执时，原主按钮为“查看进展”，含正常运行、失败和已结束的已知记录，均只导航不再次 POST。记录尚待核对且无可靠 ID 时使用“核对提交结果”，不能猜同岗位记录或使用空 ID。明确未建记录的拒绝仍按既有安全错误文案处理。

候选继续使用 `/deal/:id` 外形；Backend 参数接纳合同允许的 `dlg_`／`mc_` 记录坐标。已有 Case 深链由后端 alias 归一能力承接，GET 成功后按返回 canonical record_id upsert，可 replace URL 但不追加一次导航历史。不得通过字符串替换推造 ID。Mock 路由语义不改变；招聘 `/hr/candidate/:id` 仍使用 Case ID。

候选详情 GET `getCandidateNegotiation` 不带 include，`case_detail` 已含 screening_records。同一页面不再并行调用另一个候选 Case GET 补同份资料。现有 Case 动作成功后刷新拥有该 Case 的 negotiation；招聘方仍刷新自己的 Case 详情。从列表、岗位、历史、真人会话旧深链直接打开或硬刷新，均不能依赖之前列表缓存才能识别记录。

## 5. 在谈、历史与统计

候选在谈接 `listCandidateNegotiations?shelf=active`，默认省略 intention_id，覆盖全部意向；不依赖当前意向有效才能展示旧记录。若保留既有明确意向入口，其过滤必须显式、可见且与 cursor 绑定，不能悄悄用当前意向缩小主列表。

active 按服务端 `needs_action DESC, created_at DESC, record_id DESC` 原序显示。history 使用同一接口 `shelf=history`，按创建时间和 record_id 倒序。历史页面保留原外壳及卡片视觉，以一个连续分页集合承接已结束 Case 和已归档初评失败，不再拼两个 Case 分页。不开新历史页面、不新增结果筛选布局。

- 列表按 canonical ID 去重／upsert；不同委托即使同一岗位也不能合并。
- 下一页只使用本 scope 的非空 cursor；分页返回旧 v1 cursor 对应 400 时清 cursor 重读首屏，禁止无限重试。
- 刷新、create/retry/archive、Case 动作后清游标重读首屏；复用可见列表节拍，不以已载页排序冒充全局排序。
- 跨请求不是快照；状态变化可能使记录跨页移动，刷新恢复当前顺序，不承诺一次遍历捕捉全部实时变化。
- history 的 needs_action=false 不等于禁止 retry；按钮权限读取 actions.retry，不用待办字段否决恢复。
- 首载失败不显示正常空列表；同主体刷新失败可保留只读旧列表并标出刷新失败。

初评／S0 进度放进现有卡片状态位置，缺少公司、分数或技能时按既有缺失规则处理，不跨 API 拼当前资料冒充历史事实。候选首页和市场的待办横幅改读同一 negotiation 范围，文案使用“需要你处理”，不把初评恢复叫协调。移除“初筛与前几轮我已谈完”等无条件完成断言，复用横幅原布局。

统计边界：既有 `/match-cases` 摘要只统计 Case，不能作为全量委托数。本次不新建计数服务，也不无界拉全页求总数。“我的／代理详情”保留统计格，涉及总在谈、待办、归档的现有 Case 数明确标注已开案口径；初筛数继续表示真实 Case S0。连续列表横幅仅在范围读尽时显示该范围准确待办数，未读尽用不带精确总数的文案。本项属于新 Spec 待批准的文案细化，不追认旧产品已批准。

## 6. 详情布局和阶段呈现

现有顶栏、代谈进度／职位详情 Tab、四阶段流、总结／动作区和底部输入框均复用，不另建 pre-Case 布局或新增一个业务阶段。

尚未开案时，状态区域据实显示“已接手，等待开始”或“正在进行公开信息初评”；四阶段均未到达，没有轮次、Q/A 或 S0 完成事实。已有公开初评放入现有总结展示组件，来源标签明确为“公开信息初评”，不挂成 S0 已发生的总结。原布局槽内复用该组件，不给 pre-Case 伪造阶段数据。

有 Case 后，阶段与动作来自同一 `case_detail`，复用现有映射及动作控制。候选可同时回看公开初评与 S0 总结，但只渲染一份 S0 总结历史：聚合 agent_summary.condition_confirmation 与 case_detail 中重复数据不能生成两个托盘。

公开初评 fit/not_fit/uncertain 只是建议，允许按已授权后端链路继续 S0；不把 next_action 或自由文本转成新的前端 mutation。可公开的 evidence 以源数据呈现，不生成逐条件已确认清单或匹配分。

`case_detail=null` 要区分未开案和 retention 封闭：已存在 case_id 但详情封闭时清除旧 Case 内容，仅显示合同允许的记录状态，不回退到独立 Case/推荐/附件库找回封闭资料。

第二 Tab 延续现有字段缺失与权限说明。negotiation.job 只能提供其实际字段，不能补成完整 JD、公司或在线简历。招聘方不增加候选私有初评读取。

## 7. S0 消息、结果和原输入框

Q/A 继续消费稳定 id、role、真实 round 和服务端顺序；己方 Agent 在右、对方在左。角色标签使用“候选 Agent／招聘 Agent”，不显示内部 ID、task 或 operation 字样。无回答分支沿用“已拒绝回答／暂无法确认／暂无可用信息”，不能编造回答正文。成功 GET 整包替换，不 append 重复消息，不因 version 相同丢掉新问答。

系统事件以系统状态显示，不投成对方 Agent 气泡；总结在现有总结区域独立显示。保留旧合法历史，但不把用户叮嘱或人工历史伪装成双方 Agent 新问答。不公开模型内部推理和工具日志。

严格解码并映射 `outcome=outcome_code=semantic_uncertain_stop`：必须为 ended／anonymous_screening／ended／complete，needs_user=false、needs_action=false、finalized_at 合法且动作表为空。专属文案为“信息不足，未能确认条件”。保留真实问答、轮次与候选总结，进入历史，不递交 PDF。semantic_not_fit、用户结束、权限终止、业务拒绝和技术故障分别显示，不用一个“不匹配”概括所有出口。

双端 S0 不提供 respond_fact 输入／提交，新后端不应再返回该动作。若遇旧 S0 needs_user/human_decision 卡，不自动结束或伪装新终局，明确标为旧状态待核实、停止该卡交互并交负责人处理；实际版本切换前须满足后端存量盘点门。不得用前端隐藏当作存量已处置。

输入框实施约束：

| 情况 | 原输入框 placeholder | 行为 |
| --- | --- | --- |
| 尚未开案、初评运行中 | AI 代理正在进行公开信息初评 | 输入与发送禁用，无 Case 叮嘱请求 |
| S0 正常运行中 | 双方 AI 代理正在确认条件 | 输入与发送禁用 |
| S0 技术故障 | 条件确认遇到问题，待排查 | 禁用，不承诺刷新可重跑 |
| S0 信息不足终局 | 信息不足，未能确认条件 | 禁用 |
| S0 不适配终局 | 条件不适配，本次代谈已结束 | 禁用 |
| S0 其它终局 | 本次代谈已结束 | 禁用，原因在现有结果区显示 |

保留真实 input 和发送按钮的 DOM、尺寸与位置，支持原组件的禁用能力；`详情底栏` 当前把禁用输入换成只读 div 的分支必须按本需求调整，不能仅给 DTO 填禁用说明就算完成。输入值清空；键盘、Enter、按钮及程序回调都不得发请求，不仅靠颜色灰化。

进入 S1 后按真实当前阶段恢复既有非 S0 行为；即使展开历史 S0，底栏仍按当前阶段判定。其它阶段既有授权、终局只读及 Mock 演示默认行为不随本任务扩大改变。共享输入组件新增能力应保持其他消费者的默认行为。

## 8. 失败、幂等和跨刷新恢复

开案前技术失败只有 actions.retry/archive 允许时出相应按钮。retry POST 使用原 record_id、当次 expected_retry_generation 和新用户意图的 key；202 表示受理，不立即宣称 Agent 已恢复成功。failure_history 原样保留。归档 body 严格为 `{}`、不带 Idempotency-Key；成功后回读权威 shelf，不仅前端隐藏。已归档失败可按权威动作恢复原卡；已结束 Case 不因此复活。

create/retry 的未决命令在发送前冻结并按后端环境、已认证 subject/role 隔离，存入同标签页 sessionStorage：

- create：operation、key、intention_id、原有序单岗位 selection、准确 PDF pair、当次 disclosure_acknowledged=true；收到后补 delegation_id/canonical record_id。
- retry：operation、key、原 record_id、原 expected_retry_generation。
- 不保存 PDF 正文、文件名、私有诉求、消息、token 或 cookie；ID 仍按私有数据保护。

有限 pending 集合仅覆盖未决 create/retry，同一目标未决时不允许另起同目标命令。记录在已确认命令结果并恢复持久记录后删除；离开岗位页、切意向不能像现有 scope 清理那样丢弃。退出／切主体清对应 pending、视图和旧请求；硬刷先完成身份确认再恢复。存储失败时同页保留内存恢复能力，明确无法保证硬刷恢复；不因此自动重发。

恢复顺序：有 ID 先 GET record/delegation；无 ID 可用原 intention 的推荐／receipt 和 active/history 辅助核对。GET 不是按幂等 key 查命令，找不到、404、503 或存在同岗位记录都不能证明原写未受理或某次 retry 成功。

原完整命令仍在且需要确认写入结果时，允许在恢复流程中原 key＋原 body 重放一次，随后回读；不重新要求用户选 PDF／授权，不换 key，不取最新 generation，不循环自动 mutation 重试。仍未知则保留待核对，由用户显式再次核对或负责人排查。没有完整原命令时不猜测，查询只恢复能够确定的业务记录；不承诺换设备能识别丢失的未知命令。

409 按 code 区分幂等冲突、generation 或业务门，回读真实状态，不绕过门槛。Case attention 不出 Agent 重跑、pre-Case 归档或保证可结束按钮。人工排查复用现有联系／反馈方式，未真正发送不得显示“已通知负责人”，不新增管理后台或工单服务。

## 9. S1 交接与 PDF

S0 通过且原授权 PDF ready 时后端自动披露，前端只观察，不加一次确认或暂停流程。未 ready 时据实显示等待，用户执行 retry_resume_readiness 才调用既有 submitResume；使用原 Case 绑定 file_id/file_version_id 及原授权，不重新选文件、不重新要求披露确认，也不把这一写操作叫纯刷新或重跑 Agent。

双端 attachment 仅允许在 resume_submission；严格 decoder 与展示一致。阶段标题为“递交简历”。附件元数据不等于已披露，显示状态以权威阶段事实为准；不能因 filename 存在就标已发送。

下载复用 candidate/recruiter 的 Case 专属 resume-submission/content GET；GET 不创建披露。409 未授权或 404 时不得改走附件库 latest。PDF URL 租约在关闭／换主体／换 Case／卸载时回收，不持久缓存正文。

候选进入后续阶段仍从聚合详情读取 Case，现有 S1–S3 合法动作继续使用真实 case_id，mutation 后回读聚合状态。招聘方继续其原 Case 读取与权限。本任务不补齐完整 S1–S3 的新产品能力，但要验证共用链路未破坏既有消费者。

## 10. 权威快照、兼容与错误

浏览器只请求 BFF，沿用会话 cookie、Origin、no-store 和既有 HTTP 错误规范；不在 URL 放私有命令、授权凭据或全文。

negotiation DTO 对 required/nullable、枚举、record_kind、phase、shelf、actions 和嵌套对象做闭合解码；新字段不能通过放宽任意对象或把 null 补数组绕过。公开接口不支持的筛选／include／排序参数不得自行发送。

同 scope 失败可保留标明过期的只读快照；401/403、切账号角色、详情 404 清敏感视图并阻止旧请求落位。404 导致清视图与“不能推断写入未受理”同时成立，不能为核对而继续露出无权限的旧资料。独立保存命令身份不等于展示旧业务快照。

同一 canonical 记录的开案不重建第二条记录；正常轮询避免丢 Tab／折叠 UI。切主体或换记录则清草稿、弹层、PDF 及在飞归属。复用当前可见列表和详情轮询节奏、单飞与清理机制，不能同时运行 candidate Case 和 negotiation 双轮询。

当前 App-Version header 不是兼容版本门。本次部署须核对成套前后端版本；不设计旧合同 fallback 或双协议开关。后端被观察到的 candidate-recommendations 空数组序列化问题属于另一个接口，单独追踪，不把该修复或招聘发现旅程并入本 Spec。
