# 求职端 AI 聊天与内嵌查询卡片 Spec

状态：产品方向已在对话中确认；本文待用户审阅批准。用户已启动 development-workflow；本 session 只交付设计、批准后的零上下文 Plan、异构文档 review 与执行提示词，不实施产品代码。

## 1. 目标、基线与范围

开放求职端 Backend「问 AI 代理」聊天：真实发送、持久化历史、轮询、失败恢复，以及回复内部的岗位推荐列表、在谈列表和在谈详情摘要。用户可以点击业务项目进入现有详情页，也可以根据列表中的真实文字继续追问，由 LLM 定位在谈记录并查询详情。

调查基线：

- 前端：`e01291de47e4ade2b66ab681e69145e6e32bade8`；当前已有两端独立 Mock/Backend 容器、禁用聊天外壳、固定 AI 消息入口、纯展示气泡、今日简报、求职在谈卡。
- 后端仓库 `agxp-monorepo`：`release/0.2.5`，`719ead0a0a4368b4dc2ff7e85d57ab74f47e9095`。实施时由调用者提供 checkout，以该精确版本的 `apps/recruitment-bff/openapi/mobile-v1.yaml` assistant 标签及 schema 为契约依据，不依赖规划机器路径。
- 核对过后端 `apps/recruitment/internal/assistant/queries.go`、`apps/recruitment/internal/mcpgateway/assistant.go`、`apps/hub/internal/worker/assistant_process.go`。源码调查不代表运行环境已部署或真实模型链路已验收。

本设计仅替代 `docs/superpowers/specs/2026-09-14-agent-session-and-display-components-design.md` 中求职端助手禁止真实聊天和暂不接业务结果的局部约束。招聘端仍保持未开放；Mock 现有剧情、日报与交互保留。

## 2. 已确认的产品形态与最小方案

比较过三个方案：纯文字/紧凑列表会偏离用户希望的原生卡面；完全复刻页面详情和补齐后端字段会扩大范围；采用「今日简报式消息容器 + 复用原生列表卡 + 独立详情摘要卡」，先用现有契约、缺失字段占位。

具体约定：

1. AI 消息框参考求职端 Mock 今日简报的头像、气泡宽度、标题层级、留白和内嵌卡片形式。解释正文与查询结果处于同一助手回复容器，结果按 `cards` 原序排列。
2. 岗位列表逐项复用市场页岗位卡的展示组件和样式。在谈列表逐项复用现有「求职在谈卡」。不另外设计精简列表皮肤。
3. 在谈详情新增独立摘要卡，视觉与现有卡面一致，呈现职位/状态、公开初评、条件确认与详情入口。可复用已有阶段标签和摘要展示，不能嵌入整个业务详情页。
4. 项目主体点击跳转到对应原生业务页面；查询时间置于对应结果区域。不得把一整条助手回复包成按钮，避免与内部项目按钮嵌套。
5. 纯文本回复使用现有普通气泡；有卡片时使用简报式宽容器。没有真实数据的统计、日报、漏斗和规则建议不展示，不把「今日简报」标题硬套给查询结果。

只提取当前第二个真实消费者需要的市场卡展示部分；不增加通用卡片注册引擎、模板配置、聊天框架或第二套会话存储。

## 3. 消息与轮次契约

浏览器沿用现有同源 BFF 客户端和鉴权，唯一助手数据来源为：

|方法与路径|请求|响应用途|
|---|---|---|
|GET `/api/v1/me/assistant/messages`|可选 `cursor`|历史 `items`、`next_cursor`，默认每页 20 条，最新在前|
|POST `/api/v1/me/assistant/messages`|`{text}` 和 `Idempotency-Key`|202 返回一条消息及轮次|
|GET `/api/v1/me/assistant/turns/{turn_id}`|无正文|读取处理状态与最终回复|
|POST `/api/v1/me/assistant/turns/{turn_id}/retry`|无正文，新 `Idempotency-Key`|202 返回同一消息的新轮次|

消息字段：`message_id`、`turn_id`、`text`、`created_at`、`status`、`retryable`、`error_code`、`reply`。`reply` 仅成功时存在，包含 `text`、`visibility`、`cards`。字段、ID 模式、nullable、枚举及响应信封由正式 OpenAPI 校验，不将任意 JSON 强制转型为可信数据。

- 首次进入先读历史，展示倒序为旧到新；首读失败可重试，不将失败当成空历史。首读完成并确认没有处理中轮次后允许发送。
- 新消息 trim 后为 1–4096 UTF-8 字节；本地校验不能按 UTF-16 字符数替代。输入占位使用用户语言，不暴露 Backend/Runtime 实现术语。
- 从发出 POST 到轮次离开 `processing` 禁用输入与发送。202 后每 2 秒定向轮询，无 SSE、无逐字模拟输出。同时保留逻辑单飞保护。
- 页面卸载、退出账号、角色或数据源切换时停止轮询、隔离旧请求结果。重进重新读历史，最新消息仍在处理中则恢复轮询。加载更早历史保持阅读位置；新回复在接近底部时跟随，不打断阅读旧消息。
- `succeeded` 展示真实文本和卡片；`failed` 展示中文失败状态；`uncertain` 展示结果暂无法确认，不自动重跑。
- 只有 `failed && retryable` 展示显式重试。新重试使用新幂等键，以 `message_id` 原位替换，`turn_id` 更新，不能多出一条用户消息。
- POST 网络错误、超时、503 或成功响应无法可靠解析时保留同一操作的原 key/text，提供重试确认结果的入口；不能用新 key 当新消息发送。确认结果前不允许发起不同内容。刷新后通过服务端历史恢复，不另建本地持久化发件箱。
- 409 `assistant_turn_in_progress`：重读历史找到活动轮次并恢复轮询；`assistant_retry_not_allowed`：重读对应轮次；`assistant_unavailable`：说明代理当前不可用，不切换到 Mock。
- 轮询读取失败保留已知状态，显示可重试提示，不自行判定执行失败或成功。账号/角色失效服从原有鉴权门控。错误码仅作分支，不原样显示内部英文错误。
- `reply.visibility=unavailable` 只显示服务端提示和用户原文，不恢复旧卡片。未知卡片 kind 不渲染，不当成其他已知卡片；已知类型数据不合法时显示数据读取失败，不能用 Mock 或缺字段占位掩盖契约错误。

## 4. 三类结果与占位规则

每个结果外层固定有 `kind`、`queried_at`、`data`。时间使用查询时刻，不替换为渲染时间；历史快照不通过额外详情请求静默补成最新数据。空列表显示真实空态，不能填充演示行；`next_cursor` 非空时提示可继续问“下一批”，本期不新增业务结果独立分页 API。

### 4.1 岗位推荐

`data` 为 `intention_id`、`items`、`next_cursor`；每项含 `job_id`、`title`、`organization_name`、`office_location`、`salary_lower`、`salary_upper`、`salary_period`、`annual_salary_months`、`safe_reasons`。

复用市场岗位卡的公司头、职位、薪资、标签、发布人/操作区域布局：职位、公司、地点、薪资、年薪月数由真实字段映射；安全推荐理由在对应项目附属区域展示，保留原序。薪资周期区分月/日/小时，缺年薪月数不假设 12 或 13 薪。

公司简介、Logo、匹配分、发布人等未提供字段用明确未知/中性空图占位，不根据公司名字命中演示 Logo；数值缺失不显示 0 分。市场卡中的委托操作位置保留并禁用，显示需进入详情操作的说明，不能从只读快照推导“已委托”或可委托权限。

市场页自身的原样式、真实字段、计算适配分和委托行为保留在原连接层；共享卡片只消费 props，不读取 Context、模拟数据或自行请求/算分。

### 4.2 在谈列表

`data` 为 `items`、`next_cursor`；每项含 `record_id`、`record_kind`、`intention_id`、`job`、`case_id`、`phase`、`needs_action`。`job` 只含 `job_id`、`title`、`location`、`public_salary_range`、`availability`。

复用「求职在谈卡」原结构；公司、简介、图片、匹配分、未提供技能等保留占位。真实职位、地点、公开薪资、待办状态正常呈现。

`phase` 只有 accepted/evaluating/evaluation_failed/refused/case_started，不等同于 S0–S3；不得从 `case_started` 猜测详细谈判阶段。显示对应受理/评估/失败/拒绝/已进入在谈状态，需要行动仅用 `needs_action`。列表显示稳定的当前结果内序号，帮助“第二个”等追问；序号不是全局排名。

### 4.3 在谈详情摘要

包含在谈列表项相同字段及 `agent_summary`：

- `public_evaluation`：decision、summary、coverage、evidence、next_action、completed_at、evaluation_id。
- `condition_confirmation`：case_id、stage_status、latest_summary、summaries；表示已保存的 S0 条件确认，不代表所有阶段的实时全貌。

摘要卡展示职位与当前已知状态、公开初评判断/摘要/证据/建议、最新条件确认摘要；需要时以卡内展开方式查看已有历次总结，遵循返回顺序。没有初评或条件确认时标明“暂无公开初评”/“暂无条件确认”，不生成分析结论。卡片提供清楚的“打开完整详情”入口。

## 5. 原生详情导航

- 岗位推荐项目使用可信 `job_id` 进入 `路径.职位详情(job_id)`。
- 在谈列表和详情摘要使用可信 `record_id` 进入 `路径.在谈详情(record_id)`；不要求先有 `case_id`，支持 pre-Case。
- 不从回复自然语言、公司名或模型生成 URL 解析跳转。岗位 `availability=unavailable` 的项目显示不可查看、禁用项目入口；目标页 404/权限变化沿用原生不可查看状态，不补假数据。
- 从聊天进入详情后，正常返回应回到聊天，并从持久化历史恢复消息。现有职位详情只识别市场来源的安全返回路径，应以窄范围助手来源支持完成返回链；不能冒充 `candidate-market` 或破坏深链/刷新安全兜底。
- 对话正文可以自然追问；保留此前讨论的“让 AI 解读”作为在谈项目之外的独立次级动作，与卡面“打开原生页”分开。点击后按普通发送锁发送可见的“请查看在谈记录 <record_id>（<真实职位名或职位未知>）的详细进展。”；ID 来源于已解码结果，正文不伪装成隐藏上下文，不能生成假的结构化 API 字段。

## 6. 查询能力与连续追问上下文

后端 MCP 两个列表工具只接受 `intention_id`、`cursor`、`limit`（默认 5，最大 10），详情工具只接受 `record_id`；每轮查询上限 6。没有公司/职位关键词、薪资、城市、技能、阶段或时间搜索参数。

岗位推荐读取已有结果，不重新计算推荐；无指定意向且存在多个有效意向时助手先澄清。在谈列表固定 active，不指定意向时跨意向读取。关键词追问是对已返回结果的实体定位，不承诺全库关键词过滤。

上下文要求：

1. 卡片真实字段、实体 ID、项目顺序和查询时间已通过同一后端工具结果交给 LLM，再作为快照返回前端。前端完整利用这些已有字段，不新增浏览器拼接 system prompt 或回传全部消息历史的协议。
2. “未知”、空图、中文格式化标签、序号等展示占位不作为新增业务事实传入模型；详情解读动作携带可信 ID 只帮助定位，服务端仍校验归属权限。
3. 用户可以按列表中真实职位、地点、薪资、序号等追问。助手从已知结果关联 `record_id`，调用详情工具产生新详情卡，不能只复述旧记忆当作查询结果。
4. 名称重复、指代不明或模型上下文已经裁剪时，应澄清或重新查询，不能猜 ID。前端可恢复完整可见历史，不代表模型无限保留历史。
5. 不增加前端关键词匹配器或引用关系图；不补齐后端卡片字段、不修改 Runtime 记忆策略。真实模型验收若发现工具结果/ID 未进入后续上下文，记录后端边界失败并停止宣称连续追问已打通，不以浏览器伪造上下文掩盖。

## 7. 前端责任与非目标

沿用现有数据源 facade、HTTP 客户端、身份隔离和纯展示边界。助手数据源负责协议/校验；求职 Backend 容器及专用 hook 负责历史、发送、幂等操作状态与轮询；固定结果组件负责按类型组合卡片和回调。不要为该页面增加通用全局聊天 store 或缓存基础设施。

求职端固定 AI 消息入口文案改为真实可聊天的说明。没有助手最近消息/未读 API，不伪造时间、摘要和未读；保留当前分类/搜索/固定顺序，不混入 P7 真人会话。

非目标：招聘端聊天、主动通知、日报/漏斗、流式输出、助手业务写入、全库自然语言搜索、岗位详情工具、多会话/删除/清空/取消、自动重跑、离线发件箱、完整历史注入、通用卡片框架和后端字段补齐。

后续只有在已运行卡面显示实际信息缺口、用户真实检索需求或连续追问失败证据出现时，再安排后端字段、查询过滤、上下文改进；不在本 Plan 顺带实现。

## 8. 验证与完成标准

规划阶段不跑产品测试来伪造实现证据。批准后的 Plan 精确绑定测试文件、命令、前置和权威验收责任：

1. 协议：四条路由、严格字段与状态、UTF-8 长度、空页/分页、三个卡片类型与不可见结果；正确区分合法 null 占位和非法缺键。
2. 生命周期：先读历史、发送/轮询锁、离页停止、返回恢复、身份/模式隔离、网络失败同键恢复、409 活动轮次恢复、失败显式重试同 message_id 不重复。
3. 展示：今日简报式回复内嵌真实卡片；三类结果原序和查询时间、缺失占位、空态、无业务假动作；原页面和 Mock 重用后保持原行为。
4. 导航：每类具体项目进入正确原生详情；pre-Case、不可查看、404、安全返回；“让 AI 解读”发送选中项可信 ID，不触发页面导航。
5. 浏览器 HTTP fixture：320px/390px 的长标题、缺图片、长回复、多卡片、输入固定与单一消息滚动，历史加载不跳动；不能以 fixture 证明真实模型理解。
6. 真实后端验收：普通聊天 → 岗位推荐 → 在谈列表 → 依据真实列表关键词/序号追问 → 获得对应 record_id 的详情卡 → 点击原生页并返回；另验证同名歧义与重新进入后的连续追问。证据须区分 UI/HTTP 与真实模型工具链。

真实环境验收使用仓库 `docs/dogfood/真实后端行为验收.md` 的环境与证据原则；现有 B/H 用例不自动覆盖新助手旅程，也不扩大为全量 dogfood。目标 URL、后端 checkout、测试账号安全来源、部署版本与实际助手能力在实施 final gate 中核实；缺失时如实记录阻塞，不能把本地合同测试当端到端通过。

## 9. 工作流批准与交付

本 Spec 是本任务唯一设计文档。用户审阅批准其提交后，再调用 writing-plans 编写一份零上下文 Plan；Plan 冻结本文 revision/blob、任务/编辑文件/协议/测试责任和宿主执行档位，自动进行 Claude 异构文档 review，结果就地记录于 Plan，再生成一个含 Claude Code/Codex 两节的执行提示词文件并校验。

实施由用户在新 session 启动，复用所选工作区；当前规划不修改产品代码、不部署、不运行正式集成验收或 push。
