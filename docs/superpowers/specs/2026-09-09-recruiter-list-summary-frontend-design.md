## 2. 方案与最小边界

采用现有请求 → 严格解码 → 页面映射 → 卡片的路径，增加显式摘要展开及对应展示。两个列表复用七字段摘要的类型、解码和展示格式化规则，是当前重复消费同一接口对象所需的小范围复用；不提取通用卡片框架，不合并 Mock/backend 状态源。

比较过的替代方案：逐卡请求简历/推荐详情会增加请求、引入不同披露上下文，且详情没有该摘要，故不采用；全面统一 Mock 与 backend 卡片组件会扩大交互和状态回归面，当前不需要。

本次范围：招聘推荐主列表和招聘在谈 open 列表的卡片展示；相应请求、DTO、解码、映射、测试以及共享消费者的兼容性调整。推荐列表现有的收藏筛选、分页、刷新、委托更新仍须正常工作。

非目标：候选人侧、匿名简历/Case 详情的新展示、历史卡和已筛卡的改版、个人亮点建议/编辑/确认入口、后端修改、Mock 数据改写、排序/匹配算法、搜索及筛选能力扩展、部署发布。

只有出现明确的其他页面展示需求、后端补充匹配分契约、或多张卡重复维护造成实际问题，才重新考虑上述延后能力；不新增配置开关、缓存基础设施或逐卡补查机制。

## 3. 请求与协议

以下两个请求使用单次 `include=candidate_summary`，保留现有岗位过滤、limit、cursor 等参数：

- `GET /api/v1/recruiter/jobs/{job_id}/candidate-recommendations`
- `GET /api/v1/recruiter/match-cases`

首载、翻页、刷新和轮询均保持相同展开语义。共用推荐集合被收藏/已筛入口消费时须保持旧功能；不为这些入口新增卡面行为。单条推荐详情、Case 详情、历史接口和候选人侧请求不添加本 include。

展开页每个 item 必须携带 `candidate_summary`，值为对象或显式 null；遗漏键是协议错误，不视作 null。默认响应没有该键。解码器按实际请求区分展开与默认合同，不能把新键全局变成可有可无，也不能破坏默认详情和历史响应。推荐页错误、P5 页协议错误沿用已有错误路径与重试；展示状态矩阵错误继续沿用逐行错误处理。

摘要为闭合对象，以下七个键全部必返：

| 字段 | 合同 |
| --- | --- |
| `gender` | `male / female / null` |
| `experience_years` | 非负整数或 null |
| `job_status` | `student / employed / unemployed / null` |
| `degree` | 展示字符串或 null |
| `latest_experience` | null 或闭合对象 `{company: string|null, title: string|null}`，两键必返 |
| `latest_education` | null 或闭合对象 `{institution: string|null, major: string|null}`，两键必返 |
| `personal_highlights` | 字符串数组，每条 1–24 个 Unicode 字符；空数组合法 |

不自行增加接口未声明的数组数量上限。不接受未知字段、错误类型或非法枚举。新增披露白名单只限上述展开对象；其他位置的性别、身份、出生、联系方式、薪资等原有边界不放宽。

## 4. 卡片展示契约

两张卡的摘要位置和空值规则一致，摘要事实只来自当前响应的 `candidate_summary`，不回填推荐顶层旧字段、匿名简历、其他 Case、历史工作或 Mock。

| 位置 | 展示 |
| --- | --- |
| 头行 | 性别图标 + 工作年限｜学历｜求职状态 |
| 工作信息行 | 公文包图标 + 最近工作公司 · 最近工作岗位 |
| 教育信息行 | 学帽图标 + 最近学校 · 专业 |
| 标签行 | `personal_highlights`，按响应顺序逐条显示 |

- `male → 男`、`female → 女`；复用 Mock 的 SVG、16px 默认尺寸、颜色令牌、图标间距和 `aria-label`。null 不渲染图标及占位壳。
- 年限 n>0 显示「n 年」，0 显示「不满 1 年」，null 隐藏该项；0 不是未知。学历直接使用服务端展示文案，不从教育数组第一项或最高学历重新推断。
- 求职状态与 Mock 口径一致：`employed → 在职看机会`、`unemployed → 离职可到岗`、`student → 在校`，null 隐藏。
- 公司和岗位均使用 `latest_experience`：title 就是用户指定替换方向描述的岗位。不从技能、招聘岗位或公司名推断 title。最近记录的选择已由服务端完成，前端不排序或回退旧记录。
- 对显示字符串 trim 后判空；有一个字段就只显示该字段，两个都有才加入「 · 」。两个都空时收起整行及图标。教育行同理。头行分隔符仅出现在实际存在的相邻文字项之间。
- 摘要整体为 null，或头行信息全部为空，显示中性「候选信息暂未披露」；不推断是候选不存在、无工作经验或授权失败。在谈 Case 保留可打开、阶段和待办能力。
- 个人亮点仅展示 API 已给出的数组；空数组收起整行，避免空容器。后端负责确认状态与披露过滤，前端不再次生成或自行分类。
- 推荐卡原 `highlights` 为批次匹配理由，本次卡片标签位改为个人亮点，不合并、不兜底。个人亮点不受 `structured_requirements_confirmed` 控制；卡面原「经验与学历尚未核对」匹配理由替代行及代理摘要段不再占据 Mock 中没有的行。旧字段及其他页面的匹配依据逻辑保留。
- 两张卡均不展示代号、真名、通用匿名头像、候选薪资关系或招聘岗位技能作为候选画像。
- 推荐卡保留真实 `match_score` 的匹配环及既有收藏、滑动淘汰、委托按钮和状态。
- 在谈接口无匹配分，不补造或回查匹配环。卡片主体替换为上述候选摘要，保留现有阶段、状态、待办/注意提示和 Case 跳转；招聘岗位名、城市薪资带及岗位技能不再充当候选信息行。列表筛选、计数、服务端顺序、轮询及错误提示沿用现有行为。

## 5. 状态与共享消费者边界

摘要随原列表 item 保存，不增加独立索引或持久化缓存。沿用现有 owner、role、岗位 scope 隔离和异步响应栅栏。成功刷新返回 null 或空数组时必须覆盖旧摘要，不能保留旧披露信息；刷新失败沿用现有错误与旧快照策略，不宣称已取得最新披露结果。

默认推荐详情无摘要，不能被扩展页的严格必返规则误拒绝；详情更新后若主列表所需摘要丢失，通过已有列表刷新机制重新取得，不能从旧详情拼装摘要。历史与候选侧共享的 P5 列表类型/映射须保持原路径可用；新增展示只由招聘 open 卡消费。明确区分未请求摘要与请求后返回 null。

## 7. 验收

1. 请求测试验证两个目标列表每页及刷新均携带一次 include；候选侧、详情、历史不携带。展开缺键、非法摘要失败，显式 null 合法，默认形状仍合法。
2. 映射测试验证男女、0 年、三种求职状态、所有空值组合、部分遮蔽、最近岗位原样呈现、亮点与旧 highlights 不混合；与旧字段冲突时只取摘要。
3. 两张屏幕卡验证头行、工作、教育、标签的顺序和图标；无姓名、无重复状态、无孤立分隔符；在谈无伪造匹配环；推荐匹配环和操作、在谈阶段与导航保留。
4. 回归共享消费者：匿名简历直达、已筛/收藏入口、P5 历史和候选侧仍能读取原响应；刷新从有摘要变为 null/空标签后旧内容消失，换主体/岗位不混用。
5. 实施时选择现有 Vitest 定向文件与 typecheck/lint；正式命令、最小测试集和最终责任在批准后的 Plan 冻结。本次仅文档，不提前运行产品测试。
6. 真实 backend+local 浏览器验收参照 `docs/dogfood/真实后端行为验收.md` 的环境与证据规则，验证招聘推荐、在谈真实请求与卡片位置，记录前后端 revision、截图及缺失数据。使用合成测试数据覆盖完整摘要；隐私 null、男女及 0 年边界由自动化样本补充，不用 Mock 页面冒充真实 API。未取得账号、匹配 Case 或已部署接口时明确记录未完成项，不声称视觉一致验收通过。

成功标准是实际 API 事实落到约定位置且原交互可用；API 合法空值导致的信息减少、在谈无匹配分属于明确的真实数据差异，不以填入演示内容消除。
