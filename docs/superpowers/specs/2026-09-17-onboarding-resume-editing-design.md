## 1. 目标与范围

解决用户本轮指出的五类问题：候选 onboarding 薪资与求职意向分离、招聘名片混入公司资料维护、招聘类别仍需逐级点开、简历编辑入口与保存返回混乱、求职意向管理中的状态不可编辑。

成功标准：

- 求职薪资与职位、城市、求职类型、办公方式在同一求职意向区域采集，学生与社招均无独立薪资页。
- 招聘名片 onboarding 不出现公司主页资料维护入口，所属公司选择仍可完成。
- 招聘职位类别打开后，当前一级下的二级分组及三级可选职位自动展示。
- 简历各区进入对应编辑上下文，有明确保存动作；成功后回原入口，继续返回不会重新进入刚退出的编辑页。
- 简历与求职意向管理均可编辑同一份真实求职状态，保存、刷新和重新进入一致。
- Mock Up 与 Backend 使用一致的目标流程和交互；相关测试及活动验收指南同步修改，受影响的验收责任均有实际结果。

这里的 Mock Up 指仓库现有 Mock 数据源模式，不另建静态原型项目。

## 2. 现状证据与方案取舍

| 问题 | 当前源码证据 | 后果 |
| --- | --- | --- |
| 薪资独立且两身份顺序不同 | `src/流程/onboarding配置.ts`、`src/屏幕/学生分流.tsx`：社招先进入 `/wizard?stage=salary`；学生在后段问薪资 | 同一求职意向被拆散，页面突兀 |

| 求职状态不可改 | `src/屏幕/求职意向管理.tsx`：Backend 点击回调为 undefined，Mock 只修改本地状态下标 | Backend 无入口，Mock 无真实跨页一致性 |
| 无效说明与多余入口 | `引导问答.tsx` 普通 textarea 旁写“长按段落”；`我的简历.tsx` 底部添加意向 | 操作提示不成立，简历与意向职责混杂 |

基本信息源码已有编辑模式“保存”按钮；用户观察到“没有保存”不能简单归因为完全没实现。实施时须验证实际来源标记、短屏和滚动可达性，不能只改按钮文案后宣称解决。

比较三种方案：

1. 只修标题和跳转：成本低，但无法解决独立薪资、聚合编辑与三级目录多点一次的问题，不采用。
2. **采用：调整现有页面组织，复用已有表单、薪资层与目录分组能力，明确日常编辑来源、分区和返回规则。** 不改后端 schema，不引入路由框架，覆盖当前全部问题。
3. 重建 onboarding 和全站表单/目录框架：会扩大到不相关页面、缓存和持久化，不采用。只有后续多个独立流程出现同类不可复用问题，才重新评估通用机制。

新增能力仅允许为当前入口服务的轻量分区定位、来源识别，以及必要的既有组件提取。共享正文用于 Mock/Backend 一致；目录查询复用已有逻辑是因为招聘与候选两个实际消费者需要同一三级目录展开。不得增加通用树引擎、全局编辑事务平台、配置中心或新依赖。

## 3. 候选 Onboarding

### 3.1 页面顺序与职责

目标总顺序：

```text
求职意向（现有完善资料首屏）
  → 基本信息 → 求职状态
  → 最高学历 → 毕业院校 → 专业 → 就读时间
  → 简历资料（工作/实习、教育核对、技能、证书、作品集、个人优势）
  → 补充偏好（现有排除项、屏蔽公司与自定义诉求）
  → 披露说明 → 添加头像 → 已完成主页
```

学生、社招采用上述同一主顺序。学生继续使用在读/预计毕业、实习经历措辞和现有条件字段；社招继续采集开始工作年。身份分流与上传 PDF 入口保留在现有首屏，不另造一个欢迎页。学生求职状态原来位于简历资料之后，本次移到基本信息之后，避免两身份的主顺序再次分叉。

不合并学历四个现有页面，不删除披露/头像步骤，不改变最终完成接口与完成条件。首屏保留现有标题及整体视觉，求职意向字段成为同一连续区域；不把“求职意向”标题变化当成必须重做整屏的理由。

### 3.2 薪资并入求职意向

- 在首屏现有职位、城市、类型、办公方式区域加入期望薪资选择行，跟随主要类型显示“月薪 · K”或“日薪 · 元/天”。
- 复用 `薪资区间层`；入口的左右布局、数值与单位、箭头、抽屉布局遵循发布岗位的现有样式。求职侧仍保留现有面议语义和合法档位，不机械复制招聘方限制或新增薪资字段。
- 打开抽屉只编辑临时值；确定后回填，取消、遮罩和 Escape 不改原值。未填写时显示占位，不把滚轮初始落点当成已填写。
- 首屏下一步要求用户确认合法薪资区间或明确面议；Backend 不预填虚构薪资。用户真实确认且被接受的当前轮解析建议可按现有预填合同回显，不能仅因 PDF 含薪资文本就直接建立已选答案。
- 切换类型导致月薪/日薪周期变化时清除旧区间并要求重新确认，不把 20K 解释成 20 元/天；同周期及重复点击同类型保留已填值。返回首屏修改后，下游必须读取新值。
- 学生、社招均取消独立薪资题。旧 `/wizard?stage=salary` 地址保留最小兼容：替换导航到首屏且保留可识别的现有草稿，不插入新历史项，不自动提交或跳过基础资料。没有有效草稿时走正常首屏。

### 3.3 简历资料与首次意向的提交边界

- 将个人优势 textarea 放入简历资料页，与工作、教育、技能等同属简历阶段；复用现有字数限制、真实预填建议及恢复语义，移除无实现的长按删除提示。空优势仍按原合同处理，不新增必填要求。
- 简历资料的继续动作等待必要简历写入成功；个人优势只有在自己的保存成功后才确认 summary 分区。其他分区保存成功而 summary 失败时保留已成功事实，留页显示失败并保留待重试内容，不能伪装成事务回滚或推进下一屏。
- 后段 `引导问答` 在 onboarding 中只负责补充偏好，不再补问已在首屏确认的职位、城市、薪资，也不再混入个人优势。
- 首次意向在补充偏好确认后调用现有 `保存首次意向`，使用最新职位/城市真实引用、类型、办公方式、薪资及偏好。不是在首屏、资料页或每次返回时新建意向。
- 现有单槽、请求身份、失败恢复、已完成首次意向追踪和刷新防重规则继续有效。重复点击、回退修改、超时与重试不得产生第二条首次意向；不新建平行持久化机制。
- 补充偏好写入失败留页，允许重试；成功后才进披露说明。硬性筛选与私人偏好映射保持现状，不能因页面叫“排除”便将私人原文改写为新的硬淘汰条件。
- 基本信息与状态原有空身份延迟写入边界保留：未拿到合法身份前不发非法 profile；调整学生状态页顺序时同时修正分区确认和出口，避免跳过教育。

### 3.4 预填、恢复及历史草稿

手填与 PDF 使用同一目标流程。当前轮建议只有在现有 ready/eligible/未确认等边界内应用；用户输入优先，已确认分区不能因新页面挂载而重放建议。个人优势迁移后继续区分用户内容、真实建议、可恢复建议，日常编辑不消费 onboarding 建议。

保持已有草稿数据结构和合法已填值。旧薪资答案只有周期匹配才恢复；旧页面地址转换不能清空姓名、目录引用、经历或待写入槽。确需数据兼容读取时只针对本次已有字段，不新增缓存版本迁移平台。

## 4. 招聘 Onboarding

### 4.1 名片与公司资料

onboarding 招聘名片去掉“公司主页资料”行，不只是点击后拒绝。保留招聘者姓名、职务、头像及所属公司选择/关系等完成名片所需内容；所属公司选择不是公司主页维护。

公司资料继续通过现有公司管理入口维护。本轮不改变日常名片页已经存在的公司入口、公司管理权限或后端组织接口；Mock onboarding 同样不得展示该维护行。展示组件根据调用方是否提供维护能力渲染，不能用数据源类型代替流程来源判断。

### 4.2 职位类别

- 全屏选择外壳及左右栏保持；左栏一级，右栏二级标题及其三级可选职位。打开默认一级或切换一级后自动获取该一级的分组与职位，无需再点二级。
- 二级分组是标题，不是假按钮。招聘侧保持单选，点合法职位即回填并关闭；不引入求职端的多选数量、选择确认步骤或新搜索入口。
- 使用现有 `期望职位目录钩子` 的三级分组能力，必要时提取为供两个真实页面复用的局部模块；不再维护一套独立的招聘下钻查询状态机。
- 仅加载当前一级，沿用已有自动加载顺序、分组分页、去重、版本换代、重试与迟到响应守卫，不预下载全目录。一个组失败不清空其他成功组，空组和失败必须可区分。
- Backend 只回填真实 selectable 目录项的 ID/名称，不靠标题或中文名称推断 ID；目录暂未加载到已选项时不清原值。同名不同 ID 不合并。
- Mock 使用现有本地合法目录数据，提供相同的标题/叶子点选结构；不得为凑三级伪造真实目录引用。
- 原有职位类别与岗位名联动、已发布岗位类别不可改、JD 用户修改保护继续有效。打开和取消后，原步骤、岗位名、JD、城市与薪资均不丢失。

## 5. 日常简历编辑

### 5.1 入口与编辑范围

| 点击位置 | 目标行为 |
| --- | --- |
| 姓名、工作年限 | 同一“编辑基本信息”页，显示姓名/性别/出生年月/开始工作年份；不再姓名行内即时提交 |
| 当前状态 | 共用求职状态编辑，见 §6 |
| 最高学历、教育区添加 | 教育分区列表，允许添加/选择条目 |
| 已有工作/实习或教育条目 | 直接打开该条编辑器，以稳定条目身份定位 |
| 工作/实习区添加 | 直接打开空条目编辑器 |
| 专业技能 | 技能分区编辑 |
| 已有证书、证书区添加 | 对应证书编辑或新增 |
| 个人优势 | 独立“编辑个人优势”，复用 textarea 与保存逻辑 |

复用 `工作经历.tsx` 中已有工作/教育/技能/证书编辑器；onboarding 可以继续使用聚合资料页，日常入口不再显示整份聚合页。分区和条目定位属于页面局部参数，不建立新的业务实体或重复存储模型。条目不存在时显示已不可用并允许回列表，不回退去编辑第一条或偷偷新建。

基本信息标题按模式区分，日常编辑不得写“创建在线简历”。工作年限仍从开始工作年派生，不新增独立年限字段；学生不强填工作起始年。

### 5.2 保存、取消与返回

- 日常编辑统一为局部草稿，明确的“保存”才提交。顶部返回/取消、浏览器后退离开编辑不提交；未保存内容不能提前污染简历首页或 Mock 的已保存态。
- 已有条目直接编辑时，保存一次即完成必要业务写入并回原简历页，不再要求返回聚合页点第二次总保存。教育等分区列表可继续进入子编辑器，保存子条目后回该分区，最终退出返回原简历；每级只有明确的一份保存责任。
- 公司/学校/专业/行业等全屏选择子视图仍只回填父草稿，保持已有“选定关闭、取消零回填”边界，不在选目录时提前保存整条经历。
- 保存期间禁止重复提交，成功才退出；失败留页、保留输入、可重试，不发假成功提示。部分写入沿现有数据源事实处理，不新增前端伪原子事务。
- 从“我 → 我的简历 → 编辑”进入，保存/取消后回**原来的**简历页，再返回到“我”；同样验证连续编辑两次后返回。不能用 push 新简历，也不能仅 replace 当前编辑页而留下两张简历首页。
- 正常来源使用已有历史返回能力；直接深链、刷新后无法证明来路时，用明确来源的安全替换落点，不盲退外站。来源只允许本次简历/意向管理等既定站内入口，不引入任意 return URL。
- 对选择器同页子视图的浏览器后退维持既有规则，不为本轮新增虚拟 history 层或全站清栈。日常保存不能调用 onboarding 的清栈进主壳。
- 空身份基本信息需状态页收口时，保留其尚未保存的基本草稿；状态保存成功后一起回原简历，不产生中间编辑页返回循环；取消整条编辑链不把该草稿当成已保存内容。
- 日常编辑继续显式绕过 onboarding 建档草稿、分区确认、首次意向和完成接口；刷新时来源参数不得丢失导致误入注册旅程。

保存和返回必须在现有移动视口、短屏及键盘收起后可达。以实际页面交互检查“没有保存按钮”的问题，不只做静态文案断言。

### 5.3 清理

删除个人优势的“删除一行：长按段落”，保留普通文本编辑和字数提示。删除简历底部“还可以再加一个求职意向”；添加和管理意向继续由现有求职意向管理承担，不删多意向能力。

## 6. 求职状态的唯一归属

后端当前 `BFF简历资料.status` 为 `student | employed | unemployed | ''`；合法写入为前三项。状态属于候选 profile，全账号一份，不是每条意向各一份。

- 日常编辑显示“在校／在职／离职”三个真实选项，当前值正确预选，空值不假选。保存用既有简历 profile 写入及权威回读；取消不改。
- “我的简历 → 当前状态”和“求职意向管理 → 求职状态”进入同一状态编辑。前者返回简历，后者返回意向管理；各处展示更新后的同一值。
- 删除意向管理 Mock 的本地轮转假状态，改用同一份候选状态与同一编辑交互；刷新遵循现有 Mock 持久化规则。
- 日常状态不把“看好机会／随便看看／保密求职中／随时到岗”等额外语义包装成独立持久化选项，也不将仅有 employed 的事实自动翻译为保密求职。
- onboarding 既有到岗选项及其已支持的草稿映射不在本轮扩展成新的 API 字段；其页面处于明确的 onboarding 模式，不能被日常入口误用。未来确需独立的求职积极度/到岗时间时，须先有批准的产品语义与后端字段再设计。
- 单纯切换身份不清空教育/经历，也不自动改变已有意向类型、薪资周期或数量。相关信息缺失由现有完整度展示处理，不回退已完成 onboarding。

## 7. Mock Up 与旧合同

两数据源必须同顺序、同编辑入口、同保存/取消方式、同目录展开形态。数据和持久化实现仍分别走各自适配层，Backend 错误不得回退 Mock 种子；不得修改 Mock 让它看似可用而保留 Backend 旧流程。
