# 招聘前端 P0 契约校准与并行接缝设计

**日期：** 2026-08-25

**状态：** 已获用户批准，待实施计划

**范围：** `agxp-a2a-recruiting-web` 的已批准招聘阶段语义校准，以及行为保持的数据源、状态与异步操作接缝整理

**前端基线：** `origin/main@c982dda3770b0b85a99432fe04662106a59aea44`

**跨域契约基线：** 后端仓库 commit `1d553a4e3` 的
`docs/superpowers/specs/2026-08-25-recruitment-product-contract-foundation-design.md`

## 1. 背景与结论

当前前端已经完成 PM 视觉和主要交互，并接入认证、目录、在线简历、求职意向和招聘方岗位等第一批真实
BFF 能力。其余招聘产品域仍主要由 Mock 数据与 `应用状态.tsx` 的本地 reducer 驱动。

P0 需要同时解决两个已经有现实证据的问题：

1. 前端仍混有“匿名 PDF”“S3 才释放候选人身份”等已经被 PM/用户推翻的旧口径。
2. 未来 P1–P7 都会继续修改 2452 行的 `应用状态.tsx`、506 行的 `HTTP招聘数据源.ts` 及根数据源契约，
   多 worktree 会争用相同文件并混淆业务所有权。

满足当前需求的最小方案是：

- 不改 CSS、页面结构、视觉效果或主导航流程；
- 只校准已经明确批准的 S1/S3 披露语义；
- 保留单一 React Context、Provider、`use应用状态()` 和页面调用接口；
- 将已有业务逻辑按 owner 移到域文件，根文件只保留组合与机械路由；
- 不引入新状态库、Query 框架、schema generator 或尚无实现的空模块。

## 2. 已批准产品契约

### 2.1 简历对象

- 在线简历是数据库字段组合，用于推荐和 S0 匿名筛选。
- PDF 是候选人上传的完整正式简历，不是在线简历的另一种渲染格式。
- 不建设匿名 PDF，不自动擦除或重排 PDF。
- PDF 多模态解析由后续 P2 实现；P0 前端不伪造解析进度、解析结果或重试。

### 2.2 阶段语义

- S0 匿名初筛：招聘方只能看到不含姓名、联系方式的在线简历投影。
- S1 递交简历：候选人提交 PDF 原件；招聘方可看到 PDF 中的姓名和联系方式，候选匿名在此结束。
- S2 需要协调：双方 Agent 处理完整 JD 与完整简历筛选后剩余的差异。
- S3 意向确认：双方独立确认是否进入真人沟通/约面，不再承担身份或联系方式交换。

### 2.3 发起授权

- 候选人主动点击“让 AI 代理去谈”时，为该 Case 预授权 S0 通过后的 S1 原件递交。
- 公司主动发起时，S0 通过后必须由候选人接受简历邀请，才允许进入 S1。
- 前端 P0 不新增候选人主动委托确认层，也不在市场卡增加说明行。
- 授权告知复用现有披露说明和用户协议；主动委托按钮及点击流程保持不变。
- 公司发起后的真实简历邀请状态和动作由 P5 实现，P0 不用本地占位状态冒充后端能力。

## 3. 用户可见语义校准

### 3.1 只修改现有文字，不新增布局

P0 修改已有文字槽位：

- 披露说明的“递交简历”行明确：初筛通过后递交 PDF 原件，并向招聘方显示姓名和联系方式。
- 用户协议把候选人匿名终点从“意向确认”改为“S1 简历原件成功递交”。
- “我的简历”附件区删除“自动隐去联系方式”描述，改为原件披露事实。
- S1 Mock 对话、附件说明和注释删除“匿名版”“已隐去真名与联系方式”。
- S3 双端提示删除“双方互相披露姓名与联系方式”，改为双方最终确认并进入真人沟通/约面。
- 帮助、设置、披露偏好及其他明确声称“S3 才露名”的现有文案同步校准。

P0 不添加新标题、卡片、说明行、弹层、按钮或 CSS。若既有文字槽无法承载准确口径，应在实施时缩短文案，
不能修改页面结构解决。

### 3.2 身份显示规则

身份可见性不能再用 `阶段 === '意向确认'` 推导。招聘方视图只消费投影中的真实身份事实：

- `真名` 为空：继续显示代号和匿名样式；
- `真名` 非空：显示真实姓名；
- 联系方式只在对应投影明确存在时显示；
- 阶段标签只表达流程位置，不兼任披露权限。

P0 复用现有 `真名: string | null` 等页面字段，不额外增加与它重复的 `身份已披露` 布尔值。后续 BFF DTO
必须由服务端权限投影决定是否返回真实字段；页面不得下载 owner DTO 后自行删字段。

### 3.3 Mock 数据校准

Mock 必须表达业务事实而不是通过阶段名称猜测：

- S0 或 S1 尚未提交原件的候选人保持 `真名=null`；
- 已存在 S1 原件附件/递交成功事实的候选人填入真名和原件视图；
- S2/S3 Case 因为已经完成 S1，同样保留已披露身份；
- 招聘方打开 S1 附件看到原件，不再传匿名代号生成打码预览；
- S3 reducer 的现有演示能力可以保留，但不再承担首次写入真名的唯一职责。

P0 不补完整邀请、招聘方筛选或双方确认状态机；这些由 P5 以服务端权威状态替换。

## 4. 前端代码接缝方案

### 4.1 保留稳定外观接口

以下接口保持稳定：

```text
应用状态提供者
use应用状态()
状态
动作
应用操作
招聘数据源选择
创建招聘数据源(...)
```

屏幕仍从 `use应用状态()` 读取 `{ 状态, 派发, 操作, 后端 }`，不要求全站迁移到多个 Context 或新的 query
hook。Mock/Backend 的配置选择和 Backend 失败不回退 Mock 的规则保持不变。

### 4.2 状态与 reducer 按已有业务拆分

P0 只为当前已经存在真实 state/action/reducer 分支的业务创建域文件。建议所有权为：

| 域文件 | 移入的已有逻辑 | 后续 owner |
|---|---|---|
| 候选资料与意向 | 在线简历、本地附件名、onboarding 资料、求职意向 | P2 |
| 组织与岗位 | 公司资料、招聘方身份资料、岗位本地状态 | P1 |
| 隐私与设置 | 屏蔽、披露档、隐私/设置开关 | P3/P8，按动作归属分组 |
| 发现与推荐 | 市场委托、不感兴趣、候选收藏/淘汰/补给推荐 | P4 |
| MatchCase | 双端在谈、阶段决策、归档、叮嘱归属 | P5 |
| Agent 规则 | 双端规则 CRUD、开关和规则草案 | P6 |
| 消息 | 双端未读和读消息 | P7 |

域文件导出自己的 action 子联合和 reducer 函数。根 `动作` 是这些子联合与少量 UI 导航 action 的联合；
根 `归约` 仍用显式 `switch` 把 action 路由到对应域 reducer。不得改成字符串注册表、动态插件或自动发现。

显式 root switch 会保留少量机械共享行，但业务实现不再集中在根文件。未来该机械入口由 integration owner
组合，收益足以覆盖一次行为保持搬移，又不需要改变全站 dispatch shape。

### 4.3 异步操作拆分

`应用状态提供者` 当前同时拥有会话、简历、意向、岗位和初始化水合等异步流程。P0 将已有操作按现有真实
域移动到操作工厂文件，每个工厂接收所需的最小依赖，例如数据源、`dispatch`、当前服务端快照读取函数。

根 Provider 只负责：

- 选择 Mock/Backend；
- 创建 root reducer；
- 组合各域已有操作；
- 执行既有初始化顺序；
- 暴露兼容的 `应用操作`。

P0 不改变加载、错误、stale response guard、revision 或水合时序。跨域保存仍由现有调用者明确编排，不新增
通用 command bus、effect middleware 或 transaction abstraction。

### 4.4 HTTP 数据源拆分

`HTTP招聘数据源` 的现有方法按真实后端 owner 拆为小接口：

- Session/principal；
- Catalog；
- Resume 与 resume files；
- Candidate intention；
- Recruiter jobs；
- 已存在的 evaluation/promotion/MatchCase/S1 方法。

根 `HTTP招聘数据源` 是这些接口的交集，`创建HTTP招聘数据源` 只组合现有实现。P0 不给 P1–P7 新增空方法，
也不改变 URL、body、DTO 校验、错误映射或幂等行为。

现有 `招聘数据源选择` 判别联合保持不变。Mock 演示读取和真实 HTTP 域继续明确分开；Backend 请求失败绝不
回退演示数据。

## 5. 拆分顺序与行为保持

为降低一次性回归，实施按以下顺序：

1. 先用测试冻结当前 reducer、数据源工厂和 Provider 的可观察行为。
2. 校准 S1/S3 文字与 Mock 身份/PDF 投影，给这些批准差异增加针对性测试。
3. 拆 HTTP 数据源接口与现有实现，根 facade 保持签名。
4. 拆 Provider 已有异步操作，保持公开 `应用操作`。
5. 按域搬移 reducer 分支，根 action 和 `use应用状态()` 保持兼容。
6. 删除搬移后确认无调用的旧代码，不保留双实现。

每一步单独运行相关测试。机械搬移与语义校准不能混在同一个无法解释的巨大 diff 中。

## 6. 错误处理与初始化

- 每个域继续使用现有 `后端状态` 的加载/错误/失败语义；P0 不设计新的通用异步状态机。
- 初始化仍遵守当前依赖顺序，不让目录预取重新进入已改为分页选择器的路径。
- stale response、AbortSignal、revision conflict 和 session invalidation 行为必须保持。
- 域操作只捕获它真正能够映射的错误；未知错误回到现有统一错误投影，不能返回 Mock 或伪造成功。
- 语义校准后的 Mock 是演示模式事实，不是 Backend 失败兜底。

## 7. 测试策略

### 7.1 语义校准测试

- S0 和未完成原件递交的 S1 候选仍显示代号。
- S1 原件成功递交后，招聘方列表、详情和在线简历入口显示真实姓名。
- 招聘方 S1 附件打开原件视图，包含原件身份/联系方式，不走匿名代号分支。
- S3 提示不再包含“交换/披露姓名和联系方式”。
- 披露说明和用户协议明确 S1 的不可逆披露后果。
- “让 AI 代理去谈”仍一次点击执行原委托动作，不出现新确认层。

### 7.2 接缝回归测试

- 每组 reducer action 在搬移前后的 state 结果一致，明确批准的披露语义除外。
- `创建招聘数据源` 在 Mock/Backend 配置下返回与当前相同的判别联合。
- 拆分后的 HTTP facade 对现有方法保持签名、请求和错误透传。
- Provider 初始化、stale guard、保存成功水合和失败保留行为不变。
- 现有页面无需改为新 Context/hook 即可通过 TypeScript 检查。

### 7.3 验证命令

实施至少运行：

```bash
npm run typecheck
npm test
git diff --check
```

若仓库已有对应 lint/build 命令，Plan 根据 `package.json` 和当前 CI 再列出准确入口，不凭空增加新工具。
实现差异不应包含 `.css` / `.module.css` 修改；若出现必须停止并重新取得用户批准。

## 8. 非目标

- 不实现 PDF 上传、多模态解析、解析状态或重试 UI。
- 不接入新的发现、盯盘、推荐、MatchCase、规则、消息或通知 API。
- 不实现公司发起后的真实简历邀请、招聘方 S1 筛选、S2 协调或双方 S3 服务端状态。
- 不新增确认弹层、常驻授权说明、页面、导航、设计 token 或 CSS。
- 不把单一 Context 改成多 Context，不引入 Redux、Zustand、TanStack Query 等框架。
- 不建立通用 domain plugin、动态 reducer registry、command bus 或跨仓库代码生成。
- 不借拆分机会重命名全站中文领域词、重写所有 Mock 或清理无关 UI。

## 9. 风险与控制

- **语义与机械搬移混淆**：先用针对性提交完成 S1/S3 校准，再逐层搬移；测试明确哪些结果允许变化。
- **循环依赖**：域 reducer 对 root 状态只使用 type-only import，运行时依赖方向保持“根组合 → 域实现”。若
  需要共享纯类型，移动到无 React 依赖的类型文件，不建立互相调用的域模块。
- **跨域 action**：保留显式根编排；不得让一个域 reducer 偷改另一个 owner 的私有状态。确有当前用例时，
  由根操作顺序派发已有域 action。
- **过度拆分**：只为现有逻辑创建文件；单个一次性 helper 留在 owner 文件内，不建设通用 utilities 层。
- **视觉漂移**：代码审阅检查无 CSS 文件，页面 DOM 只允许现有文字节点内容变化，不新增结构。
- **前后端漂移**：本 Spec 绑定后端契约 commit `1d553a4e3`；后续计划若改变披露时点或阶段职责，必须先
  重新批准跨域 Spec。

## 10. 验收标准

P0 前端实现完成时：

1. 所有用户可见匿名 PDF、S3 才释放候选人身份的冲突口径已清除。
2. S1 成功后的招聘方 Mock 投影显示 PDF 原件、真实姓名和联系方式。
3. 页面布局、CSS、导航和主动委托点击流程没有变化。
4. 单一 Context 和现有页面 API 保持，业务逻辑已按 owner 从共享热点移出。
5. 不存在仅为未来计划创建的空模块、空方法或新框架。
6. TypeScript 检查、现有测试、新增针对性测试和 diff 检查通过。

## 11. 后续所有权

P0 完成后：

- P1 只扩展组织/岗位域数据源、操作和状态文件；
- P2 只扩展候选资料/PDF 域；
- P3 只扩展隐私策略和匿名投影消费；
- P4 只扩展发现推荐域；
- P5 只扩展 MatchCase 域；
- P6 只扩展 Agent 规则域；
- P7 只扩展消息域。

共享 Context composition、route table 和根数据源 facade 只接受机械装配，由 rolling integration owner 组合。
任何后续 Plan 若需要修改另一个域的业务内部，必须先证明当前契约不足并修改 Spec，而不是现场跨域实现。
