## 1. 目标与已确认边界

将 `test:agent-browser:backend-local` 和 `test:agent-browser:hosted-agent` 两个真实业务验收入口替换为 Agent 使用 `agent-browser` 执行的 dogfood。Agent 根据当前页面选择操作路径、观察异步结果，并依据关键业务节点和证据判断结论，降低固定点击、文案和等待时序对测试的影响。

用户已确认：

1. 环境启动、测试数据准备和清理由 Agent 按文档调用现有工具，不新增前端环境编排脚本。
2. 被测业务写入通过 UI 完成；以页面结果和刷新复读为主要证据，必要时允许同权限的只读 API 核验。
3. 保留原有九类行为目标，改写成目标、前置条件、关键验证点和证据要求。
4. **删除 `test:agent-browser:unit`、`test:agent-browser:shell` 及失去实际消费者的专属实现。** 与两个业务入口一起退役旧前端整栈测试体系；两份合成 PDF 迁移后供 dogfood 继续使用。
5. 保留其他 Playwright、Vitest、Mock 视觉回归及其现有职责。

本设计的“容错”是 Agent 能重新观察、重新定位和选择符合用户行为的路径，不是放宽业务结果、忽略问题或无限重试。当前没有对新旧方式做失败率对比，本次不宣称已证明 dogfood 与旧套件检测能力等价。

## 3. 方案选择与最小实现

文档组织考虑两种方案：

- 扩充 `docs/dogfood/backend-local-onboarding.md`：复用原入口，但会把全新账号注册与存量资源/Hosted 场景合为一份长文，前置数据和覆盖范围容易混淆。
- 新增独立真实后端 dogfood 指南，和 onboarding 文档相互链接：沿用已有文档、工具和证据目录，单独表达本次替换的业务范围。

采用第二种。最小交付是四个旧 npm 入口及专属测试代码的移除、一份行为指南、一份 Markdown 报告模板、现有合成材料迁移，以及说明和构建引用清理。环境调用、浏览器操作和结论均由当前执行 Agent 完成。

不新增 npm 占位入口、LLM CLI wrapper、自定义 skill、浏览器步骤 DSL、通用断言或报告 schema。普通 npm 进程无法自主执行 Agent 推理，不用“打印说明后 exit 0”的命令冒充测试完成。

## 4. 执行入口与 Agent 职责

指南提供可直接交给 Agent 的任务提示词，必需输入为实际目标 URL、后端工作区/测试环境位置、测试账号与登录材料的安全来源。范围可选全部、基础行为、Hosted 或单个 Case ID；未选或尚未执行的项记录为 NOT_RUN。

本轮范围是 backend/local 测试环境。使用与后端 Cookie/CORS 配置一致的 Origin；迁移基线使用 `http://localhost:5173`，不得未经核对自动换成 `127.0.0.1` 或其他端口。前端必须显式 `VITE_DATA_SOURCE=backend`、`VITE_BACKEND_ENV=local`。

执行者先加载当前安装版本的 `agent-browser skills get core` 和 `agent-browser skills get dogfood`，使用独立命名会话分别承载候选和招聘账号。新指南把通用 dogfood 的探索方式具体化为本项目的覆盖责任，不以“找到若干个问题”代替完成所选 Case。

浏览器工作循环：

1. 通过 snapshot 和截图理解当前页面、实体与状态。
2. 根据当前 refs 或可访问语义选择用户操作；跳转、重渲染和弹层变化后重新观察。
3. 根据实际结果决定下一步，允许重新定位、滚动、关闭遮挡弹层或正常导航恢复。
4. 到关键节点验证结果、刷新/重开后的持久化和角色可见性，并立即记录证据。

不固定控件 refs、完整提示语、CSS module 名、像素坐标或整段点击序列。Agent 不把页面判断外包给旧旅程，也不现场写另一套自动点击大脚本。

准备阶段允许阅读工具和环境文档；页面 dogfood 按用户视角进行，不能用源码里的状态推测代替浏览器观察。问题取证后的代码归因另行进行。

## 5. 环境、数据与恢复合同

### 5.1 环境归属

由 Agent 按当前后端文档调用已有 `apps/recruitment/scripts/dev-local.sh`。需要 acceptance profile 的场景核对 `health --acceptance`，必要时使用当前支持的 `prepare --acceptance`、`up --acceptance`。复用栈不由本轮关闭，不强切换其他人的普通栈。

前端使用独占或已经确认配置正确的服务。Agent 记录自己启动的 PID、两个会话名和栈归属；只结束自己创建的资源，不按端口批量杀进程、不 `close --all`、不删除持久卷。

### 5.2 测试资源

基础行为需要候选简历/意向/可用附件槽位，以及招聘名片、可编辑公司介绍、在招和归档基准岗位。通过现有 fixture 工具准备，或使用已按等价要求准备的专用账号；在变更前记录初始值和对象归属。

Hosted 的 happy、p4、p5、p6 必须由真实后端现有 acceptance 能力准备；不得通过网络 route mock、前端状态注入或修改业务代码制造结果。缺少某场景时明确 BLOCKED。

基线文档已记录部分后端版本没有 `baseline` scene。此时不能借用会要求 Hosted 图的 happy 做普通 CRUD；没有等价的安全基准准备与清理能力，就把受影响基础 Case 记 BLOCKED，不把本次范围扩展为实现后端 fixture。

### 5.3 回执生命周期

复用 `apps/recruitment/scripts/browser-fixture.sh` 的 `converge --scene`、`verify --ledger`、`cleanup --ledger`。当前前端基线已按 receipt v2 接线：

- 一轮场景使用一个唯一 `BROWSER_FIXTURE_RUN_ID`，该轮 converge、verify、cleanup 共用它；下一轮使用新 ID。
- 后端生成的准确 receipt 路径用于该轮后续操作；前端自写报告或 journal 不能冒充 receipt。
- verify 成功才开始消费场景。一次只消费一个 fixture 生命周期；收尾完成前不并发改写同一组测试资源。
- cleanup 成功后 receipt 退休，不再对它 verify、重新 converge 或手工删除。需要复测时创建新一轮。
- 遵守实际登录限流，重复获取 OTP 或重复调用 fixture 不能成为无界重试手段。

旧 `docs/AgentBrowser真实后端验收.md` 的“每次算子调用换新 ID”与规划基线的 v2 运行器不一致，新指南必须写清上述生命周期，不能在删除旧代码时丢失这一环境合同。实际后端版本若与上述合同不匹配，先记录版本差异和阻塞，不臆造协议；当前 Spec 不声称已检查某个正在运行的后端。

converge 或业务过程失败也要检查已产生的 receipt/对象并尝试现有清理入口。对于自行准备的账号，按事前记录的对象和原值通过 UI 恢复。不能确认归属时不按名称猜测删除。

### 5.4 写入与只读核验

被测业务写入全部走 UI，包括规则确认、附件上传、委托和 Case 推进。环境准备与收尾清理是明确例外，只使用现有工具的允许范围，不能在测到失败后补写业务结果让 Case 通过。

只读 API 核验使用当前角色权限与当前测试实体，核对业务字段、实体归属、创建/删除和持久化事实。不能用管理员全量数据冒充用户权限验证，不能用 API 成功掩盖页面未显示结果。只读失败导致关键事实无法证明时，记录未验证节点，不能猜 PASS。

## 6. 行为覆盖

Case ID 是范围选择和报告追溯标识，不是新的场景 DSL。每条组合 Case 要逐节点记录，不能只完成其中一个动作就判整条通过。

### 6.1 基础行为

| ID / 原旅程 | 用户目标 | 必须验证的关键结果 |
| --- | --- | --- |
| B01 / candidate-load | 候选登录，查看简历、求职意向和披露偏好 | 基准姓名/摘要、意向职位/城市/薪资及数量、披露选中档位正确；各页刷新仍成立；无 Mock 数据或对方私有资料混入 |
| B02 / candidate-crud | 改名并还原；意向新建、调薪编辑、删除；披露改档并还原；附件上传、替换、删除 | 保存后与刷新后值一致；意向删除后目标消失且基准仍在；披露与姓名恢复；附件上传/替换按当前 UI 完成授权，目标附件可回读、替换后槽位仍正确，删除后刷新仍消失。解析终态独立记录，不以本 Case 宣称解析质量已验证 |
| B03 / recruiter-load | 查看招聘名片、公司介绍和岗位管理 | 姓名/职务/公司/介绍与基准一致；在招/归档岗位位于正确分组；刷新恢复；无候选私有摘要混入 |
| B04 / recruiter-crud | 修改并还原职务/介绍；发布岗位、编辑、停止招聘、重开、删除 | 创建目标岗位；刷新重开后描述等本次编辑字段正确；停止后归档、重开后在招；删除后目标消失且基准岗位保留；原职务/介绍恢复 |
| B05 / session-isolation | 双账号分别读取资料，只退出候选端 | 两个独立会话各自显示授权数据；候选退出生效；招聘端刷新仍登录且资料正确 |

删除断言先确认对应列表已加载，再检查目标不存在。写入响应未知时先回读是否已生效，不能盲目重试制造重复资源。合成附件迁移后引用 `docs/dogfood/resources/简历-v1.pdf`、`简历-v2.pdf`；使用 fixture 时临时对象名称遵守其当前清理合同。

### 6.2 Hosted 行为

| ID / scene | 用户目标 | 必须验证的关键结果 |
| --- | --- | --- |
| H01 / happy | 规则解释并确认 → PDF 解析 → 候选委托 → Case → 候选补充事实 → 招聘初筛 → 双方协调与确认 → 深链复读 | 有效规则确实增加且内容对应；PDF 成功解析；委托产生 Case；双方查看同一业务 Case；招聘初筛实际成功；通过公开允许的动作到达双方确认完成，重开两端详情仍成立，过期推进动作消失 |
| H02 / p4 | 在已准备的委托失败场景中发起委托，再刷新 | AI 不可用被准确解释，本次没有创建 Case，没有假进展入口；刷新后事实一致。必要时只读回读补充零 Case 证据 |
| H03 / p5 | 成功开案和候选推进后，招聘 Agent 进入 attention，双端复读 | Case 存在但未继续；招聘端显示需注意，两端原因一致且安全；不把 readiness 校验伪装成 Agent retry；刷新后不变成假成功 |
| H04 / p6 | 提交规则后解释失败，刷新并关闭失败卡 | 失败说明明确，无确认成功入口、无新增有效规则；关闭失败卡可恢复原草稿，刷新后仍无新增规则 |

H01 的迁移终点保留为双方确认完成及创建会话阶段，不因此宣称已经验证 P7 私聊发送/接收。可以接受后端在重新进入时已合法推进到更后的已创建会话状态，但必须有对应实体和双方确认的证据，不能只靠匹配旧提示语。

保留 H01 清理后再次运行成功的责任：完整验收中至少两次独立 H01，前轮清理完成后才准备后轮。H02/H03/H04 各执行一次；不再要求跨 Case 的固定五轮 Shell 调用顺序，但场景内部依赖和资源生命周期必须成立。部分范围不自动补跑未选择的 Hosted 场景。

### 6.3 视觉观察

保留七个观察位置：候选简历/意向/披露加载、候选改名并上传附件后、招聘名片/公司介绍加载、新岗位发布后的列表。Agent 检查可读性、遮挡、溢出和状态/数据一致性，记录实际视口与截图。

新 dogfood 不使用旧 PNG 差异率或浏览器版本匹配来判定通过；旧整栈专属 PNG、比较器和 unit 测试删除，独立的 Mock 视觉回归保持原有职责。此次不增加逐帧闪屏、像素等价或跨浏览器覆盖声明。

## 7. 判定与证据

| 状态 | 含义 |
| --- | --- |
| PASS | 该 Case 所有必需节点均有证据，结果与刷新/重开核验成立 |
| FAIL | 已观察到业务、数据、交互或隔离违反目标；关联问题证据 |
| BLOCKED | 环境、账号、故障场景或工具使关键目标无法验证；写具体边界与已完成节点 |
| NOT_RUN | 未选择或尚未执行；不能用缺少问题记录代替 PASS |

同一 Case 已有明确 FAIL，后续被环境阻塞也不抹掉失败，额外记录未完成节点。页面缺陷绕行后仍保留 FAIL；仅工具 ref 失效且重新观察后正常完成，可记录工具恢复而不判产品失败。

异步等待有界：优先使用当前测试环境的公开约定；没有约定时，Agent 在启动任务前记录本轮各类节点的观察预算。预算是执行限制，不是新增产品 SLA。到期记录时间、最后状态、诊断与原因；无法确认是产品还是环境时写“原因待定位”，不得无限延长至通过。

关键节点保留截图或页面快照摘要；写入需有操作后及刷新证据。只读核验记录 method/path、必要的脱敏字段和结论。问题立即记入报告：预期、实际、复现步骤、影响、证据、再次复现情况和绕行；偶发问题保留首次证据，不因无法稳定复现就删除记录。静态问题截图即可，交互/时序问题在可复现时补视频和步骤截图。

产物使用现有忽略目录 `dogfood-output/<run-id>/`，主报告为 Markdown，配 `screenshots/`、按需 `videos/` 等证据。模板包含环境/commit、范围、每个 Case 及节点状态、H01 各次执行、视觉观察、问题、恢复和最终结论；初始状态为 NOT_RUN。

不把 OTP、Cookie、Authorization 或完整认证状态放入报告，不在登录材料输入期间录像；包含私密业务数据的原始证据只留本地忽略目录。可长期保存的摘要沿用 `docs/runs/` 脱敏约定。

完整业务通过需九类 Case 全部 PASS、H01 重复运行责任完成且清理成功。部分通过必须写所选范围；有 FAIL 不报全通过，有 BLOCKED/NOT_RUN 不报全覆盖。清理单列完成/未完成/不涉及；清理未完成时，即使业务节点通过也不能宣称整轮通过。

## 8. 失败与中断后的收尾

报告从执行开始就持续更新本轮服务归属、场景、receipt 的本地路径及已创建对象，保证中断后可以恢复。下一次 Agent 先核对真实服务/回执状态，再继续或清理，不默认重开同一场景。

正常、失败和中断路径都需要清理义务：按本轮 receipt 使用现有工具回收其拥有的资源，或按事前记录通过 UI 还原自行准备的数据。后端工具内部合法的 acceptance 清理属于收尾，不算产品业务成功证据。

清理失败保留准确回执位置、对象归属和恢复步骤；依赖相同资源的后续测试停止。不能猜测删除目标、强行推进业务终态或把失败 receipt 当成下一轮准备成功。

Agent 进程终止时没有新增自动 trap/watchdog。本次最小方案依靠持续记录与下一次恢复；不声称具备进程退出自动清理的能力。

## 9. 非目标与重新考虑条件

- 不把新 dogfood 再包装成假 Agent 单测、固定点击合同测试或备用旧 runner；只有出现具体、可验证的独立风险与实际消费者时，再评估所需测试或工具。
- 不建设 Agent 调度服务、自定义 skill、无人值守 CI、自动评分或统一 JSON schema。实际出现重复启动成本、报告消费需求或漏项证据时，再讨论最小支持。
- 不实现后端 baseline、故障注入或业务功能修复；缺失按阻塞记录，由对应 owner 处理。
- 不替代原 HTTP fixture 契约、单元测试、Mock 视觉回归，也不扩大到完整 P7、全路由、性能或生产环境验收。
- 不建设会话崩溃后的自动资源回收；若实际出现多次无法恢复的残留或干扰其他任务，再评估后端已有 lease/recovery 是否足够。
- 不提前保证 Agent 测试更稳定或同等检错；后续依据真实运行中的完成率、误报、漏项、证据质量和耗时决定是否调整。

## 10. 验证与完成标准

### 10.1 实施产物验证

1. `package.json` 恰好移除第 2 节四个入口；其他测试 scripts 与共享包依赖保持不变。
2. 旧专属目录和 `tsconfig.e2e.json` 已删除，根引用及活动文档无悬空依赖；两份迁移 PDF 与原文件字节一致；其他功能/Mock 视觉测试、脚本、配置与资源仍可用。
3. 新指南具备环境、数据、Agent 操作、九类行为、只读核验、证据、清理及启动提示词；独立新会话不需要本次规划聊天即可执行。
4. README 和 Agent 共享规则能发现新入口；旧指南明确四个入口退役，当前指南无旧执行命令和错误的 run ID 规则。
5. 报告模板包含全部 Case、组合节点、H01 重复运行、清理及未覆盖状态；文件链接与现有资源路径可用。

实施阶段通过文档/配置校验核对删除范围、路径、覆盖和 PDF 内容；运行现有构建/类型检查以发现已删除 tsconfig 或 import 的残留，定向运行仍保留的 Mock 视觉/报告与 UI 回归编排单测，确认共享工具链可用。三个现有 Playwright 入口使用 `--list` 核对用例发现与选择；这不等价于浏览器执行通过。已经删除的 `unit`/`shell` 不再成为验证命令，也不新增测试来只证明删除动作本身。未改动产品代码时不机械重跑所有浏览器套件，具体最小命令与最终责任在批准后的 Plan 中冻结。

### 10.2 新工作方式的真实演练

实施阶段在可用环境中至少演练 B02、H01 和 H04，以覆盖 CRUD/刷新、Hosted 成功、公开失败/草稿恢复与清理；H01 需要清理后再执行的证据才能声称重复运行已验证。其他场景若未执行，报告明确标记，不把小范围演练写成九类完整验收。

缺少真实环境或对应 fixture 时，区分“迁移产物检查通过”和“dogfood 实际执行未完成”，保留 BLOCKED 与后续责任，不把其他单测 PASS 或历史 unit/shell PASS 用作替代证据。完整真实验收仍按第 6–7 节覆盖全部范围。

本 Spec 阶段只检查文档完整性、矛盾、占位内容、边界与源码引用，不执行后端场景，也不开始修改测试入口。
