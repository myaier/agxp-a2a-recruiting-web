# 短信登录角色水合与薪资滚轮无障碍修复设计

## 背景

Backend 模式下，已有账号完成交互式短信登录后，前端只完成登录尝试和主体读取，未执行与冷启动、切身份相同的角色支持域水合。根应用随后根据 `last_used_role` 进入角色主壳，候选简历、active intentions、隐私、附件和 Agent 规则仍是 Backend 空种子；招聘方也可能进入缺少组织、岗位和规则数据的空壳。保持 cookie 刷新后，冷启动恢复链会执行完整水合，因此数据立即恢复，证明 BFF 合同与权威数据不是本次故障来源。

薪资要求弹层复用的双滚轮只在滚动停止 90ms 后计算选中项。listbox 不可聚焦，没有键盘处理或活动项语义，option 也不能直接点击选择。数字滚轮和年月滚轮复制了同一交互模式，存在相同的可访问性缺口。

本次修复不修改 BFF 合同、意向 DTO、revision/ETag、`If-Match`、权威重读或 Backend 失败策略，也不在角色页面增加补偿 GET。

## 已整合的前序基线

2. `fix-recruiter-onboarding-frontend`（worktree：`unarmed-wolverine`）最终实现锚点 `59cd1ee6dfa3a0ba43ec30b3b1d33cc28e8a23e8`；`68935537` 随后整合上述候选分支，主线校准锚点为 `37b0a459e53b48dfb3e204a647c805334d0bff06`。

本设计以该合并后接口为准，消费而不重做以下前序能力：

- candidate-only、subject-scoped onboarding 草稿及其恢复写屏障；会话层继续只发既有 `清后端草稿` 生命周期信号，不新增第二套存储。
- recruiter 的 `招聘方档案水合阶段`、`招聘方组织水合`、完整组织链错误传播和显式恢复操作。
- recruiter 根路由 guard：档案缺失进入招聘名片，档案成功进入招聘主壳，组织水合失败进入恢复面。
- 前序分支创建的 `src/应用.test.tsx` 及扩展后的 Provider/session 测试桩。

若执行前 `origin/main` 再次移动，必须重新 rebase 并复核这些接口和语义；不能把本基线的代码片段直接覆盖到更新后的主线。

## 目标

1. 交互式短信登录只有在上次使用角色的支持域水合结算且会话仍有效后，才向 UI 提交已登录状态。
2. candidate、recruiter 和无上次角色三条路径与冷启动语义一致。
3. 401、跨账号、同账号重登、StrictMode 和迟到响应不能污染或登出更新会话。
4. Backend 页面不显示 Mock 姓名或 Mock 求职状态。
5. 薪资双滚轮支持键盘、鼠标直接点选和现有触摸/滚动输入，并保持提交规则不变。
6. 三种滚轮共用无样式的可访问交互行为，视觉和数据范围保持不变。

## 非目标

- 不修改短信登录、主体、简历、意向、隐私、附件、组织、岗位或 Agent 规则的 BFF 接口。
- 不给“我的简历”“求职意向管理”等页面添加挂载读取。
- 不增加本地意向缓存，不回退或播种 Mock Backend 数据。
- 不修改意向创建 201、更新 `If-Match`、revision/ETag 或成功后的权威 GET。
- 不重构为新的公开会话状态机。
- 不合并三个滚轮的视觉 DOM 或 CSS，不改变档位、步长、单位和上下限归一规则。
- 不在本次增加 PageUp/PageDown。
- 不改造微信外部重定向流程；OAuth 回跳后的会话仍由冷启动恢复链处理。

## 方案选择

采用“现有公共角色水合 + 原子登录提交 + 无样式滚轮 Hook”的方案。

没有采用仅在 `完成手机登录` 后补一次水合、只修薪资组件的最小补丁，因为它会保留候选简历/意向及部分 401 扫描的迟到响应缺口，也会让三个滚轮继续分叉。没有引入完整会话状态机和统一视觉滚轮组件，因为这会扩大公开状态接口、样式回归面和本次缺陷修复范围。

## ISSUE-001：会话架构与数据流

### 交互式短信登录时序

`完成手机登录` 保持现有公开签名，内部按以下顺序执行：

```text
完成验证码登录
→ 读取主体
→ 执行现有跨 subject 清理
→ 写入 subject fence，并递增会话代际
→ 按 last_used_role 调用公共 水合角色数据（非交互失败策略）
→ 确认 subject、generation 仍属于本轮
→ 提交 主体 + 已登录=true
→ 根应用按角色导航
```

水合期间保持 `已登录=false`。支持域可以按既有规则独立提交到状态，但根路由不能进入角色主壳；因此这里的“原子”是登录态和路由可见性的原子提交，不是把所有支持域改成全成全败事务。

`水合角色数据` 仍是唯一角色水合入口：

- candidate：简历、active intentions、隐私、附件简历库和候选 Agent 规则。
- recruiter：招聘方档案、企业关系、当前企业公开资料、owner jobs 和招聘方 Agent 规则。
- `last_used_role=null`：不读取角色域，水合立即结算，最终允许根应用进入身份选择页。

登录场景以 `交互=false` 调用公共水合，复用冷启动的非交互失败策略。非 401 单域失败只提示该域；成功兄弟域照常提交，登录最终成功。这样不会把“简历服务暂不可用”等支持域错误包装成验证码失败。

### 最终提交守卫

登录水合开始前写入 `主体标识引用.current`，递增 `会话代际.current` 并捕获本轮 generation。水合返回后只有同时满足以下条件才能提交 `{ 主体, 已登录: true }`：

- 水合未报告会话失效；
- `主体标识引用.current === 主体.subject_id`；
- `会话代际.current === 本轮generation`。

任一条件不满足时直接结束，不恢复登录态。登出、401 清理、另一轮登录或主体切换都能让旧轮次失效。

冷启动和切身份继续调用相同的 `水合角色数据`。本次不复制资源读取到页面，也不引入新的公开 Provider 阶段。

交互登录最终提交主体后，前序 candidate 草稿持久化 effect 可以按新 subject/role 恢复草稿。登录编排不直接读写该存储；跨主体和角色转移继续保持前序 `清后端草稿` 先于主体失效的动作顺序。

## ISSUE-001：失败、清理与迟到响应

### 统一 fence

公共水合对整轮结果统一应用 subject + generation fence：

- candidate 的简历、意向、隐私、附件及规则结果，只有本轮有效时才能提交、提示或触发 401 清理。
- recruiter 的组织、岗位及规则结果采用同一条件；岗位成功提交必须同时校验 subject 和 generation。
- 迟到的成功、非 401 失败、401 和错误提示全部丢弃，不能影响更新会话。

当前实现只为隐私、附件、规则和组织的部分步骤提供完整 fence；简历、意向、岗位提交及 session 层的部分 401 扫描需要补齐。本次只统一既有水合边界，不改变各资源的数据映射或请求数量。

### 401 与非 401

`水合角色数据` 的依赖扩展为携带统一账号清理所需的 P4、P7 和 P8 运行时引用。当前轮次的任一水合 401 继续调用 `清账号状态`，并复用前序 recruiter 空状态工厂，复位：

- 登录主体和支持域快照；
- 简历、意向、岗位、隐私、附件和 Agent 规则页面状态；
- Backend 草稿、组织状态和目录缓存；
- recruiter 档案/组织水合阶段及错误；
- P4、P7、P8 内存快照及运行时引用。

Provider 现有主体/角色 effect 继续负责其已拥有的 P5 等派生会话边界，不在本次新增第二套清理机制。

非 401 单域失败保持 `Promise.allSettled` 的独立提交语义。短信登录完成接口失败仍抛给登录页；`读取主体` 失败沿用现有行为：401 全清，非 401 保持未登录并显示统一错误提示。为避免多个 settled 域重复提示，公共水合只返回一次 session-expired 结果：交互式短信登录与切身份操作把它转成标准 `invalid_session` 错误，分别由登录页和身份页显示一次既有文案“登录已失效，请重新登录”并阻止后续导航；冷启动恢复 401 改为静默落回未登录页，以登录页本身作为恢复信号。

冷启动水合被另一轮会话 supersede 时只禁止旧轮提交 `主体/已登录`，仍须把 Provider 的 `初始化` 从“进行中”收口到“完成”。否则新短信会话即使已经权威水合并提交，根应用仍会永久停在路由加载页。

### 同主体与跨主体

同 subject 重登保留现有草稿口径，但建立新的会话 generation；旧请求不能覆盖新会话。跨 subject 登录先执行现有旧账号清理，再建立新主体 fence。现有目录 stale 401、P4/P7/P8 清理和导出恢复句柄语义必须保持。

## ISSUE-001：导航所有权

删除 `src/屏幕/登录.tsx` 短信 Backend 分支在 `完成手机登录` resolve 后的 `跳转(路径.选身份)`。登录页只提交认证并呈现认证错误，不再决定 Backend 角色落点。Mock 短信登录继续即时进入身份选择页。

原子水合延长了“进入”操作的等待时间。Backend 请求进行中时按钮禁用并显示“正在进入…”，同时保留既有 ref 防重入；结算后恢复“进入”。该状态只提供操作反馈，不提前改变登录态或导航所有权，Mock 行为不变。

`src/应用.tsx` 是 Backend 登录后的唯一导航所有者。当前设计扩展前序 recruiter guard，不重建或简化它。仅当以下条件同时成立时决定落点：

- Backend 初始化已完成；
- 当前路径仍是登录页；
- `已登录=true`；
- 主体已经随最终提交可见。

落点规则：

- `candidate` → 候选主壳；
- `recruiter` 且组织水合成功、档案缺失 → 招聘名片注册流；
- `recruiter` 且组织水合成功、档案成功 → 招聘方主壳；
- `recruiter` 且组织水合失败 → 保持前序真实错误、重试和切换身份恢复面；
- `null` → 身份选择页。

水合中、操作失败、401 或旧轮次失效时始终保持登录页。

## ISSUE-001：Backend 与 Mock 展示隔离

`src/屏幕/我的.tsx` 根据数据源选择展示值：

- Mock：保留“沈亦舟”和“在职 · 保密求职中”。
- Backend 姓名为空：显示“未填写姓名”。
- Backend `后端状态.简历快照 === null`：状态显示“资料暂不可用”。
- Backend 简历成功水合且 `简历快照.profile.status === ''`：状态显示“未填写求职状态”，不能使用映射层为了注册流表单而提供的“在职”默认值。
- Backend 简历成功水合且服务端 status 非空：只显示对应权威映射值，如“在职”“离职”或“在校”，不拼接 Mock 文案。
- Backend 权威姓名为空时头像不显示“未填写姓名”的首字“未”；Mock 头像首字行为保持不变。

页面不发补偿请求；它只消费登录编排已经提交的状态。

## ISSUE-002：共享可访问滚轮行为

### 无样式 Hook

新增 `src/组件/可访问滚轮.ts`，导出无样式 Hook。Hook 接受选项、当前值、设值回调和行高，返回滚轮引用、滚动与键盘处理器、活动 option ID 以及 option 点击属性。三个现有组件保留各自 DOM、类名、单位和高亮层：

- `src/组件/内嵌双滚轮.tsx`
- `src/组件/数字滚轮层.tsx`
- `src/组件/年月滚轮层.tsx`

### 交互合同

每个滚轮列统一实现：

- listbox 设置 `tabIndex={0}`；双列可以分别通过 Tab 聚焦。
- 每个 option 使用 Hook 生成的稳定 ID、`role="option"` 和 `aria-selected`。
- listbox 使用 `aria-activedescendant` 指向当前选中 option。
- ArrowUp/ArrowDown 移动一档；Home/End 选择首尾；到边界夹紧且不循环。
- 点击任意 option 立即选中，聚焦该 listbox，并把目标档滚到中间。
- 外部值变化时同步 `scrollTop`。
- 触摸、滚轮和拖动继续使用 scroll-snap；停止 90ms 后按 `scrollTop / 行高` 取最近档。

不采用 roving `tabIndex`，避免与 `aria-activedescendant` 混用。程序性滚动记录待忽略目标并清理已有防抖，防止其生成的 `scroll` 事件再次回写相同值；如果下一次滚动位置不是待忽略目标，则按真实用户滚动处理。

每列独立创建 Hook 实例，引用、活动项和防抖计时互不共享。年月滚轮的动态月份列表仍由现有边界 effect 夹紧，Hook 只响应最终选项和值。

### 薪资规则保持

薪资档位仍为 3–100K、步长 1。编辑中继续允许上限小于下限；点击“确定”时使用 `Math.max(上限值, 下限值)` 抬高最终上限。重新打开弹层从保存值初始化。键盘、点击和滚动都写入相同 React state，因此 `aria-selected`、视觉高亮和确认值保持一致。

## 真实 Backend 验收

以 `VITE_DATA_SOURCE=backend VITE_BACKEND_ENV=local npm run dev` 启动前端，完成“退出登录 → 短信登录 → 我的 → 我的简历 → 求职意向 → 编辑保存 → 退出重登”闭环。

短信登录已有 candidate 后至少观察：

```text
POST /api/v1/auth/login-attempts/:id/complete  200
GET  /api/v1/me                                 200
GET  /api/v1/me/resume                          200
GET  /api/v1/me/intentions?status=active        200
```

其余候选支持域按公共水合合同各执行一次。进入求职意向页不补发 intentions GET。已有一条 active intention 的账号首次进入即显示 `1/5`；“我的”不出现 Mock 姓名或状态。

薪资弹层分别验证键盘、直接点击和触摸/滚动输入。保存时 PATCH 继续携带当前 revision 对应的 `If-Match`，后续权威 GET 与页面一致；重新打开和刷新保持新薪资。

若本地 BFF、短信验证码或测试账号不可用，验收结果必须明确记录为环境阻塞，不能使用 Mock 流程代替真实 Backend 结论。

## 完成标准

- 交互短信登录与冷启动恢复得到一致的角色支持域状态。
- 登录态提交前角色水合已结算，角色资源无重复读取。
- current-session 401 全清，stale-session 成败不影响新会话。
- candidate、recruiter 和无上次角色路径均有自动回归测试。
- Backend 不泄漏 Mock 姓名或 Mock 求职状态。
- 三类滚轮共享可访问行为；薪资双列可 Tab、键盘、点击和滚动选择。
- `aria-selected`、视觉高亮和最终提交值一致。
- focused tests、全量测试、typecheck、lint、build 通过，并完成或如实记录真实 Backend 验收。
