## 2. 方案比较与推荐

1. **推荐：沿现有边界修复。** 推荐前提只保留 owner 水合和用人企业坐标；预览直接使用已有草稿；“我”页消费已有身份；城市共用现有钩子，默认目录按四个国家码分页，热门用经过接口验证的小型明确配置。新增状态仅服务图片失败和四路分页，不增加全局机制。
2. **运行时逐国家解析海外精选。** 从七个海外国家的分页目录筛出十城，可取得即时目录记录，但需要额外请求与解析完成状态，热门展示依赖远端排序，找不到目标时还需继续翻页。已有稳定快照 ID，不采用此复杂度。
3. **新建后端精选/批量接口或重做城市目录系统。** 长期可集中维护精选与版本，但超出纯前端范围；当前需求无须新增服务、缓存框架或通用能力层。

## 3. 推荐页契约

### 3.1 可用条件

保留在招 owner job、job_id、角色、主体与 scope 的既有核验。组织前提变为：

| Owner Job 状态 | 结果 | 请求与展示 |
| --- | --- | --- |
| 未水合 | unknown | 不注册错误 scope，不发推荐请求，显示“正在加载岗位信息…” |
| 已水合且 hiring_organization_ref 去空白后非空 | ready | 不读取 verification_status 决定可用性；verified、unverified 均正常注册、读取、刷新、补给和轮询 |
| 已水合但 ref 缺失、空串或纯空白 | blocked / missing_ref | 不发推荐请求，显示“这个岗位尚未选择用人企业” |

“有效 ref”在前端此处沿用既有非空权威坐标定义，不增加查询企业是否存在或认证状态的请求；合法性最终仍由既有 DTO/后端契约负责。

缺 ref 的引导只保留一个明确动作“编辑岗位并选择用人企业”，走已有 `路径.编辑岗位(当前活跃岗位)`。删除该页面所有要求认证的横幅、空态、去认证及加入企业替代 CTA。编辑页真实企业读取失败继续显示其既有错误，不在本任务修复或隐藏。

### 3.2 旧后端兼容

保留 HTTP 客户端与推荐数据源对精确 `organization_verification_required` 响应的严格解码，包括原来的路由、状态码和报文形状限制，不扩大错误白名单。

删除 refresh 操作中仅为旧认证前提服务的 Owner Jobs 重读/二次分类分支，以及页面对此错误的静默吞错。旧后端实际拒绝时通过已有失败快照与提示路径展示“推荐请求被服务端拒绝，请稍后重试”，保留原始错误码供诊断，不宣称成功，不产生认证 CTA，也不因本地 unverified 而禁用正常重试。不把这个已知旧错误转换成新的 invalid_response。

保留真实 invalid_response 的已有异常处理；不放宽其他 P4 闭合错误、推荐 ID、岗位坐标、幂等键、单飞、竞态栅栏、401、切岗/换主体/离屏等保护。删除的只是旧认证专用恢复，通用 `运行范围刷新` 的写入与重读流程不改。

## 4. 招聘名片姓名预览

- Backend 未实名、公开名可编辑时，预览姓名直接取当前本地 `公开名`；清空也反映空草稿，不回退旧服务端名字。保存时继续沿用现有 trim、必填校验和请求。
- 存在权威 verifiedName 时，预览和只读字段均使用它；不让公开名草稿覆盖实名。保持现有“verifiedName 是否为 null”可编辑判断，不从组织认证推断个人实名。
- onboarding 和普通编辑共用当前组件，仅导航 state 决定现有保存后跳转。
- 保持水合同步、revision、头像上传、错误保留与保存逻辑。Mock 维持已有状态归属，覆盖入口一致性，不复制第三套表单。

## 5. “我”页面招聘者入口

- Backend 主标题：非空 verifiedName → 非空 publicName → “完善招聘名片”。是否有企业信息不参与名字判定。
- 有 avatarUrl 时渲染图片，alt 为“招聘者头像”；无图或加载失败显示招聘者有效姓名的首个字符。姓名也缺失时用中性“人”，不使用公司首字或“完善招聘名片”的首字。
- 图片失败状态限定于当前主体和当前 URL；URL 更新或切主体后允许新图加载，旧图片迟到的 error 不污染新图。不增加全局头像缓存或重新请求档案。
- 姓名下方显示非空职务、既有来源的任职企业；原个人验证与任职关系标签保留。公司缺失不伪造、不为补名字重新请求公司。
- Mock 读取现有 `企业认证.姓名/职务/公司` 和 `招聘头像`，具有同样的姓名与头像展示语义，继续零 Backend 请求。
- 整行点击仍进入招聘名片。仅增加圆形图片的 object-fit 等必要样式，不重排统计与其他入口。

## 6. 城市浏览、精选与搜索

### 6.1 默认目录

保持现有平铺布局、城市按钮、已选区、选择上限、历史与保存交互。顺序：现有定位/历史区域 → 国内热门城市 → 海外热门城市 → 中国大陆省级分组 → 台湾省 → 香港特别行政区 → 澳门特别行政区。

Backend 默认目录分别请求 CN、TW、HK、MO，均不带 q。首次四路各读取一页；后续通过当前控件为仍有游标的分支追加一页，不预加载全球或一次拉完目录。每次追加必须携带该分支的国家码与自身游标。完整目录指能够继续分页访问后端全部 active、selectable 记录，不承诺首页展示全部城市。

中国大陆按返回的 admin1_code/admin1_name 分组；直辖市各自成组，不恢复旧的四直辖市合并配置。TW/HK/MO 按 country_code 强制使用用户指定的三个名称，优先于任何返回的英文 country_name 或细分 admin1_name。CN 缺少可用行政区信息时不编造省份，该记录仍可由真实搜索找到。标题排序稳定：大陆省级分组按 admin1_code，三个指定区域置后。

默认长列表只接收 CN/TW/HK/MO，搜索结果和海外热门永不写入它。正常接口不应越过所请求国家；若出现跨国返回，视为该分支的目录响应异常，沿既有错误提示处理，不默默混入或冒充完整成功。

四分支分别持有游标、版本、加载/失败状态；失败保留其他成功分支，用户可重试失败分支的原页，不把失败写成“没有更多”。沿用现有轻提示与加载交互。换版本时按原规则强制刷新并重开受影响查询，避免跨版本拼接；保留去重、单飞与迟到响应保护。不同分支的独立版本无需强行拉齐。

### 6.3 搜索、Mock 与三个消费者

**中文覆盖的核实与限制（用户截图追问后补充）：** 当前后端快照的 337 条大陆可选记录均有汉字 display_name；台湾 96 条、香港 326 条、澳门 8 条可选记录的 display_name 均无汉字。页面直接显示 display_name，接口没有独立中文展示字段或 locale 查询参数。抽查 Taipei、Kinshasa、Istanbul、Lagos、Ho Chi Minh City 等记录，location_names 快照中也未找到中文别名，不能假定中文搜索必然可用。以上是所审后端快照的事实，尚未核验运行实例。

**用户已确认的展示规则：** 本轮不修改后端，也不要求补齐中文目录或中文搜索别名。精选不含港澳台；默认目录的三个标题仍固定为“台湾省”“香港特别行政区”“澳门特别行政区”，组内条目直接显示 API 的 display_name，接受英文或拼音，不翻译、不音译。其他全球搜索结果同样允许原名。港澳台条目英文是本次明确接受的行为，不列为后端依赖、未解决缺陷或验收阻塞。三个区域仍可在默认目录、搜索以及既有已选/历史区域正常出现和选择；精选排除不影响这些路径。

全球搜索仍调用 `查询Location({ q, cursor })`，不加默认四国限制；保留防抖、全球分页、去重、换词栅栏和目录版本重同步。清空搜索立即恢复默认四国目录状态；海外搜索选择仍按 ID 保存，历史/已选不受默认浏览过滤影响。

规则集中在 `src/屏幕/城市查询钩子.ts` 与共用城市数据配置；`选工作城市.tsx`、`引导问答.tsx`、`选择城市.tsx` 仅适配数据与事件。`备选城市选择正文` 增加第二个热门区域的展示输入，不引入数据源逻辑或另建通用城市框架。

向导城市题现在没有分页接线。本设计明确允许在现有城市列表尾复用“加载更多”按钮，分别接当前默认目录/全球搜索的游标与加载状态，不改共享滚动容器基础设施。这是满足三入口一致与完整目录的必要补充，并覆盖旧 dogfood 文档“只有首页”的限制说明。

Mock 默认目录拆开三个指定区域，删除海外长分组；Mock 全球搜索保留海外模拟记录，不能因为默认目录删除而失去搜索结果。热门列表与 Backend 共用产品顺序和中文名称，均不含港澳台。港澳台模拟目录条目采用与后端样本一致的英文/拼音展示名，三个组标题保持中文；既有已选和历史值不因展示调整而迁移或丢失。Mock 保留模拟数据量与既有存储格式，覆盖大陆各省级分组和三个指定区域，不复制后端数十万全球记录；生产完整性由 Backend 的实际可选目录及分页保证。
