# 聊天身份、在线简历与推荐匹配解释设计

日期：2026-09-17。Spec revision：1。状态：产品范围已确认，正式 Spec 待用户审阅批准。规划流程：development-workflow；批准本文件后才编写单份实施 Plan，再执行异构文档 review 和新会话执行提示词交付。本轮不实现业务代码、不清库、不部署。

本文是本任务唯一设计文档，包含执行规划需要的调研结论，不依赖聊天记录或独立 handoff。前端路径相对当前前端仓库，标注“后端”的路径相对 agxp-monorepo 仓库；执行工作区由用户指定，不绑定规划机器目录。

## 1. 目标与最小范围

覆盖原六项展示问题及后续确认的企业屏蔽语义、聊天消息头像修复：双端消息列表显示真实对方资料；招聘聊天打开结构化在线简历；说明个人亮点为何为空；招聘推荐详情用真实评分依据展示匹配状态；候选卡按披露结果显示最近公司 · 职位。Mock 与 Backend 共用展示组件，数据来源独立。

用户确认：

- 匹配分析解释当前后端六维评分，不改成 Mock 的 JD 逐项评分算法；资料不足为“未核对”，不是“不匹配”。
- 在线简历先统一版式；手机、邮箱缺失时显示占位符。
- 招聘聊天列表和详情顶部副标题为“投递企业 · 投递岗位”，代招取实际用人企业；求职聊天保持“招聘者所属公司 · 招聘者职务”。
- 真人消息两侧头像均为 32×32px 圆形，优先照片，缺图/失败用各自姓名首字，缺姓名用“·”。
- “对这家公司隐藏我的信息”按企业访问屏蔽执行，与公司字段披露分开。
- 现有测试数据可重建，不做旧 hidden 或旧推荐解释的数据迁移、回填与兼容。
- 本 session 只调研和准备执行 Spec/Plan，不实施业务代码。

最小方案：复用 P7 既有授权查询补充紧凑对方资料；复用 P5 已有在线简历；在推荐批次生成时保存有限六维评分结果，详情读取时返回；不引入身份缓存、第二套推荐引擎、模型调用或自动补标签。

新增一个紧凑评分快照有现实必要性：当前存储只有总分/正向原因，无法区分不匹配和未知，且当前资料可能已偏离批次。浏览器不能可靠重建用户要求的解释。新快照只含六维状态/得分，不存原始薪资、简历全文或对方私人意向。

非目标：改变评分权重/排名/候选全集、对 JD 做语义匹配、加入学历计分、改变投递建会话的业务准入、开放联系方式、放宽本设计之外的公司/亮点披露规则、重做个人信息编辑、回填历史推荐、自动重解析旧 PDF、改变求职端职位详情既有核对卡。只有独立产品需求或实际数据故障证据才重开这些范围。

## 2. 已确认样本与剩余归因

用户提供的两条推荐列表响应均为 `candidate_summary.latest_experience.company=null`、`personal_highlights=[]`。第一条详情同样为空，三段经历公司均 null，包括两段已结束经历。前端未丢弃这两个字段。

- 样本 A：50 分，方向/经验/地点三个原因，岗位要求已确认；25+15+10=50。
- 样本 B：55 分，在样本 A 原因基础上多办公方式；25+15+10+5=55。
- 两条薪资关系均 unknown；不能画成薪资不匹配。
- 未返回技能命中原因；仅凭响应不能区别岗位无关键词和技能零命中。
- 样本 A 的工作意向包含 remote，响应中办公方式未命中；需要批次时岗位模式才能给出可靠的双方证据，不能用当前模式冒充。

后续 owner 响应显示三段经历公司均非空且全部 hidden=true，现任公司和教育均设为 resume_submission，一份附件已解析成功。用户进一步提供该精确 file/version/parse 的 owner 建议响应，suggestions=[]：该解析在招聘方隐私过滤前就没有可用标签。当前隐私配置又是一个独立披露限制；不能仅归因为隐私。

空结果的内部原因仍可能是模型输出空、条目全部被校验丢弃或旧解析缺附属结果。现有公共 API 不能区分，需该环境按 parse_id 做最小服务端只读诊断，不自动重解析。用户明确可能存在同名测试账号，跨接口只按 ID/授权关系关联；已有响应尚不能把这份 owner/parse 绑定到样本 A 或 B，不能用姓名、状态或自述相似度代替关联。只保留结论及必要定位坐标，不存储真实简历全文或联系方式。不得把尚未证实的“改生成器”“改隐私默认值”写成必做修复。

最新补充已定位样本 A 的公司缺失：用户找到正确账号后，privacy.current_employer=anonymous 已保存，最近经历 company 非空但 hidden=true；固定推荐 ID `rec_b30a56639dd6fd44cbe026dafff9b9b1` 的职位摘要同步变为其刚修改的“产品运营 - 抖音增长部 2”，公司仍 null。说明摘要已读取更新，经历 hidden 独立遮蔽公司。响应 batch_id 与此前相同，不将此证据描述为已生成新批次。此前另一账号的 PDF 空建议不适用于此账号；本账号工作来源标签会被 hidden 过滤，纯教育来源是否有生成结果仍未核实。

## 3. P7 对方资料合同

### 3.1 公共字段

在双端会话列表/会话详情的 available `context` 内新增必返 `counterpart`，其值为 null 或闭合四键对象：

```ts
type ConversationCounterpart = {
  name: string | null;
  avatar_url: string | null;
  company_name: string | null;
  title: string | null;
};
```

保留现有 primary_label、secondary_label、job_ref、resume_ref 的语义；不把旧代号字段改成姓名，以免无关消费者暗中改变含义。context unavailable 时沿用既有不带 context 的合同，不返回身份。counterpart=null 表示资料投影不可用；四键对象内 null 表示该字段未提供/不可披露。

### 3.2 权威来源与失败边界

招聘查看者：

- `name/avatar_url` 复用同 Case `CaseCandidateIdentities` 的实际披露判断；anonymous 时均 null，disclosed 可部分缺失。头像仍走已授权 Case content URL。
- `company_name` 为同 Case 冻结职位展示资料中的用人企业名称（DisplayJob.organization.display_name），`title` 为该会话冻结岗位名称。招聘查看者此字段表示投递企业，不表示候选现任公司；代招必须取用人企业，不能替换为猎头/发布企业。缺失时返回 null，不用其他岗位或企业补值；不能用候选最近职位替代投递岗位。

求职查看者：

- 姓名、头像、职务沿用同 Case 冻结 `DisplayJob.PublisherProfile` 的公开投影语义，与现有会话详情一致。旧 Case 缺冻结发布人时给 null，不拿其他发布人补值。
- 公司沿用岗位当前可信 `publisher_organization_ref` 指向的公开 active 公司 display_name；不是 `hiring_organization_ref`，不是未核验 claim。当前岗位/发布公司不可用时只置公司 null，不影响其余可读字段。
- BFF 复用现有招聘者头像媒体路径投影；不能原样传内部 URL、对象存储地址或随意拼接头像路径。

此投影加入既有 Recruitment 会话授权链；不新增接口、轮询、持久化身份表或浏览器每行 P5/Job/Org 请求。后端允许用既有读取方法补公开字段；只共享已有授权逻辑，不复制另一份身份资格判断。

内部 Recruitment → BFF 的 counterpart 使用闭合四键 `candidate_identity`、`publisher_profile`、`company_name`、`title`：前两键复用既有 CaseCandidateIdentity 和 PublicRecruiterProfile（内部 avatar_media_id）类型，均可 null；招聘查看者只有 candidate_identity，求职查看者只有 publisher_profile。BFF 复用现有身份/发布人严格解码与头像投影，再组装上述公共四键；内部两个身份结构不直接透传浏览器。不同角色的身份字段同时在场、候选头像 Case 坐标与授权 Case 不符均拒绝。

资料补充失败给 counterpart=null 或失败字段 null，消息仍可读写；授权本身失败维持现有拒绝。不能把身份读取错误当作拥有披露资格。失权后不继续从旧列表或 P5 缓存恢复身份。

### 3.3 列表与详情呈现

- 招聘：头像、姓名；小字“投递企业 · 投递岗位”，聊天详情顶部副标题使用完全相同口径。企业缺失时仅显示投递岗位；岗位也缺失时显示“投递岗位暂未提供”，不显示孤立分隔符。姓名缺失为“候选人姓名暂未提供”；资料不可用为“会话资料暂不可用”。
- 求职：头像、姓名；小字“公司 · 职务”；缺字段分别为“公司暂未提供”“职务暂未提供”。
- 头像缺失/加载失败用已授权姓名首字占位，缺姓名用中性“·”；绝不显示破图或固定“会”。图片失败状态按 URL/会话切换复位。
- 共用三行布局：第一行姓名与时间；第二行小字岗位或公司·职务；第三行最后消息与未读数。AI 动态入口沿用同外壳和原数据语义。
- 搜索最终显示的姓名、副标题、消息摘要；分页、未读、顺序、read-through 不变。Mock 双端同步副标题语义；头像用本仓库已存在且对应演示人物的资源，缺图用同一占位，不下载无授权“真人照片”。
- 会话详情页头也消费同一个 counterpart，避免列表已显示真名、详情又闪回代号。P5 读取只负责资料层，不再为了姓名额外读公司链。

### 3.4 聊天消息头像尺寸与本人图片

- 用户确认消息两侧头像统一按现有对方尺寸：32×32px 圆形；当前共享 CSS 对方 32px、我方 26px，需同步修正我方 2px 顶部偏移及气泡两侧按旧尺寸预留的净空。覆盖求职/招聘真人聊天及对应 Mock，不改变消息列表头像尺寸。
- Backend 当前我方只渲染姓名首字，不读取照片；改用当前登录角色的本人头像。求职端复用候选账号头像及已有 revision 缓存更新机制，招聘端复用招聘方档案 avatar_url；页面直达也须确保本人资料已读取，不依赖先访问个人信息页。
- 对方继续使用授权披露的头像。双方优先显示图片；缺图或加载失败时，我方显示本人姓名第一个字，对方显示对方已授权姓名第一个字，均保持 32×32px 圆形。姓名取 trim 后第一个 Unicode 字符；姓名也缺失时使用中性“·”，不从 candidate_alias、职位、公司名或固定标题推导姓名。不能用 Mock 人像替代真实用户。图片 URL 更新后应重新尝试加载，不永久沿用旧图的失败状态。本人换图/删除后正确更新，账号或角色切换不能残留上一身份图片。
- 复用现有头像资料和会话渲染，不新增头像 API。验收双角色本人及对方照片、直达加载、双方缺图/坏图的各自姓名首字回退、缺姓名中性回退、换图后重试/删图及两侧尺寸对齐；长消息宽度应与新的头像净空一致。

## 4. 聊天“看在线简历”

- 招聘聊天主项改名“看在线简历”，打开既有全屏资料层，底部“继续沟通”关闭层，路由不新增。
- 正文以用户截图为准：姓名 → 最近职位 · 工作年限 → 手机/邮箱 → 工作经历 → 教育经历 → 个人优势。日期右对齐，职位和段落正文在公司下方；沿用简历纸身 CSS。
- 姓名取当前授权 Case 身份；工作年限、职位、工作/教育/自述取同 Case `candidate_resume`。最近职位取 summary.latest_experience；完整经历按该份源序展示，不自行排序。缺公司显示“公司未展示”，不从描述自由文本反推公司。
- 手机、邮箱当前固定显示“手机：—”“邮箱：—”。不读取 Mock 联系方式、登录手机号、PDF 解析联系方式。
- 缺失值用“—”；缺失整个区域显示“工作经历暂未提供”等；空数组显示“暂无工作经历”等。正文缺失仍保留纸身布局和定向重试，不能假装打开 PDF 作为兜底。

- 保留 MatchCase 阶段里的 PDF 附件下载/预览入口及其租约；只移除聊天在线简历入口的 PDF 请求和租约代码。
- 提取纯展示 `真人在线简历正文` 及输入模型，Mock/Backend 分别映射，禁止让纯展示组件读应用状态。只提取此次两个消费者需要的纸身，不重构所有简历组件。

## 5. 推荐评分解释合同

### 5.1 评分结果

仅招聘推荐详情 GET `/api/v1/recruiter/jobs/{job_id}/candidate-recommendations/{recommendation_id}` 新增 required `match_analysis`，不扩大列表 payload、不改求职端详情页面。

```ts
type MatchDimension = 'category' | 'skills' | 'experience'
  | 'location' | 'workplace_mode' | 'compensation';
type MatchAnalysis = {
  ranking_version: 'discovery-ranking.v2';
  dimensions: Array<{
    dimension: MatchDimension;
    status: 'matched' | 'partial' | 'unmatched' | 'unknown';
    score: number;
    max_score: number;
  }>;
};
// match_analysis: MatchAnalysis
```

固定六行，按上面维度顺序，满分 `[25,35,15,10,5,10]`；score 为整数且 0..max_score，和必须等于同条公开 match_score。仅技能、薪资可 partial；unknown/unmatched 均得 0，不能把 0 分写成未知总分。

状态与得分同一次批次计算：

| 维度 | matched | partial | unmatched | unknown |
| --- | --- | --- | --- | --- |
| 方向 | 相同 ID，25 | 不使用 | 两边已知不同，0（当前筛选不入榜） | ID 缺失（当前筛选不入榜） |
| 技能 | 全部岗位去重 token 命中，35 | 至少一个、未全中，按现有公式取整 | 两边有可比有效 token、零命中，0 | 岗位无有效关键词或候选无可比技能，0 |
| 经验 | 批次已确认且年限达标，15 | 不使用 | 已确认、年限已知且不足，0（招聘当前不入榜） | 未确认或年限缺失，0 |
| 地点 | 意向地点含岗位地点，10 | 不使用 | 双方有效地点已知但不含，0 | 必要地点缺失，0 |
| 办公 | 意向模式含岗位模式，5 | 不使用 | 双方模式已知但不含，0 | 必要模式缺失，0 |
| 薪资 | overlap，10 | near_miss，5 | disjoint，0（当前不入榜） | unknown，0 |

技能只说明结构化关键词命中，不把未命中表述为候选“不具备能力”。当前规则 near_miss 不在新推荐生成，只保留评分函数既有语义。

### 5.2 存储

- 在既有 discovery 推荐行增加评分解释 JSON 字段，通过必要的 schema migration；新批次两方向均保存同源结果，招聘详情开放公开投影。共享生成器只实现一次，不为两个方向复制规则。
- 内部只保存六行状态/分值及 ranking_version；不保存原始薪资、私人规则、候选原文或技能全集。这个任务不要求逐关键词勾选。
- `ScoreV2`、safe reasons、analysis 必须使用同一批次事实；可将 V2 六维计分提取成同域纯函数供总分和解释复用，不建立通用规则引擎。不为本次新增历史 V1 解释兼容分支。
- 新记录保存后不因简历、岗位、意向更新而重算；详情读取保持当前权限校验。
- 用户允许重建测试数据：不迁移或回填旧推荐，新合同要求完整 match_analysis。实施交接注明环境数据重建前提，不另做历史 null 展示机制。
- 缺失、畸形、重复维度或分数不一致的数据走既有数据错误路径，不从 highlights 或总分拼造解释。

### 5.3 视觉呈现

- 招聘推荐详情只有一处“匹配度分析”，移除独立“推荐依据”标题和重复空提示。顶栏仍为唯一总分位置。
- 六行：黑色维度名及 `得分/满分`；下方灰色说明；matched 为绿色勾；partial 为中性部分命中标记并写“部分匹配”；unmatched 为空心未选并写“未匹配”；unknown 为中性空心并写“未核对”。任何说明字符串都不能决定是否打勾。
- 未知不是不匹配，不用灰叉误导。状态对读屏可见，不只靠颜色。
- Mock 招聘推荐详情改用相同六维模型和组件；更新演示分数使总分等于六项之和，不能沿用与新行矛盾的旧 94 分。其他求职 Mock 的旧评分不在本次范围。

## 6. 亮点与公司卡片

- 个人亮点继续只消费个人亮点字段，匹配原因不能塞进个人标签。
- 有标签正常呈现；合法空统一改为“暂无可展示亮点”，不声称未生成或解析失败。列表和详情 summary 同源口径保持。
- 公司已知：公司 · 职位；公司缺失：只显示职位；最近公司被隐藏时不借上一任。无两项时延续工作经历缺失占位。
- 保留适用的披露门；经历 hidden 的错误耦合按 §6.1 移除。真实响应若证实字段合法空，归类数据/隐私状态，不创造前端“修复”；若证实源合法且应放行但响应错误，单独补充基于样本的修复范围再执行。

### 6.1 经历开关按字面语义修正

用户要求按“对这家公司隐藏我的信息”修正行为。开关应控制该 organization_id 的企业屏蔽；公司名称向其他招聘方的披露继续由披露设置控制。本节是明确批准的产品方向，现有测试数据可重建，不设计旧字段兼容或数据迁移。

- 复用现有 organization_blocks 及隐私变更 revision/事件/授权检查，不新建屏蔽系统。经历开关读企业的有效屏蔽状态，隐私页与同公司其他经历同步展示；公司以 organization_id 判定，不按字符串匹配。
- 新的主动开关操作使用 manual 企业屏蔽，避免被 employer_privacy_enabled 总开关意外失效。已有其他来源的屏蔽不得重复新增或覆盖来源；关闭时沿用现有解除流程，现任/关联企业来源保留已有风险确认。
- 编辑经历与更换公司不得暗中解除旧企业屏蔽；删除经历也不删除独立的企业屏蔽。尚未选定有效企业时不能声称屏蔽已生效。保存失败需保留待处理状态，不以“完成”冒充服务端成功。
- 企业被屏蔽后，其招聘访问应被拒绝，覆盖推荐列表、旧推荐详情及后续在线简历/身份读取；代招的招聘企业与发布企业沿用现有双侧检查。实施须核验既有会话/附件路径，不能仅过滤新一批推荐；已被对方接收的历史内容不能承诺撤回。
- 新经历不再用 hidden=true 表示企业屏蔽；PDF 预填也不自动把每一家历史雇主加入屏蔽名单。开关初值来自已有企业屏蔽，用户主动打开后生效；现任企业既有保护流程保留。
- 移除经历 hidden 的旧公司名遮蔽语义及其亮点过滤耦合，贯通前端类型/预填/写入、后端合同/模型/投影与测试。企业访问由组织屏蔽控制，公司和亮点仍遵守适用的披露设置。不保留历史 hidden 转换、回填或双轨兼容；必要的数据库结构变更不等于历史数据迁移。本轮不执行数据清理。
- 验收新增：A 企业被屏蔽而 B 企业仍按披露设置看到公司名；同企业多经历与隐私页一致；代招双侧屏蔽；旧推荐和身份访问拒绝；新建/导入经历不再错误遮蔽公司名；修改/删除经历不意外解封。

最小方案是复用企业屏蔽作为单一事实源。仅改文案不符合用户当前要求；另外增加一套逐经历企业访问控制会与现有屏蔽名单形成重复状态，因此不采用。

本轮暂缓：

- **亮点生成器修改及旧解析追溯**：正确账号精确解析结果未核实；另一账号 suggestions=[] 的内部原因也未查明。重启条件为精确 file/version/parse 与推荐主体关联、服务端解析结果存在性及可用诊断计数证明生成/校验链有缺陷。本轮用明确有标签和合法空的可控数据验收接线与隐私，不保证每份 PDF 必然生成标签。
- **联系方式授权披露**：在线合同没有手机号/邮箱；另有用户确认及授权设计后再开，禁止借用登录手机号。
- **评分算法升级及逐 JD 条目核对**：没有本轮需求，不新增学历分、语义匹配、模型调用或新排序规则。
- **历史数据修复**：用户允许测试数据重建，不提供迁移兼容。本设计不授权清理未知环境；实施时应在明确的可重建测试环境准备新数据。
- **无关页面重构与发布**：不改求职推荐详情原有分析，不新建通用身份缓存、隐私系统或规则引擎；部署和正式集成按既有工作流处理。
