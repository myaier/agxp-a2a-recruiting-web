## 3. 方案取舍

推荐复用现有区号按钮，点击后在小弹层直接编辑区号。备选为常用国家列表加自定义输入，但当前只有默认大陆登录和 STG 合成号码两个明确用例，没有国家目录、搜索或国际短信运营需求，因此延后列表。

不采用仅为测试注入 Cookie 的方式：本轮明确要证明真实 UI 登录、刷新和会话隔离。也不修改后端合成号码生成策略：现有服务已支持这些号码，前端显式传递区号即可解除当前限制。

登录接口采用兼容扩展，保留原一参数调用，第二参数为可选区号，缺省为 `+86`。这个默认值直接保护现有组件、测试桩及其他调用方，不引入全局默认国家配置或电话号码依赖库。

## 4. 产品行为

### 4.1 默认态与区号编辑

- 每次新挂载登录页默认 `+86`，手机号和验证码为空；区号不写入 localStorage、sessionStorage 或服务端。
- 保持原默认页面布局、手机号 label `手机号`、placeholder `输入手机号`、四位验证码、协议与微信登录入口。默认手机号仍为 11 位，展示保留 3-4-4 分组；原测试无需先操作区号。
- 区号按钮保留当前值可见，通过可访问名称表达编辑目的。弹层采用现有框架，有区号输入、确认和取消；Escape/遮罩关闭等价于取消，关闭后焦点回到触发入口。未打开时不渲染额外表单。
- 区号输入允许首尾空格和可选的一个前导 `+`，确认后规范为 `+` 加 1–3 位数字、首位非零。不静默删除中间非法字符或截断区号。非法值在弹层内给出中文错误，不提交或请求后端。
- 取消编辑或确认相同区号不改变手机号与当前有效取码状态。确认不同区号时保留完整号码数字供用户检查，作废验证码状态；若号码在新区号下不合法，提示用户修改，不因切区号悄悄截掉号码。
- 非 `+86` 号码不套 11 位及 3-4-4 展示限制；拼接后按当前后端合同校验 8–15 位数字。`+999` 与 12 位号码必须完整保留、可提交。普通分隔符的清理保持明确且可预测，非法或超长输入不得静默变成另一个可提交号码。
- `+86` 保留原有 11 位长度要求，不顺便增加原先不存在的号段限制。前端只证明输入形态与对接合同成立，后端仍决定短信通道是否支持。

### 4.2 请求与验证码生命周期

- `开始手机登录(phone, dialCode?)` 的省略区号调用继续生成 `+86` 完整号码；显式传入规范区号时只拼接一次。状态层透传区号，不能在某层再次补 `+86`。
- HTTP path、`provider: phone_otp`、两步独立幂等请求和 4 位 proof 不变；后端错误继续走现有错误展示，不回退 Mock。
- 取码和完成登录请求进行中禁用手机号编辑、区号编辑及相冲突的登录操作，使用同步守卫避免快速连点穿透。请求结算后才恢复操作；不增加自动重试。
- 已取码后，只要实际号码或区号变化，验证码清空、旧取码资格失效；新号码必须重新成功取码才能完成登录。切回原号码也不能恢复旧资格。相同号码的格式化变化不视为换号。
- 取消区号弹层不重置倒计时。换号不作为绕过短信限流的手段；保留当前未到期的客户端重发等待约束，最终仍以服务端限流为准。
- 请求迟到、页面退出/重进或失败时，旧尝试不能覆盖新尝试或启用错误号码的完成按钮。实现优先使用已有会话引用与局部请求守卫，若需扩展状态，仅限本登录流程，不重构全局认证体系。
- 完成登录仍由现有 Provider 水合角色并由根路由决定落点；四位码、失败可重试、重复提交保护、退出/401 清理、跨账号数据隔离继续成立。
- Mock 模式保持原本地四位码登录与零 `/api/v1` 请求，支持同样的区号输入交互但不宣称验证真实短信。P8 换绑本轮仍为原大陆手机号合同，不扩大到国际换绑。

### 5.1 准备与边界

执行者提供前端目标 URL、后端 checkout、实际前后端版本与安全登录材料通道。按后端仓库规则准备工具依赖，从后端 checkout 根调用现有环境 skill/CLI；不复制 CLI，不读取秘密到日志，不手写业务 SQL，不自动部署。

默认使用 `ephemeral-baseline`；不因失败降级为固定账号。`validate` 成功、prepare 返回 READY、verify 成功后才启动消费。preflight 是两类 scene 前置的并集，必须区分固定账号输入缺失与本轮 ephemeral 必需前置，不能因无关 baseline 输入缺失误判一次性场景不可用，也不能忽略真实 fixture 前置失败。

前端使用 `VITE_DATA_SOURCE=backend VITE_BACKEND_ENV=stg` 和独占服务，默认目标 `http://localhost:5173`，端口严格匹配。浏览器分别建立候选、招聘独立具名会话，加载现场 `agent-browser` core/dogfood skills。实际验证 Cookie、Origin、刷新与注销；不放宽后端 Cookie/CORS，不复制 API 会话绕过 UI 登录。代理确有缺陷时记录具体证据及所需调整，超出已核实接线范围则修订设计，不临时建立新代理架构。

采用现有默认样本的实际资源与初始值作为本轮基准；不要求旧 local 基准姓名、两个基准岗位或预先存在的公司介绍。岗位归档/重开在浏览器新建的岗位上验证。公司资料编辑与首次 onboarding 不作为本轮必需项。

### 5.2 两轮责任

第一轮完整执行以下节点：

1. skill prepare/verify，记录 run、安全回执路径、登录材料路径、资源归属与版本。
2. 两个角色通过 UI 输入各自区号、号码与 OTP 登录；验证角色和基础资料与准备结果一致。
3. 候选修改普通简历字段并刷新回读；意向新建、编辑、删除，保留基准意向。
4. 招聘名片职务修改并刷新回读；浏览器新建岗位、编辑、归档、重开、删除，保留基准岗位。
5. 候选退出后确认退出生效，招聘会话刷新仍有效、资料归属正确。
6. 关闭本轮浏览器会话，cleanup 必须达到 CLEANED、残留为空、占用释放。

第二轮使用全新 run，重复 prepare/verify、双角色 UI 登录、一次意向新建/删除与刷新、cleanup。通过受限材料在进程内比较身份，报告只记录“身份不同”等结论及允许的安全实体 ID；确认首轮新建资源没有进入第二轮。验证首轮身份清理后无法再建立会话，可使用现有正常认证 API 做一次有界反证，不把该只读/验证性辅助流程冒称 UI 登录覆盖，不暴露号码或 OTP。

被测业务写入经 UI；准备与清理仅使用现有环境工具；只读 API 辅助核对当前角色、当前实体。记录页面自动请求产生的资源，不能因没有手点委托就假定零副作用。严禁为消除残留直接修改业务数据库或把失败结果补写成成功。

### 5.3 非覆盖与恢复

不执行附件/PDF、首次 onboarding、发现刷新/委托、规则创建、Hosted、MatchCase、IM、实名、导出、反馈等不在清理范围内的动作。基础导航若自动产生此类资源，记录真实问题，停止依赖该 run 的后续动作，并按现有 CLI 能力尝试清理；不得屏蔽产品请求让测试通过。

单轮从开始持续记录，finally 语义覆盖成功、失败及中断后的恢复。保持后端 checkout 的受限 proof/session 状态，未清理前不删除工作区；只清理本轮有 proof 的 run，不抢占或清理他人 run。cleanup 失败保留回执、残留与恢复责任，不换 run 绕过。proof 丢失按已知 `fixture_proof_stranded` 边界处理，不声称自动恢复。

每个节点用 PASS/FAIL/BLOCKED/NOT_RUN 及证据判定；清理单独判定。两轮完成且各自 CLEANED 才能称试点完整通过。新登录代码通过但 STG 不可用时，必须分开写“代码回归通过”和“试点 BLOCKED”，不能声称基础设施迁移成功。
