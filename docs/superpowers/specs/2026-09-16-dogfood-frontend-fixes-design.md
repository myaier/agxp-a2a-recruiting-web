状态：用户于 2026-09-16 批准本设计，并授权编写零上下文 Plan、Claude 文档 review 与执行提示词；未实施。

## 1. 目标与授权范围

用户要求按 DF-005 → DF-002 → DF-014、DF-015、DF-004 → DF-011 制定计划，并在 DF-005 后回归 DF-016、DF-008；明确使用 development-workflow，本分支不跑 L3。

本设计以六项局部修复恢复详情可达性、建档错误可发现性和已有数据的正确展示。DF-016、DF-008 只承担回归责任，不预设新增产品改动。

- 源码核查基线：`30a0d3b24c2257da70c8b54fff4ee0ebb5ad71d0`，核查时与 origin/main 一致。
- 工作区：`.`；目标分支：`main`。规划阶段只提交本设计及获批后产生的 Plan/prompt，不合入或 push。
- 项目规则：`CLAUDE.md`、`AGENTS.md`；测试总入口：`docs/testing/README.md`。
- 既有展示约定：`docs/superpowers/specs/2026-09-16-s0-s3-display-alignment-design.md`。本次保持其历史卡匿名身份、详情画像同源、经历源序及 Case 冻结资料边界。
- 报告中的真实账号、Case ID、HAR、简历和联系方式不进入提交或测试；用合成等价数据验证。

## 2. 方案取舍

采用现有 decoder、页面编辑目标、账号水合、推荐 view-model 和展示组件上的局部修复。现有六个具体故障已有直接因果链，不需要新增平台能力。

比较的替代方案：

1. 统一改造表单校验与展示层：能覆盖更多页面，但会扩大行为回归面；当前只有工作经历保存反馈需要局部定位，不采用。
2. 扩展后端 highlights、匹配证据或返回约定：会引入新接口和资源确认语义；当前前端已有足够数据解决六项缺陷，不采用。

允许提取同域的小型纯函数，以复用已有缺项判定或匹配原因词表；不新增通用校验框架、缓存服务、可配置 schema、请求聚合层、依赖或环境变量。

## 3. DF-005：可选发布人头像不阻断详情（P1 / required）

现状：`src/数据/招聘数据源/展示资料.ts` 的 `解发布人档案` 强制四键；本仓库 CandidateJob 类型允许头像键缺席。合成样本实测缺键报 invalid_response，补 null 通过。

行为合同：

- wire 的 publisher_profile 对象省略 avatar_url 时，只在该对象边界补 null，再按原闭合结构校验。
- 内部 `BFF公开发布人档案` 继续保持 avatar_url 为 string | null；不把 optional 扩散给内部消费者。
- 显式 null 和合法字符串保留；显式 undefined、数字、对象、未知嵌套键和其余必需键缺失继续拒绝。
- publisher_profile 整体缺席或 null 的现有合同不改变；不修改通用闭合对象 guard，不放宽其他可选字段。
- 候选、招聘完整详情链路，以及候选连续详情的嵌套 Case，均不得因该键缺席降级为服务返回异常。

复杂度影响：不变，局部归一化替代错误的 wire 必需约束。

## 4. DF-016 / DF-008：DF-005 后的页面回归

本分支 L3 selection 为 none。这里的页面回归指真实浏览器运行产品 Backend 分支，由现有 Playwright fixture 提供受控 HTTP 响应；不连接真实业务服务，不把 fixture 结果标为真实后端通过。

- DF-016：招聘详情响应同时提供安全 resume.summary 与缺席头像键的 publisher_profile；通过正常路由进入详情，顶部性别、经验、学历、求职状态与在线简历同源。响应摘要变 null 时清空旧画像。保持既有去名策略，不加载身份头像。
- DF-008：双角色分别验证 open → ended，候选走 negotiations，招聘走 open MatchCase 列表。先观察当前卡，再改变 fixture 的权威集合；保持页面可见，跨至少一次生产 5 秒轮询，断言当前卡移除；正常导航进入历史，断言出现终态记录且无“代理处理中”。不能靠手动刷新替代轮询验证。
- 历史页面保持零轮询；首次进入历史的读和已加载快照的刷新遵循现有合同，测试不得通过清缓存绕过陈旧状态。
- 异步等待使用可观察请求和页面断言，不缩短产品轮询周期，不新增测试专用产品开关。
- 若受控回归暴露新故障，先给出具体反例及归因；不自动改变状态机、后端字段或启动无边界重构。超出本设计的产品修复须修订设计。

真实服务的状态迁移、权限和实际 Agent 结果本分支不获验证，不列为本分支阻塞项，也不记 PASS。

## 5. DF-002：工作经历保存错误可发现、可修正（P1 / required）

现状：`src/流程/候选Onboarding简历预填.ts` 已统计预填物化经历中的公司名称、真实组织 ID、行业引用、职位、开始时间缺失；`src/屏幕/工作经历.tsx` 保存只 toast 后返回，折叠卡不解释缺项。

行为合同：

- 保持已有必填规则和适用范围，不把预填专属校验扩成所有旧简历的新增必填要求。
- 存在已有校验认定的缺项时，工作经历卡显示具体提示，例如“待补充：公司、行业”。有公司原文但缺 canonical ID 时提示选择公司，不自动匹配或创建目录项。
- 点击保存，在没有发出该次无效总保存请求的前提下，使用现有编辑目标打开第一条不完整工作经历，并在挂载后滚动、聚焦其第一个缺失字段的输入或选择触发按钮；字段附近保留可见提示，不能只靠短 toast。
- 目标按当前经历列表顺序选择；字段定位按现有表单顺序：公司、行业、职位、入职时间。同字段的名称与引用缺失合并为一个用户提示。
- 修正或删除条目后实时重算提示；下一次保存定位下一条错误，全部补齐后走既有成功流程。返回编辑页不丢已填写草稿。
- 现有统计还包含教育与证书；只剩这些错误时保留现有拦截，不错误打开一条完整工作经历。不顺带重建教育、证书的校验 UX。
- 复用同一经历缺项判定，让卡片提示与保存拦截不产生两套规则；不新增全局表单引擎。

复杂度影响：增加局部错误定位状态与引用，直接解决用户无法识别建档阻塞项的问题。

## 6. DF-014：服务端拥有 Backend 账户头像（P2 / required）

涉及 `src/状态/资料持久化.ts`、`src/数据/资料缓存.ts`、`src/状态/应用状态.tsx` 与 `src/状态/后端/会话操作.ts`。

行为合同：

- Backend 求职头像以现有 account-profile 水合和上传后的权威回读为来源，继续使用已有 revision URL 策略。
- Backend session cache 不再持久化或恢复该字段；旧缓存中的 null、旧 URL 或旧本地图片均不得覆盖服务端值。
- 同时处理默认空快照合并：从写白名单删除字段不够，`空账号资料` 的默认 null 也不得在缓存水合时覆盖当前头像。
- 缓存先完成、服务端先完成两种顺序，最终均服从服务端事实；服务端明确 null 必须清旧头像。
- 保持退出、切主体时清空及现有代际栅栏，防止沿用前一个账号的图。服务端读取失败不得用缓存伪装权威成功。
- Mock 头像缓存与编辑行为保持；“我”页 URL 缺席时的姓名首字降级保持。本次不新增图片请求失败处理，不改图片组件或媒体服务。

复杂度影响：降低，移除 service-owned 字段的重复缓存写入者。不得把全部账号缓存清空作为修复。

## 7. DF-015：推荐横幅与可见集合一致（P2 / required）

`src/屏幕/候选推荐.tsx` 横幅数量使用当前 `待选卡们.length`，与实际卡片渲染共用集合。已有 delegation 的推荐仍按既有规则过滤。混合列表、全部已委托、零结果均保持数量与可见卡数一致。

不新增批次总数解释区、不增加接口、不改筛选或委托行为。复杂度影响：不变。

## 8. DF-004：个人优势说明对应实际预填（P2 / required）

`src/屏幕/引导问答.tsx` 的非简历编辑入口，仅在本轮有效 summary 建议实际作为初值应用且输入仍非空时显示“已根据你上传的简历预先提取，直接删改即可。”。

未上传、建议缺席/空白/不可用、由已有用户文本初始化或用户清空输入时，使用中性说明“可以介绍你的经验、技能和擅长的事情。”。不因为当前恰好存在建议，就声称已经应用到另一个现存文本。

独立简历编辑继续不显示上传提取说明；保留现有建议恢复、summary 保存和确认顺序，不自动覆盖用户输入，不接 personal-highlights 新资源。Mock 也不应对未实际应用的建议声称已预填。

复杂度影响：不变，修正说明来源判定，不改变保存资源。

## 9. DF-011：展示当前推荐的已有安全原因（P2 / required）

现有推荐上下文已能到达页面；`src/数据/发现推荐映射.ts` 接收候选 match_reasons、招聘 highlights。缺口在正文消费，不新建全局 recommendation store。

行为合同：

- 只使用当前岗位/候选、当前意向或岗位 scope 的有效推荐响应。直接访问没有推荐上下文的详情时不借用其他记录的原因或分数。
- 双端详情的匹配区增加“推荐依据”说明，复用同域已知原因码映射：category_matched→职位方向匹配、experience_met→经验要求匹配、location_matched→工作地点匹配、workplace_mode_matched→办公方式匹配。
- 未知开放码不透出、不猜词义；已知原因稳定去重，保持首次出现顺序。全部缺席时显示“暂无推荐依据”。
- 这些文字只表示该推荐批次返回的依据，不升级为当前简历逐条证据、不冒充个人亮点；经验/学历尚未核对的现有说明保持，不能被原因词覆盖。
- 候选侧已有合法结构化核对行继续展示；行数组为空也保留匹配标题、真实推荐分和可用原因。分数为 0 必须显示 0；无推荐分不造 0。
- 招聘匿名简历沿用顶栏唯一分数位置，正文展示原因但不重复分数环；无逐条证据使用“暂无逐条匹配证据”，不以已有原因生成 Mock 级对齐行。
- Case 冻结详情不得为了本项补读实时推荐；本项只修改候选独立岗位详情与招聘推荐匿名简历消费者。共享正文的新可选输入不得污染 Case 页面或 Mock 现有对齐证据。
- 切换记录、意向或新响应原因变空时清除旧原因；不额外发起详情逐卡请求。

复杂度影响：增加有限展示接线。双端已有真实原因消费者构成复用词表的当前依据；无需新增后端能力。
