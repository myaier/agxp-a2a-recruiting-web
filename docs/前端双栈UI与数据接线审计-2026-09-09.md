# 前端 Mock / Backend UI 与数据接线审计

日期：2026-09-09。代码基线：`7ff13eef`。本次只审查与记录，不修改业务代码。

## 结论

用户观察成立：当前不是「相同页面组件，只替换数据提供者」，而是「Mock 原型运行路径 + Backend 业务运行路径」。数据源判断已经进入路由守卫、页面入口、列表、卡片、表单和按钮层。

这与 local / stg 的区别无关：`src/配置/运行配置.ts` 中，`VITE_DATA_SOURCE` 决定 mock/backend，`VITE_BACKEND_ENV` 只选择代理目标。屏幕与组件的生产代码未发现按 local/stg 切换布局的判断。

需要区分三件事：

1. **数据变化**：文字长短、字段为空、分页尚未完成、权限导致未披露；即使共用组件，也可能改变高度和可见行数。
2. **功能差异**：Mock 有模拟对话、日报、人脸验证和本地成功；Backend 没有相同能力，因而关闭功能或替换内容。
3. **展示实现分叉**：两边分别维护 JSX/CSS，除了必要的数据与功能差异，还出现了结构、间距、状态位置的独立变化。

前两项不意味着必须维护两套卡片布局；目前实现把这几项混在了页面模式分支里。

## 接线主干

```text
运行配置 → 接口层.创建招聘数据源 → 应用状态提供者
  mock    → 演示种子 / 页面直接 import fixture / reducer / 本地缓存
  backend → 应用操作 → HTTP招聘数据源的各业务域 → 同源 /api/v1 → Vite 代理
                      ↓ 响应严格解码、字段映射
            后端状态快照 或 水合到状态中的页面领域数据
                      ↓
                页面分支 / 展示映射 / 卡片
```

关键代码：

- `src/数据/接口层.ts:77`：`招聘数据源选择` 的 mock 成员只有模式/环境，没有与 HTTP 后端对称的一套方法。旧 `数据 = 模拟数据源` 仍是另外的演示入口。
- `src/状态/初始状态.ts:317`：初始状态分 Mock 种子和 Backend 空底座。
- `src/状态/应用状态.tsx:846`：组合会话、候选、岗位、组织、P4/P5/P7/P8 等操作；Context 同时暴露 `状态`、`后端状态`、`数据源模式`、`操作`、`目录查询`。
- `src/状态/后端/候选操作.ts:208`：简历等较早接入的操作在内部做模式分支；Mock 派发本地数据，Backend 请求后水合。因此这些表单更接近共用 UI。
- `src/数据/HTTP招聘数据源.ts`：组合各域 HTTP 实现。不是可以直接替换 Mock 页面所用全部接口的对称 adapter。
- `src/状态/资料持久化.ts`：Backend 已接业务的服务端事实不从旧 Mock localStorage 恢复；部分草稿/恢复控制信息有各自边界，不能笼统称为 Backend 完全无本地存储。
- `src/应用.tsx:237`：Backend 才做会话恢复、角色路由限制、招聘组织失败恢复面；同一地址在不同模式可能根本不挂载同一业务页面。

后端读取存在两种形态：简历/意向/岗位等映射后水合到通用 `状态`；P4 推荐、P5 MatchCase、P7 会话等另存专属快照，页面再投影。Mock 则主要直接消费老的中文领域对象。这种不对称推动了上层分支的增加。

## 最明显的卡片结构差异

### 求职端在谈

入口 `src/屏幕/在谈首页.tsx:52` 直接二选一：

```tsx
return 数据源模式 === 'backend' ? <Backend在谈首页 /> : <Mock在谈首页 />;
```

| 位置 | Mock：`在谈首页.tsx:251` | Backend：`P5/MatchCase列表.tsx:80` |
| --- | --- | --- |
| 头部 | 公司字标、公司名、公司简介 | 职位名称、待办徽标 |
| 右侧 | 匹配环、环下薪资 | 无匹配环 |
| 薪资位置 | 头部右列 | 职位下方，与城市并排 |
| 标签 | 原型岗位标签 | 冻结工作区职位技能 |
| 底部 | `阶段标签` + 原型下一步 | P5 阶段标题 + 状态文案，可加注意说明 |

这不是同一个组件因 null 隐藏了几行，而是另一套 DOM。P5 当前卡片只拿该业务域提供的职位上下文，不从公司、推荐等其他域拼齐原型公司卡。

### 招聘端在谈

入口 `src/屏幕/企业在谈候选.tsx:59` 分流。

- Mock 的 `候选卡` 在该文件内：读 `企业候选列表`，再回查静态 `推荐列表` 取亮点；头部右侧匹配环，底部使用通用 `阶段标签`。
- Backend 用 `src/屏幕/P5/MatchCase列表.tsx:98` 的 `招聘在谈卡`：只读 MatchCase 展开的 `candidate_summary`；头部右侧是待办徽标，没有匹配分；底部是 P5 自己的阶段节点。
- 2026-09-09 已把 Backend 工作、教育、个人亮点放回类似 Mock 的位置，但组件仍独立。

即使摘要完整，样式也不相同：

| 属性 | Mock：`企业在谈候选.module.css` | Backend：`P5/MatchCase列表.module.css` |
| --- | --- | --- |
| 卡片 padding | `14px 16px 11px` | `13px 15px 10px` |
| 头行 | `padding-right:76px`，右列绝对定位 | flex 行内待办徽标 |
| 标签 margin-top | `7px` | `8px` |
| 阶段 margin-top / padding-top | `10px / 9px` | `8px / 8px` |
| 下一步/状态字号 | `11.5px` | `11px` |

没有服务端匹配分时不显示分数是必要的真实性约束；卡片 padding、阶段区间距不一致则是独立展示实现造成的，并不是缺字段必然要求。

### 招聘端推荐

`src/屏幕/候选推荐.tsx:69` 分流；文件中分别有 `后端推荐卡`（约 627 行）和 `推荐卡`（约 834 行）。两者共用本文件 CSS，当前主要位置已接近，但仍是重复 JSX。

- Mock：经验/学历/求职状态来自推荐 fixture；工作行由 `画像` 拆分；标签来自原型亮点等数据。
- Backend：`candidate-recommendations?...include=candidate_summary` → 严格解码 → `发现推荐映射` → `招聘候选摘要映射` → 卡片。摘要只从 `candidate_summary` 取，不拿旧 highlights 或其他接口兜底。
- `candidate_summary=null`：头部显示「候选信息暂未披露」，工作/教育/亮点整行收起，底行仍保留。匹配环仍使用推荐匹配分。
- 有摘要但某字段缺失：只隐藏对应字段或行；缺失工作和教育时图标也消失。
- 列表容器另有 Backend 组织认证、加载/失败、收藏过滤、委托状态等分支。

因此「有的时候不同」也可能是完整摘要和未披露摘要触发不同的行显隐，并非随机布局。

### 求职端看市场：已有的较好参照

`src/屏幕/看市场.tsx:432` 的列表有两条分支，但两边最后都调用同一个 `市场卡`（约 721 行）。Backend 把岗位投影成 `市场职位`，传入委托状态文案/禁用位/处理器，卡片内部复用同一套布局。

它仍有列表加载态、规则抽屉只读等差异，也通过 `use适配分` 区分真实匹配分与本地计算分；但卡面没有另写一份 Backend JSX。这说明不必先重构整个状态系统，便能收敛局部展示。

| 反馈 | P8 feedback | 共用输入区，提交结果/工单号不同；举报走有目标的单独入口 |
| 帮助与客服 | 静态 FAQ + 真实功能导航 | 按模式/角色替换 FAQ 与入口，隐藏无来源的热线等 |
| 用户协议 | 静态说明 | 无数据源分支或后端请求 |

辅助屏幕组件也已纳入检索：`顶部意向栏`（真实 ID 对比 vs Mock 名称）、`招聘方组织门`（失败/恢复/权限）、`拿不准弹层`（原型回调）、`真人会话操作栏`（按调用方提供的动作渲染）；`P5/MatchCase列表`、`P5/MatchCase历史`、`P5/MatchCase详情`、`P7/Backend会话列表`、`P7/Backend真人会话` 是上述页面实际使用的后端展示实现。导航未读、规则筛选抽屉、公司区块、附件/PDF 弹层等共享组件也参与差异。

## 为什么逐渐变成两套页面

这不是单个开发者偶然写了 if/else；相关设计文件明确选择过这条路径：

- 2026-08-24 数据源设计要求保留 Mock 体验、集中请求和映射，并提出页面结构不变。
- 2026-08-29 P5 设计转为 backend-only raw snapshot + P5 页面组件，禁止为了还原原型去跨域补齐公司、画像、匹配分；丰富展示列为 P5.1 延后内容。
- 2026-08-30 P7 设计 §4.1 明确选择「现有页面双分支」，入口分成 Backend/Mock 私有实现。
- 2026-09-02 真实性修复要求 Backend 不展示模拟日报、对话、统计和本地假成功，Mock 保持剧情，进一步扩大可见功能差异。
- 2026-09-09 招聘列表摘要设计明确要求按 Mock 信息位置展示，同时把「全面统一 Mock 与 backend 卡片组件」排除在本次范围之外。

因此，代码中的「复用视觉壳」「不重设计」很多时候仅指使用原有颜色、卡片风格或部分公共组件，并不代表两模式使用同一组件树。后来修改 Mock 页面时，Backend 组件不会自动随之改变。

## 发现与建议

### 1. 卡片展示存在真实重复与样式漂移

必要性：optional（当前任务是审计，且已有 spec 明确允许分支）；复杂度影响：降低。

如果产品目标确认是「同一信息布局、仅数据/能力差异」，优先收敛招聘推荐卡、招聘在谈卡、求职在谈卡的纯展示部分。保留现有请求、权限与状态处理；将展示需要的字段和可用动作传入同一个小组件，缺值规则也只实现一次。依据是本次已经观察到的重复 JSX、独立 CSS 与具体间距差异，不是为未来假设引入通用框架。

不建议一次性重写 Provider、建立新全局状态库或通用卡片 schema；`看市场` 已示范了可局部完成的路径。

### 2. Backend 仍有部分原型业务事实留在共用页面

必要性：required；复杂度影响：降低。

- `代理详情.tsx:65` 附近与 `企业代理详情.tsx:68` 附近仍无条件显示「在线」；两页都有固定 `186` 累计筛选数。
- 飞书接入块仍是 `useState` +「我已扫码（原型演示）」按钮，点击后本地显示已接入及固定人物信息；没有调用接入 API。虽然按钮标注原型，但同屏真实统计与模拟接入混合，不能把该页视为已完整后端接线。
- `初始化页.tsx:25` 起固定 862 个岗位/316 位候选、3.6 秒离场；候选头像完成与招聘注册首发岗均能进入该页，应用角色路由也允许它。页面未订阅真实扫描进度。

现实影响是 Backend 用户看到未经后端证实的业务数字、在线与完成状态。最小处理应删除或中性化无依据的业务断言，或将明确的演示交互限定到 Mock；不需要为此新增真实接入系统。此项是数据真实性问题，与是否统一布局分开处理。

### 3. 现有视觉门禁不等于跨模式一致性门禁

必要性：optional；复杂度影响：增加。

`playwright.视觉回归.config.ts:23` 固定 `VITE_DATA_SOURCE=mock`；数据源模式 E2E 分别运行 @mock/@backend 场景；卡片测试分别断言两个模式的行为及不读取演示数据。这些都不能单独证明 Mock 与 Backend 同一内容下具有相同几何布局。

如开始收敛卡片，增加少量「完整字段/空字段/待办」的并列渲染检查即可，不必新建全站视觉平台。新增维护成本只覆盖本次有证据的三类卡片，可避免相同漂移再次发生。功能不可用、隐私未披露、加载失败不能与完整 Mock 数据强行做全页像素相等。
