# 非列表页面 Mock / Backend 组件复用评估

日期：2026-09-10。范围：双端在谈详情、候选与招聘 onboarding、简历管理、求职意向管理、岗位管理及其编辑子页。只做代码审计，不实施重构；不覆盖另一个 worktree 正在处理的推荐、在谈列表。

## 结论

最值得收敛的是双端在谈详情、招聘名片，以及散落于 onboarding / 意向 / 简历 / 发岗中的选择器。我的简历适合局部拆分；意向管理、岗位管理主体已经共用展示，不需要再造一套页面。

目标应是：两种来源提供页面所需的数据和动作，共用展示组件与 CSS；展示组件按业务状态显示内容，不认识 `backend/mock`。这不意味着强迫两种来源拥有相同能力，也不意味着把 Backend DTO 填进 Mock 业务模型。

以下重构建议均为「必要性：optional；复杂度影响：降低」，以最终删除重复 JSX 和页面内接线为收益，不视为必须修复的缺陷。单独标记的事实来源问题除外。

## 1. 双端在谈详情：收益最高，但不能整页直接套 Mock

入口：`src/屏幕/在谈详情.tsx:97`、`src/屏幕/候选详情.tsx`。两者按模式切整页：Backend 进入 `P5/MatchCase详情.tsx`，Mock 保留各自页面。Backend 双角色已经共享一页。

目前共同使用 `阶段对话流`、`真输入条` 和通用外壳，但顶栏、Tab、状态区、决策卡仍分开：

- Mock 有「代谈进度 / 职位详情（或在线简历）」两个 Tab；Backend 是状态行、轮次、终局/移交区和阶段流，没有这些详情 Tab。
- Mock 顶栏含适配/匹配分；Backend 使用待办徽标。招聘端 Mock 顶栏已改成性别/年限/学历，Backend 仍用 candidateAlias。
- Backend `详情主体` 虽然接收视图，也接收 raw 快照和整个操作接口，自行管理 PDF 租约；`阶段动作区` 同时负责动作界面、提交、披露确认、请求锁和换单清理，仍不是纯展示。

适合共用：详情外壳/顶栏、阶段流、状态与终局区、具体业务动作卡、附件选择和确认层的视觉内容。沿用已有 `分段项` 和 MatchCase 展示映射，仅补页面真正需要的字段及回调。

Backend 控制层继续负责：按 role/case 读取与轮询、actions 授权、补充问题坐标、披露确认、PDF 生命周期、并发和过时响应隔离、真实 conversation_ref 导航。Mock 控制层负责本地剧情和 reducer；两者不共享状态机。

限制：不能为了显示第二个 Tab，从其他接口拼一份“当前简历”冒充 Case 的披露快照。现有 P5 spec 明确限制跨域补齐；缺匹配分、结构化简历等内容应有明确缺省状态。展示相同区块时使用同一布局，能力不同的区块仍允许不出现。

参考：`docs/superpowers/specs/2026-08-29-recruitment-p5-frontend-wiring-design.md` §3、§8、§10。后续设计须明确替代其中“Mock 整页保持原实现”的选择，同时保留数据和授权边界。

## 2. Onboarding：按页面收敛，不重写流程引擎

实际合同在 `src/流程/onboarding配置.ts:109`，恢复及角色守卫在 `src/应用.tsx`。学生和社招顺序有差异，社招薪资段还有独立 URL。招聘主流程是名片 → 发岗；实名认证不是注册必经步骤。

| 页面组 | 当前情况 | 适合的收敛范围 |
|---|---|---|
| 基本信息、求职状态、最高学历、就读时间段、披露说明、添加头像 | 主体 JSX 已共享，预填、确认状态、保存和导航混在页面里 | 保留表单，只移出来源相关的初值、确认和提交；小页面不为形式拆多层 |
| 学生分流 | 同一表单内夹附件上传、授权、解析、预填轮次；Backend 初值为空，Mock 有演示默认 | 共用表单和上传入口；解析/预填编排放控制层 |
| 引导问答、选工作城市、毕业院校、选专业、选期望职位 | 查询/分页/目录引用与渲染混合，有成块的双模式 JSX | 按真实重复提取城市、职位分类、学校/专业选择界面；复用已有城市查询钩子 |
| 招聘名片 | `招聘名片.tsx:42` 切换 `后端名片/Mock名片`，两套表单 | 高优先级统一头像预览、姓名、职务、公司区和保存按钮；控制层提供只读状态、关系选项、上传和保存 |
| 发布岗位 | 共用三步表单，但控制逻辑很重 | 与岗位编辑作为同一任务处理，见第 5 节 |
| 初始化页 | 两栈共用模拟节奏与 862/316 计数 | 保留展示，拆开演示动画和真实完成条件；无真实进度时不编造扫描数量 |

选择器是跨页面最有实际复用价值的一组：意向编辑、简历教育/工作经历、发岗也重复使用。展示层接收选项、分组、选中项、查询状态与回调；目录 ID 和可选叶子的验证继续留在控制/数据层。分页、空结果、失败属于业务状态，不需要依赖模式名控制。

不建议一开始建立万能 schema 表单、通用流程引擎或统一所有目录查询协议。城市分组、职业树与学校搜索的实际差异应保留；提取同类重复界面即可。

必须保留的现有语义：已有值优先于识别建议、建议需要确认、空值不自动视为已填、保存失败不推进、账号切换/退出后清理预填轮次。不能把滚轮显示的默认落点误当成用户确认的数据。

实名认证的 Mock 人脸模拟与 Backend 身份摘要是不同功能，暂不适合强行统一整页。若需要一致，先改变原型要表达的产品流程。

## 3. 简历管理：局部改造即可

`src/屏幕/我的简历.tsx` 的基本信息、经历、教育、技能、证书、优势已读同一组全局切片，使用同一 JSX；诊断区域也已投影成共用行。主要分叉在附件区域（约第 539 行），Backend 多附件、状态、滑动动作和授权，Mock 一条演示文件及说明。

建议优先提取附件区的展示及操作回调，把上传/替换/解析/删除、轮询和 PDF 预览留在控制层；复用现有附件刷新与预览 hooks，不另建文件管理框架。诊断区域只接收标题、摘要和行列表，不再在 JSX 内判断模式。

`工作经历.tsx` 的教育和工作编辑器主体已共享，真正重复的是学校/专业/行业目录选择。与 onboarding 选择器一起处理，避免两边分别造组件。

`个人信息.tsx` 还含账号手机号、简历披露联系方式和头像动作。可以共用字段行，但账号凭证和简历披露字段不能合并，未接入写线也不能以 Mock 的本地保存冒充真实提交。

## 4. 求职意向：管理页改造价值较低，子页价值更高

`求职意向管理.tsx:39` 已经共用完整页面；模式差异集中在求职状态：Mock 本地轮换三档，Backend 从简历快照读状态且只读。传入状态文案和可选回调即可，不必重写管理页。

`添加意向.tsx:75` 外层拦 Backend 无效编辑坐标，内部 `意向编辑表单` 已统一。需要保留跨选择子页返回时的草稿、路由编号切换，以及保存失败不清草稿。它更适合小幅整理控制逻辑。

真正值得收敛的是 `选择城市`、`选期望职位`、`选期望行业`。这些页面仍有较大模式分支，并与 onboarding 的选择器重叠。可放到同一批组件工作，避免只整理管理入口却漏掉用户实际编辑路径。

## 5. 岗位管理：重点是发布/编辑，不是管理列表

`岗位管理.tsx` 主体不读取数据源模式，已通过 `操作.归档岗位/重开岗位/删除岗位` 分离写入。`岗位详情.tsx` 主体也共享，主要分叉在公司/发布方区域、无效路由处理及地址兜底。可把发布方投影和权限/导航移出，保留现有详情布局。

`发布岗位.tsx:308` 的 `岗位编辑表单` 同时包含草稿、JD 导入、解析轮询、目录查询、引用校验、结构化要求确认、提交与跳转。已有 `基础信息步/职位描述步/职位要求步` 是合适的展示基础；但 `职位要求步` 仍接收 `是后端`，职业分类层还有两份。

建议让三步组件只接收字段值、选项、错误、编辑限制、确认状态和回调；JD 导入处理留在独立控制逻辑，复用当前操作层，不复制整份 Backend/Mock 表单控制器。不能为统一显示去掉真实城市/类别引用、结构化要求确认或 revision 并发保护。

### 需先核实并修正的数据来源

必要性：required；复杂度影响：不变。

`岗位管理.tsx` 的 `数在谈` 和 `岗位详情.tsx:89` 的确认文案，从 `状态.企业候选列表` 计数；Backend 初始状态将该 Mock 切片置空（`状态/初始状态.ts:269`），真实 P5 不水合它。代码层面因此不能把这个值作为 Backend 的真实在谈人数，也不能据此判断可以删除。

这影响人数显示、停止招聘确认和删除入口，不代表已证明服务端允许错误删除。修正应使用经合同确认的权威数量/能力；若当前无该事实，表达未知并调整文案，不能拿尚未完整加载的 P5 分页长度代替总数。本轮不修改列表，由实施 worktree 协调归属。

初始化页的固定扫描计数同属需修正的事实表达（必要性：required；复杂度影响：降低）：删除无真实来源的数量承诺即可，不必为保留动画新增扫描进度 API。

## 建议实施顺序与边界

1. 在谈详情独立成批：统一展示与动作卡，保留 P5 控制、授权和状态机。
2. 选择器 + 招聘名片：选择器覆盖 onboarding、意向、简历和发岗实际重复点；名片删除两套表单。
3. 发布/编辑岗位的控制分离，以及简历附件区局部收敛。
4. 其余管理页只做必要的小调整，不为“所有页面都分三层”制造文件。

共享展示应以现有产品视觉为起点，但用真实 Backend 支持的业务状态校准。最小结构是页面入口/控制逻辑 + 共用展示，继续复用现有操作层和 mapper；不新增全局 adapter 注册表或第二套状态系统。

验收需要两组证据：同等业务状态和等价数据走同一展示组件/CSS；真实来源控制层仍通过已有的保存失败、无效深链、权限、披露、换账号与过时响应测试。额外验证空数据/缺能力时的预期布局，不能要求不同状态的截图完全一致。

本次未改业务代码、未运行测试或浏览器验收。结论依据当前 worktree 的源码、相关 spec 和测试用例阅读，不将组件共用等同于已验证的视觉一致。
