## 四、不做及原因（与产品机制冲突，或已有更强的等价物）

| BOSS 有的 | 冲突 / 替代在哪 |
|---|---|
| 立即沟通 / 直接开聊 | 绕过「匿名初筛 → 递交简历」两个阶段直接进真人对话，违反四阶段顺序推进不可跳（`类型.ts:5-7`）。我们的等价物是职位详情的「直接聊」，且用结构表达了「点下去就实名」（旁听条 `直聊会话.tsx:58-66` + 系统条「已互相看到身份·匿名保护结束」），不需要再加任何东西 |
| 简历一键投递（露真名） | 递交简历在我们这里是第二阶段、由代理隐去联系方式后发出。跳过匿名初筛直接实名投递，整个阶段机作废 |
| 「要简历」/「要联系方式」按钮 | 这两件事是阶段的自动结果（递交简历阶段代理互递、意向确认时自动互换），做成按钮等于给用户一个跳阶段的口子 |
| 看谁看过我的岗位 / 候选人在线状态 | 前者把候选人的浏览行为交给企业；后者要求候选人实时在线态。双盲下候选人在确认意向前不该有任何可被观测的行为轨迹 |
| 竞争者人数 / 「你超过了 X%」 | 可反推他人。`企业详情.tsx:7-9` 已经写死了这条立场 |
| 按薪资范围筛候选 | 代理之间只交换「有没有交集」，企业侧根本拿不到候选期望数字（`候选筛选抽屉.tsx:10-12` 已写明为什么不给这个入口） |
| 条件搜索人才库（选城市+学历+年限出人） | 把双盲池当简历库刷，代理的初筛合同就没意义了；也没有对应数据源 —— 推荐流是代理筛出来的结果，不是可被任意检索的库。**区别于条目 26**（在自己已有的列表里检索，那条要做） |
| 简历多维筛选池 | 同上。简历要走「递交简历」阶段才到手，`匿名简历档` 是代理递过来的结果不是池 |
| 候选人「状态标记」（待沟通/已沟通/已面试/已淘汰） | 阶段由四阶段状态机唯一决定，再让用户手动标一个平行状态，两套进度会打架，「顺序推进不可跳」被架空。**区别于条目 20**（私人备注要做，它填的是用户自己的记忆，不是谈判状态） |
| 岗位置顶 / 刷新 / 曝光道具 | 前提是「候选人在刷岗位列表，谁排前面谁被看见」。我们是代理按硬性条件去找人，岗位排序对触达量没有任何影响。做进来会变成卖曝光的道具，并暗示「充钱能让代理更卖力」—— 对产品机制的直接误导 |
| 曝光数 / 沟通数 / 简历数 | 没有额度概念，「曝光」在代理主动寻访模型里不成立。已换成 A2A 漏斗四格（已寻访/初筛通过/在谈中/待你拍板） |
| 求职端列表排序器（薪资从高到低 / 最新） | 排序权在代理。给排序器等于把代理降级成列表控件。只补默认序（条目 36） |
| 快捷回复 / 常用语（两端） | 它是给「一天要发 50 条一样的话」用的，而那 50 条在我们这里被代理接走了。剩下的真人对话只发生在意向确认之后，每条都是高价值的，模板化等于承认代理没干成活 |
| 相似职位推荐位 | 「这个不合适再刷几个」是代理的活。真需求是「这家还在招什么」，已在 `企业详情.tsx:369-395` 做完，接上入口即可（条目 40） |
| 职位详情的福利 chip 行 | 会打掉我们「代理已核对 / 公司自述未核实」的区分（`企业详情.tsx:212-223`）。若要露出，只露「共 N 条条款·M 条已核」这个数 |
| 公司主页的员工文字点评 | 一旦有正文就要配审核、反诽谤、企业申诉一整套。这一页的命题是「代理核过什么」，不是众包口碑，标签统计已给出信号强度 |
| 「我看过的」浏览历史 | 用一份被动日志去凑「拿不准先留着」的需求，不如直接做那个功能（条目 16） |
| 会话置顶 / 免打扰 | 会话量结构性地少（AI代理 1 条 + 直聊若干 + 确认后的真人若干），排序已由「需要你」这条线接管。等真实量级出来再看 |
| 席位制多账号售卖 | 只补「同岗共管」（条目 22），不补席位。对候选人露出的仍是「一家公司 + 一个对接人」，不该让他面对一个委员会 |
| 批量拍板 | 一次拍板 = 一个人的机会，且拍完会沉淀成长期规则。批量拍板 = 批量写规则，用户不会知道自己刚教了代理什么。「决策一律在详情页做」的现有设计是对的 |
| 搜索建议 / 联想 / 热搜 | 7 条 mock 数据上做联想没有信息量，等于做假。真实数据后再议 |

## 五、待确认（需产品拍板，未混进上面的结论）

1. 求职端跨意向：意向栏加「全部」档，还是统计跟着当前意向走（条目 6）
2. 意向确认之后我们还管不管 —— 面试邀约 / 日程 / offer 的产品边界（条目 21）
3. 「先留着」叫什么、放哪个宫格位。**不能叫「收藏」**：企业端的 `收藏候选` 是攒人才池的语义，两端不对称，同名会混（条目 16）
4. `/hr/thread/:id` 还需不需要「连续读完整场谈判」这个视图，还是分段折叠已经够（条目 43）
5. 「已寻访」这个数的口径：代理触达过的人数，还是代理扫过的简历数？两者差一个量级，影响整个漏斗的可信度（`岗位详情.tsx:83`）
6. 「给代理提要求」是不是高频动作 —— 决定规则入口是从「筛选」位置拿走，还是换个更明确的位置（条目 38）
7. 推荐流批量否决的真实频率：如果代理筛得准，本不该出现需要批量否决的量，那这条就不该补、该去调代理
8. 市场流的真实数据量级 → 决定要不要做分页 / 无限滚动
9. 公司相册只有本公司有（`企业详情.tsx:48-53` 只对 `yunqu` 合并企业端覆盖）：mock 缺口还是设计如此
10. 「直聊」与四阶段 / 双盲是什么关系，代码里没写清；且 `直聊会话.tsx:86` 的「发简历」反馈里还带着真名文件名。建议先对齐口径再动
11. 岗位详情「已寻访」这一格：接后端前是先留静态兜底，还是先不放
12. 两端卡片密度是否要拉平（条目 61）
